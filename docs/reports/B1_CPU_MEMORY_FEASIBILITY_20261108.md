# B1 20-worker CPU and memory feasibility — evidence-based assessment

**Candidate for independent review; no host action or new experiment.** The author's B1 setting remains **20 audit workers**. The available evidence makes that setting plausible to investigate on TASL-7, but does not establish that the loaded server plus a representative 20-worker audit fits in current RAM or avoids interference. This is a practical resource assessment, not an author decision, a new requirement to benchmark every node, or launch authorization.

The independently reviewed inventory `/private/tmp/paper-b-b1-capacity-readonly-20261107.bKE0PcWq/inventory.txt`, SHA-256 `03186261d088a063335be4dc8dbda245e7bda2c43dae0f6866717ff5b9e9b704`, recorded 7 November 23:07:18 UTC: **63,420,669,952 bytes MemAvailable** (about 59.1 GiB), **24 online CPUs**, load averages 0.05/0.03/0.00 and 1,106,530,304 bytes swap already used. These are aggregate, non-atomic past snapshots, not a reservation or evidence of available CPU affinity, cgroup quota, current concurrent load or the host memory consumed by the future server. Dividing that earlier MemAvailable by 20 gives about **3.17 GB (2.95 GiB) per worker** only if the pool used every byte; this arithmetic is not a safe per-worker allowance because the server, controller, shared services and headroom also need memory.

The fixed harness nodes have modest raw dataset dimensions: bundled digits 1,797 × 64; the independently reviewed offline loader observations report credit approval 690 × 15 and ionosphere 351 × 34. These dimensions support the judgment that datasets themselves are small, not a RAM upper bound: categorical encoding, split/transformed copies, Python/numpy/sklearn libraries, allocator behavior and model state add memory. The pinned OpenML benchmark admits logistic regression, random forest and gradient boosting, with `n_estimators` up to 500 and `max_depth` up to 30; random forest sets `n_jobs=1`. Digits uses sklearn's MLP with declared grid `HIDDEN_UNITS` up to 256 and `MAX_ITER` up to 300. Model choices and fitted states can materially change peak usage; neither compressed cache bytes nor raw rows measure process memory.

`r1/exam/campaign.py:41` uses `ProcessPoolExecutor(max_workers=job['workers'])` and submits at most 20 distinct configuration audits at once; `r1/c3/audit.py:110` runs the four audit seeds sequentially for each configuration. This is not 80 simultaneous seed jobs. Each active configuration involves a pool process and its pinned `LocalWorker` shell/benchmark child, in addition to campaign/runner and the B1 server; 20 workers does not mean exactly 20 OS processes. `worker_environment()` sets OMP, OpenBLAS and MKL threads to 1 for B1 worker children. It does not prove a fixed total thread count for every linked library or server. Twenty CPU-bound benchmark children on 24 online CPUs leave only nominal room for orchestration and the server, and online CPU count is not a dedicated-core allocation. Recheck competing load and actual affinity/quota rather than inferring exclusivity or changing `workers`.

The independently reviewed TASL-7 a3fedbb real-worker test (`B1_TASL7_REAL_WORKER_RESULT_REVIEW_20261107.md`) observed two sequential seed-7001 tabular runs using one test process and recorded Python 3.13.4, sklearn 1.8.0 and one-thread settings. Its retained console SHA-256 `f2d3e11cd66e3f934e6ded98ea380fa6cf2ef877e9e76d410950fde5fe2a2d48` contains no measured peak worker RSS or aggregate 20-worker RAM. The accepted offline OpenML loader observations are compatibility/shape checks, not fitting or worker-memory measurements. No source reviewed here supplies a credible per-worker peak, actual native server host RAM, or concurrent pool peak. Consequently the old snapshot alone cannot establish 20-worker memory headroom; it also does not demonstrate infeasibility.

## Practical next action, not a new blanket benchmark gate

At the already required final host/preflight window, the operator should use current read-only `MemAvailable`, swap, CPU count/affinity and applicable CPU/memory quota where visible, current competing load, and the actual **owned** server's host-memory observation during its already reviewed native-server preflight. Record availability before and with that server loaded, interpretation limits and any visibility gaps. Account for one campaign/runner, up to 20 pool workers and their child workloads, and a practical reserve for OS/other active work. Do not double-subtract an existing process already reflected in the baseline; document whether each estimate is incremental. An RSS sum can double-count shared pages, and `MemAvailable` or a single process's peak is not an additive guaranteed bound. If existing actual observations and a conservative, justified estimate suffice for the current host, independently review that assessment and proceed with the existing gate and monitoring; no additional per-node profiling is imposed.

If a **specific material unknown** prevents a defensible assessment — for example, no credible incremental memory estimate for a potentially large admitted tree configuration relative to current remaining headroom — the smallest useful additional engineering measurement is one independently reviewed, CPU-only, bounded **single configuration** on the affected node in an exclusively new owned directory, using the pinned harness, same host venv and thread settings, no LLM/GPU, no registered B1/audit seeds and no access to earlier STOP roots. Record the exact configuration, subprocess-tree and duration, peak/overlap method (prefer `/proc` per-process RSS/PSS and process identity plus host `MemAvailable`; avoid presenting summed RSS as unique memory), disk/log hashes and outcome; do not claim it bounds all candidate configurations. Preserve every file and stop rather than retry on failure. An operator/reviewer must first specify and review exact commands, representative configuration and no-preemption conditions; this document does not authorize or run a measurement. If current availability or other work makes even one CPU test inappropriate, defer it and report the specific uncertainty.

During actual B1, keep `workers=20`, apply the existing STOP and at-least-30-minute monitoring rules, and record resource pressure and progress with a cadence appropriate to observed change. If current conditions contradict the reviewed estimate or safe headroom cannot be established, preserve the scene and use the existing STOP/escalation path; never reduce workers, rerun or change the protocol automatically. Existing exact HEAD, final config/note, author gate, server/lease, O2 handover and all other B1 prerequisites remain separate.
