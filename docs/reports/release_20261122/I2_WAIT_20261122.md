## Disk I2 actually needs (measured)

- The prior successful I2 v2 job **759693** reports `DiskUsage=30` (HTCondor kB units; i.e. tens of kB of sandbox
  scratch) and `ImageSize=50` MB; its output tree in `/work` is **13 MB** total. The probe reads the pinned archives
  from shared `/work`, writes outputs there, and needs no multi-GB local copy.
- Thus the measured need is **well under 1 GB** (sandbox scratch + image); the **30,000,000 kB request is
  ~1,000× the observed footprint**, and there is no evidence in the I2 design/measured runs that 30 GB is required.
  (The existing request is recorded as-is; a changed value needs a reviewed JDL edit, not an operator edit now.)

## Options and recommendation

1. **Recommended: a reviewed `request_disk` reduction** (e.g. 2,000,000 kB = 2 GB, >50× the measured footprint)
   via the normal JDL-review path. Under the observed ETP set this expands candidates from 37 to **192** slots
   (CPUs≥2, Memory≥8000, Disk≥2 GB), while remaining conservative. It does not change the probe script, image digest,
  requested CPUs/memory or `ProvidesETPResources`.
2. **Another CPU pool** without `ProvidesETPResources` (if the author allows the environment change): would match
   immediately but changes the route/provenance; not recommended while option 1 is sufficient.
3. **Keep waiting** with the current 30 GB request: possible (1 willing/4 drained at the sample) but has already
   cost ≈19.4 h and gives no bounded wait; not recommended.
