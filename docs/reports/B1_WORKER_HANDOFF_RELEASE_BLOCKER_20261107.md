# B1 worker handoff: ambiguous release and STOP blocker — 7 November 2026

AI-assisted (Codex). **Static source analysis, not an accepted handoff or launch authorization.** Candidate `aa1d37ffc62706274acec58cfa27f126e8b69c96` and independent review `B1_WORKER_HANDOFF_R2_REVIEW_20261107.md` identify a real possible interleaving; no production instance or actual pipe/process test has been observed. The candidate remains NOT ACCEPTED and the author's existing STOP, no-deletion, host and final-checkout requirements remain unchanged.

The parent calls `release()`, which writes a newline-terminated record to the anonymous pipe; after the function returns, it sets `released=True`. A complete kernel write can be delivered before a Python exception occurs in the gap. The child may then validate the record, attach its log and enter campaign while the parent executes its branch intended for an unreleased child. Waiting 30 seconds and then publishing STOP is not a proof that the child, its descendants or server stopped; the child could alter evidence after STOP. The process can also die after sending the record, and descriptor-close errors can replace an earlier exception. This is a possible source-level schedule, not evidence that it occurred.

Setting a flag before the write would classify a potentially undelivered message as released; setting it after cannot exclude delivered-but-not-recorded. An additional acknowledgement or ready message similarly moves the last grant window rather than proving quiescence. Blocking signals alone has not been shown to exclude previously scheduled Python callbacks, other asynchronous failures, parent death, or close errors. A complete solution therefore needs either a reviewed release/STOP protocol that establishes a defensible linearization under the specified failure model, **or** a reviewed mechanism that treats a send as potentially delivered and safely quiesces all positively owned work before STOP publication. Existing B1 supervision does not prove such process-tree quiescence; it is the separate blocker documented in `B1_STOP_QUIESCENCE_INVESTIGATION_20261107.md` and `B1_STOP_EXITED_ROOT_LIMIT_20261107.md`. No particular cgroup, signal or handshake design has been established as the only possible solution.

The source change needed to improve descriptor-close error reporting alone can preserve the initiating exception and distinguish unreaped child status, but it cannot establish the missing released-child quiescence. An unreleased bootstrap redirected to `DEVNULL` with bytecode disabled limits one identified log write; it does not prove Python startup hooks or native dependencies are read-only, nor does a timed wait prove a child exited. Thus neither a reporting-only patch nor a test shim closes this blocker. Do not run or integrate the rejected candidate as a production B1 implementation.
