# B1 worker input authority — candidate, 7 November 2026

AI-assisted (Codex). **Candidate for independent review; not B1 launch readiness.** Production `r1.exam.campaign` is an executable worker entry separate from `exam_runner`. The parent runner checks the committed B1 configuration and registry, but before this candidate the child accepted a job's `authority_config` and independently read `job.value_grids` for the random anchor. Its later `author_gate` checks the note and selected fields, not every configuration key, and `authorized_b1_observer` did not compare `value_grids`. The normal reviewed parent populates both from its checked config; a directly supplied divergent job after a valid note exists was not shown to be a normal parent output. No such actual job or B1 execution has been observed.

The candidate rechecks the canonical committed B1 config, committed registry, author-gate HEAD and selected job fields at the production worker entry **before** creating the worker output or loading a node/manager. It compares `value_grids`, W, workers, LLM cap, audit seeds, host, node, seed, mode and proposal schema with committed configuration and requires the job HEAD to equal both checked configuration and author-gate HEAD. Ordinary parent-generated B1 jobs use those same values. DRYRUN does not take this production path. The later observer candidate, stage table and schema checks remain in place; this is not a substitute for them.

This is a cooperative point-in-time check, not a process authentication mechanism. It does not prove that the caller is the reviewed parent, bind `base_url` to the parent's actual llama server, prevent a same-UID concurrent writer after checking, or establish full transitive input provenance. A direct job with otherwise matching settings may still be invoked. The operator must use the reviewed runner, and server identity/lease, STOP behavior, exact final checkout review, host handover and all author phase gates remain separately required.

Other input source trace, bounded to source inspection: `runtime.author_gate` hashes the rule, both Stage A tables and acceptance record against the canonical config and binds the committed reference JSON to the note; `stage_a_pass_set` rechecks table and acceptance hashes when deriving eligible rows. `ExamRunner` checks registry bytes against the committed HEAD, hashes the value grid into its batch binding, and `campaign` reads that grid for the random anchor; the new check binds the job's grid path to the committed config, but does not separately re-hash the grid in the child against an immutable snapshot. Repaired templates have declared SHA checks at `template_repair_args`, while `validate_spec` checks GGUF and server binary size/hash/build before server use. These checks are not a proof against concurrent modification after validation.

## Follow-up: output boundary and remaining parent chain

Review of the first candidate found the production direct worker can supply `job.out` anywhere: the old child calls `require_worker_host`, not `host_check`, before `out.mkdir`, and the later production observer similarly does not apply the approved work-directory check. The follow-up invokes the existing `host_check` after committed-config authorization and before any worker output creation; it rejects resolved output paths outside the author-approved work tree and reuses its host/disk checks. The normal parent's root path is constructed under the parent output, whose own `host_check` already requires that tree. The additional seventh pure mocked unittest checks refusal occurs before output creation or worker initialization. Command and boundaries are as above; tool output reported `Ran 7 tests in 0.006s` and `OK` with no retained raw log.

**This is only an outside-work-tree path check.** It does not establish that any existing directory *inside* the shared work tree belongs to this run, or prevent a direct worker from colliding with another operator's files there. The parent creates `job.json` and starts the worker asynchronously; it writes `in_progress` in batch state only after `Popen`. Merely trusting that job file or a caller-supplied PID cannot prove a reviewed parent or unique output ownership. A safe complete remedy must, before any mutation, bind the owned batch and root paths and verify that the live worker was released by that reviewed parent; it must preserve existing paths and handle process lifetime/STOP races. The implementer and independent reviewer must develop and verify such a mechanism; site-operator qualification is needed for any `/proc`/OFD assumptions, with effort not yet established. Do not run a production worker pending that review.

The existing parent passes its B1 lease FD to the child with `pass_fds`, but the child receives no asserted FD identity and does not prove it has the same open file description. The parent verifies the server FD by `/proc` dev/inode while supervising, but the worker accepts `job.base_url` and does not prove that its endpoint is the reviewed server. Binding the child lease and server to the live reviewed parent requires a separately reviewed parent-to-child protocol and site qualification; a pathname, PID or matching inode alone is not proof of a shared OFD or socket identity. No such proof or actual host capability is claimed here. STOP-quiescence, no-deletion, and durable-STATUS constraints remain independent.
