### 1.1 The seal (§6 "The seal is procedural"; the 3b-1 seal list)

Every sealed directory gets `SEAL_RECEIPT.json` with the sha256 of every file in it, and nothing is ever overwritten.
`verify_sealed` compares a directory with its receipt (and the receipt's `sealed_path` with the directory), so a
missing, extra or changed file, or a changed receipt, is a STOP. File modes restrict nobody (one shared account), as §6
says.

Each seal step writes into `<target>.partial` and renames it to `<target>` only after the receipt is written (review
m2). A leftover `.partial` is an interrupted seal, and the step STOPs. **The operator's action:** report it and leave it
as it is; after the inspection, it is moved aside (for example to `_to_delete/`), never into place, and the step is run
again. A `.partial` inside a sealed job directory also stops the assembly (it is not an `attempt-N`).

The runs-tree copies of `out.tar` and `plan.tar` stay in clear after the seal: the job code reads them during the
table, and nobody opens them after it. Only an `out/` left in clear and the server log are removed.

| 3b-1 seal list item | Sealed by | Sealed form |
|---|---|---|
| per-attempt `out.tar` (with `job_record.json`, `diagnostics.json`, `SHA256SUMS`) | `seal_attempt` | copied; the sums are verified first |
| node wrapper logs | `seal_attempt` (the attempt's own log, as `node.log`); `seal_run` (all of `_logs/`) | copied; `logs.tar` |
| `out/` left in clear (tar failure, deadline, crash, closed attempt) | `seal_attempt` | `out_clear.tar`, verified member by member by sha256 against the source files (review m3); the clear `out/` is then removed |
| `plan.tar` and `plan_index.json` | `seal_node` | copied; the index must bind the tar |
| `wave_checks_wave<N>.json` | `seal_node` | copied |
| the job code's access log `_access_log.jsonl` | `seal_run` | copied |
| `_k_lock.json` | `seal_run` | copied |
| `_refusals/` | `seal_run` | `refusals.tar` |
| registered server spans | `seal_run` | `server_spans.tar` |
| TASL-7 `server-N/` (record, end, `llama-server.log`, manifest) | `seal_server` (on TASL-7) | `server.tar` under the new `proposer.sealed_root`; the clear `llama-server.log` is removed after its tar member is checked against `server_end.json` |

The order is enforced:
- `seal_attempt` needs the attempt's job record.
- `seal_node` needs the node to have ended (wave-2 checks written, or a node or timing STOP on record). It also needs
  every attempt of the node sealed, with the sealed record equal to the runs tree's.
- `seal_run` needs every node sealed, or declared `--not-run` (refused at the switch, with no node directory).
- `seal_server` needs `server_end.json`, which must bind the record and the log, and needs the server process gone.
  A server that ended without `server_end.json` (the serve wrapper killed, an OOM kill, a reboot) is first closed with
  `close-server` (review M3): the same host, no process naming the directory, the pid gone, the GPU lease free. It
  writes `server_end.json` with the log's sha256 and the closing time as the conservative end, with the log's latest
  modification time beside it (`latest_log_mtime_utc`); the receipt marks the span `closed`.

A closed attempt (no sums) may be sealed only if it has a STOP and no `out.tar`; its receipt is then its only
integrity record.

**The access log** (§6: "An access log in the sealed run directory records every opening of `out.tar` (who, when,
why); STOP 11 applies to any other"):
- Every opening of sealed G.5 content goes through `SealedTree` (or, for server logs on TASL-7, `open_server_log`).
  It checks the purpose's lock (§3 below) and verifies the sealed directory's receipt.
- Each opening has a kind, and takes only that kind's members (review M1): `ledgers` (the ledger pattern, from a
  campaign `out.tar`), `plan` (`plan.json`, from a sealed `wave<N>_plan.tar`), `chunk` (`out/chunk.json` and
  `out/audit/rows.jsonl`, from a chunk `out.tar`), `server_log`. Raw rows cannot be asked for.
- It then writes one line to `<sealed_root>/<run_id>/ACCESS_LOG.jsonl` before anything is read: who, pid, host, path,
  sha256, purpose, the rows of the lock, the kind and the member names.
- **A chunk's rows leave the reader only through `chunk_rows`, reduced by `reduce_rows`.** At the train/dev stage it
  returns kind and value for the label seeds only. An evaluation-seed row gives back neither its kind nor its value;
  it is checked (one row per planned run, as the job checks; an `ok` row has a finite numeric `outcome.value`, review
  m7) and dropped. The bytes of `rows.jsonl` are read into memory inside the reader, which the review ruled
  acceptable under the procedural seal.
- `check_access_log` is STOP 11 over the log: purpose, rows, kind and members must agree. The assembly and the
  integrity check run it, and the check of the sealed copy of 3b-1's job-code log, before they read. TASL-7's log is
  checked before every seal and log opening there (review m6).

**`llama-server.log`:**
- **Option (a)**, the access-logged seal of the server run directory, is built as `seal_server` (and `close-server`
  for a crashed server). It applies once the server has stopped.
  - Under G5-SLOT A with one server start (G5-TASL-GPUH A), the log is therefore in clear on TASL-7 for the whole
    table span. Only STOP 11 governs it then.
  - Under G5-TASL-GPUH B the server stops before every audit wave, and an audit job refuses until that server's span
    is registered. So the log is sealed and removed per wave.
- **Option (b)**, prompt logging off, is not built. It is an author decision (§6 below).

**Encryption (C6):** not built. `check_seal_mode` refuses any `seal_mode` other than `procedural`, as 3a's validator
already does. Building it needs key handling inside the job, a decrypting reader behind the same locks, and C6.

### 1.2 The assembly (§3; the sweep-2 conventions)

Built in the layouts `r1.c3.release` and `r1.c3.gate_input_builder` read for the gate source `g5` (tier T1), so that
neither file changes.

**Table directory:**
- `proposals.jsonl`, one row per tabled proposal:
  - `proposal_id` `g5.<mode>:<node>__s<seed>:t<step>`. Its middle part is the P3 instance id, as `release._instance_of_pid` requires.
  - the fields the builder and the release step use: `instance`, `instance_seed`, `node`, `memory_mode`, `noop`,
    `duplicate`, `delta_hat`, `sigma_node`, `sigma_cmp`, `incumbent_hash`, `candidate_hash`, `features`.
  - plus `decision`, `wave` and `audit_group`.
- `build.json`, which is deterministic (no timestamps): every input's sha256, σ_node per node with its summary path, the
  metric direction and suite per node, K and the seeds, the train/dev row, the readings of §6 below, and counts.

**Evidence directory:**
- `label_block.jsonl`, with the row shapes of `audit.evidence_blocks`:
  - `rule_noop` for no-ops;
  - `audit` with `delta_label`, `se_label` and `soft_parameters` (`sigma_node`, `k_label`, …) at the label seeds;
  - `divergent` when E5 makes the proposal divergent.
- `evidence_completion.json`, schema `g5_t1_evidence_completion/1`. The schema is not the B.2 audit's, so
  `release.evidence_tier` gives no tier and every raw reader needs both tiers' test rows. That is the condition of
  `R1_LABEL_RELEASE_ROWS_DRAFT`.
- After the test row: `evaluation_block.jsonl` (PRE-DIV A's `divergent_seeds` and `k_evaluation`) and
  `evidence_completion_test.json`.

**Labels** (§2.4, G5-AUDIT A, E5 on the label seeds, R1-MAIN-PROPOSER (e)):
- Every audited proposal belongs to the cross-instance group of its wave's plan, or of wave 1's plan when wave 2
  carried it. Every member of a group carries the group's label.
- Per label seed s: d_s = sign × (candidate unit − parent unit). The sign is +1 for `metric_direction: maximize` and
  −1 for `minimize`. The direction is read from the node spec at the family's G.5 commit, and that spec's sha256 is
  checked against `node_spec_sha256`.
- E5: if the candidate diverged on more than half of the label seeds, the label is `divergent`. Otherwise the label is
  the mean and se over the seeds where both sides are ok, and k_label < K_label marks a partial label, also when the
  dropped seeds are the parent's (a reading, signed in `t1_table_readings`). If fewer than half the label seeds are
  left once candidate and parent divergence are dropped, the assembly STOPs (the frozen builder would refuse that
  label anyway).
- σ_node is the joint σ of the G.1b summary the train/dev row cites (PRE-DELTA A as amended by REL-T1-G1B). For the
  seven nodes that summary must be the spec's REL-T1-G1B copy; for autoresearch, the completion record's
  `noise_floor_copy` under G5-ARPEND A (review m10) or the spec's copy under B.
- One complete sealed attempt is used per job and chunk. Every other sealed attempt must be an infrastructure STOP,
  as in G.1b's assemble.
- The plan is bound to its sealed campaign attempt (by `out.tar`'s sha256). Each chunk is bound to its plan (by the
  plan sha256, K, and its runs).
- The run must be sealed (`_run`, review m8). The sealed copy of the job-code access log passes STOP 11, the runs-tree
  log may not have grown since the seal, and the sealed K lock must equal the plans' K.

**The readings are bound to the author** (review M2). They are in `g5_tasl.TABLE_READINGS` and in the new note line
`t1_table_readings` (with the new `server_log` line; both rendered by 3a's `note_lines` and so checked verbatim by
`check_note`). The line ends with the author's choice for the logged Δ̂ of a proposal that diverged or timed out in its
campaign: `refuse`, `neg_inf` or `leave_out` (spec `key_values.t1_table_readings`). `assemble --note <signed note>`
takes the choice from the note: the note is on published main byte-identically, reads `approved: true`, binds this
spec's sha256, and its `t1_table_readings` line equals the line rendered from the readings the code applies, or the
assembly STOPs. Without a note, only `refuse` applies. There is no command-line choice. `verify_evidence` re-binds the
readings to the note named in `build.json` rather than replaying it.

**Compatibility** is shown by a test. The frozen builder builds a T1 gate input from the assembled blocks: 4 train,
2 dev and 6 test instances, with divergent label and evaluation counts in its report. The release step's

### 1.4 The G5-TASL-GPUH B meter (3b-1 review ruling 2)

- **On TASL-7:** `seal_server` writes the server's span into its receipt, from `started_utc` (server record) to
  `stopped_utc` (server end).
- **On TASL-2:** `server-span <receipt>` files a copy under `<run_id>/_server_spans/`. It is written once; the same
  bytes again are accepted, and other bytes STOP.
- **The meter:** `gpu_hours_consumed` under B adds every registered span. A server that a campaign job record names
  but whose span is not registered counts as open until now (an upper bound). This replaces 3b-1's campaign-wall-time
  lower bound.
- **Gaps** (review m5). `server_attempt` numbers the servers server-1, server-2, … without gaps, so a missing number
  below the highest registered one is a server whose span is unknown (for example one used only by a closed campaign
  attempt, whose record names no server). A gap counts as open from the previous registered server's stop (or the
  earliest known start) until now.
- **Preflight under B:** a campaign job needs `started_utc` in the server record, and an audit job refuses until every
  campaign's server span is registered and the registered servers are server-1..N without a gap.
- **Limit:** a server after the highest registered number that no campaign record names is invisible to TASL-2 until
  its receipt is registered; C9 compares the meter with TASL-7's card time.

### 1.5 Close-attempt (3b-1 review n2; review M4)

The metered seconds run from the attempt's start to the closing time, as in 3b-1 (conservative: STOP 9 guards a
signed cap, so an overcount goes to the author while an undercount is overspend). The latest modification time under
the attempt is recorded beside it (`latest_mtime_utc`, `gpu_seconds_to_latest_mtime`) for C9. An author row may adopt
the latest-mtime end later.

## 7. Inconsistencies with the draft, and judgments made

1. **§6: "every T1 label reader (the table assembly, …) opens only receipted partitions".** The assembly makes the
   input of the receipted partitions, so it cannot read them. Built instead:
   - it reads the sealed tree behind the stage's row, through the access-logged reader;
   - `release.py` then partitions.
2. **One label block for both stages.** `release.py`'s test stage requires the same label block as the train/dev
   release, so the label block written at the UNSEAL stage already holds the test instances' labels (label seeds
   only).
   - This is sweep 2's design: the block is in the evidence directory, and only the release step, or after the test
     row the tier's raw readers, may open it. This module reads it back only with both rows (B2).
   - It means test labels are computed, not released, at the UNSEAL stage. The review ruled this consistent.
3. **PRE-STAGE's "no evaluation value of any instance".** The evaluation block does not exist before the test row,
   and at the train/dev stage no evaluation-seed kind or value leaves the sealed tree's reader.
   - The bytes of `rows.jsonl` are still read into memory inside the reader, because a tar member is read whole; the
     review ruled this acceptable under §6's procedural seal.
4. **§6: the receipts "cannot detect a read".** True here too. The locks and STOP 11 rest on compliance; a deliberate
   copy of a sealed file is not prevented.
5. **3b-1 report §5 item 8 lists the TASL-7 `server-N/` "per wave".** Under G5-TASL-GPUH A, with one server start, there
   is one `server-N/` for the table, sealed only at its end.
6. **The copy step requires the summary under `sealed_g1b`.** "Out of the sealed G.1b runs" is read literally. The
   joined, gated G.1b run directory, which `assemble_gated_join` writes to a destination the operator chooses, must be
   placed there.
7. **Autoresearch under G5-ARPEND A.** The row's AR summary must be the completion record's `noise_floor_copy`
   (`check_ar_record` on published main), besides the summary's own checks (review m10).
8. **`release_checks.g5_integrity` requires the G.5 code under `sweep2/` equal to origin/main.** A later change there
   on main changes what the re-derivation runs, and can make the release fail: fail-closed. Hence the freeze of §5
   item 6.
9. **The assembly needs the whole run sealed (`_run`).** Under PRE-T1 A and the freeze wait (STOP 14), the train/dev
   release covers every un-STOPped node at once, so the table has ended by then; a node the switch refused is declared
   `--not-run` at `seal-run`.

## 10. Review round 2 (accepted) and what remains open

Round 2 accepted the unit with three non-blocking points.
- **n1 (fixed after acceptance).** `SealedTree._open` itself now reduces a chunk's rows to the purpose's stage, so raw
  `rows.jsonl` never leaves the reader, not even through the private opener; `chunk_rows` returns `_open`'s result.
  The M1 test also calls `_open` directly at train/dev.
- **n2 (open).** A crash between the rename of a seal and the cleanup (`rmtree(out)` in `seal_attempt`, the log unlink
  in `seal_server`) leaves the sealed copy and the clear content both present; a re-run STOPs with "exists". The
  operator STOPs and reports (cluster notes). A cleanup that runs when the target verifies against its receipt is a
  later refinement.
- **n3 (open).** `close_server` checks the old pid with `os.kill(pid, 0)`; after a TASL-7 reboot a reused pid makes it
  STOP with "still alive", with no override. Comparing the process start time or command line is a later refinement;
  until then the author decides how to close such a server.
- **Rulings on the flagged judgments.** Accepted: the assembly's note binding (publication, approval, spec sha256,
  readings line; the switch runs the full `check_note` at every job start); a server above the highest registered
  number that no campaign record names is a C9 limit covered by operator procedure; the assembly requires the whole run
  sealed (one train/dev release per source under PRE-T1 A and the freeze wait); proposer-card hours under GPUH A are a
  reported figure needed before the T1 report, not a STOP input.
- **Cluster notes (round 2).** After any `seal-server`, copy the receipt to TASL-2 and register it with `server-span`
  at once; after a TASL-7 crash run `close-server`, then `seal-server`, before any audit; under GPUH B never leave a
  started server unregistered; a STOP on an existing `.partial` is reported and the directory left untouched; a re-seal that STOPs with "exists" while `out/` or a server log is still in clear is a STOP to report (n2); run
  `assemble` at both stages with the same `--note`; keep the G.5 files under `sweep2/` and the spec frozen on main from
  launch to the T1 test release.
