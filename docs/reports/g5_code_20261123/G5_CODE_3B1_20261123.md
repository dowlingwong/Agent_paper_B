**The job** (`run_job`; CLI `g5_tasl.py run --job … [--server-record …]`; wrapper `t1_tasl_node.sh g5 …`). One call
runs one campaign wave, or one audit chunk, of one node.

Order (§3; one worker slot):
1. campaigns-wave1 (instances 1–4).
2. audits-wave1, one chunk per call. The plan is made once.
3. The wave-1 checks (`wave_checks`), run automatically after the last chunk.
4. campaigns-wave2, refused unless the wave-1 checks have no STOP.
5. audits-wave2, then the checks again.

A job refuses if it is out of order, if the node has a STOP on record (node or timing class, in any job record or in
`wave_checks_wave<N>.json`), or if the consumed GPU-hours already exceed the cap (STOP 9).

Before an attempt directory is created, these run under the lease; a refusal goes to `_refusals/`:
- the engines are present at the family's G.5 commit;
- host, affinity, GPU and foreign processes, ptrace and the delegated scope;
- the family checkout (`harness_g5` or `harness_g5_ar`);
- the environment (for autoresearch under G5-ARPEND A, from the completion record the switch passes in);
- for campaigns, the server record and `/props` before the wave;
- for audits under G5-TASL-GPUH B, the proposer must be stopped;
- for audits, the K lock and the next chunk.

After the engine:
- for campaigns, `/props` again (a change is STOP 12, re-run as a new attempt);
- the diagnostics;
- `out.tar` is written, then `out/` is removed (after a tar failure `out/` is kept and the job STOPs);
- `job_record.json`, `diagnostics.json` and `SHA256SUMS` are written.

Attempts follow G.1b's rule: only an infrastructure STOP may be followed by a new attempt.

**Audit planning.**
- The planner reads the completed campaign attempt's `out.tar`, verified against SHA256SUMS. Each opening writes a
  line to the access log.
- For each ledger it re-materialises:
  - the baseline state;
  - for every audited step, the parent (the last kept state) and the candidate (the kept chain plus the candidate
    diff).
  The ledger's incumbent hash must equal the chain's last state, or the job STOPs (integrity).
- Which steps are audited:
  - G5-AUDIT A: kept, discarded and divergent, timed-out ones included.
  - G5-AUDIT B: `ok` steps only.
- Groups:
  - A group is keyed by (incumbent hash, candidate hash) and audited once across instances.
  - A wave-2 group already audited in wave 1 is carried, not re-run.
- Units:
  - Under `reuse_parent_runs`, a unit is a code state, run once per audit seed within the node. Wave-1 units serve
    wave 2.
  - Otherwise each group has its own candidate unit, and each distinct parent state one parent unit,
    shared by its children (review M5).
- Chunks fit the walltime: runs × census run time × 1.25 × 1.5 within 24 h − 1 h.
- The plan shows which diffs the campaign kept, so it is stored in `plan.tar`. Only `plan_index.json` (counts and
  hashes) is in clear.

**E5** (per group, label seeds only):
- divergent: more than half of the label seeds diverged on the proposal;
- partial: some label seed diverged on the proposal or its parent;
- complete: otherwise.
Evaluation seeds never enter. A divergent baseline at a label seed is counted (it feeds STOP 8).

**STOP counters** (`evaluate_stops`, after each wave's audits, from diagnostics only):

## 5. Open questions and inconsistencies found

1. **The harness engines (§2).** They do not exist, and they need their own reviewed harness unit. Until then
   `check_engines` STOPs every job.
2. **"12 baselines" in the projection.** The baseline is one code state per node, and every instance audits it at
   the same seeds, so under parent reuse it is audited once. The §8 projection is therefore conservative.
3. **STOP 4's "refusals".** These are read as model refusals, which the engine records as parse failures. Diff
   refusals (`not_run_refused`) count toward D4 liveness, not the invalid share. A reply at the cap that parsed and
   ran is a contract breach (infrastructure STOP).
4. **Audit-once across waves.** A wave-2 group audited in wave 1 is carried, not re-run; the draft states audit-once
   across instances. STOP 1's denominator and the band use groups (unique audited proposals); members are reported
   beside them.
5. **Baseline divergence in an audit.** A baseline timeout at an audit label seed is STOP 8 (timing); any other
   divergence of the baseline there is a node STOP, like `baseline_failed` (review m1). The draft states this only
   for campaigns, so it is a proposed note line (§7).
6. **When K is fixed.** The table-wide K lock is written once the first audit chunk's attempt directory exists
   (review m2). Before that, a refused audit job fixes nothing.
7. **GPU-hour accounting.**
   - The meter counts the whole job wall time on the worker slot, setup included, plus closed attempts (review M7).
   - Under G5-TASL-GPUH B it adds the campaign jobs' wall times as the proposer card's held span (review M6). That
     is a lower bound until 3b-2 adds the spans from TASL-7's `server_end.json`.
8. **What 3b-2 must seal.**
   - The audit plan (`plan.tar`) and its index.
   - The access log.
   - The node wrapper logs. They carry only scope lines and STOP messages, but they sit outside `out.tar`.
   - `wave_checks_wave<N>.json`, `_k_lock.json` and `_refusals/`.
   - Any `out/` left in clear after a tar failure. The job then STOPs and keeps it.
   - Per wave, TASL-7's `server-N/`: `server_record.json`, `server_end.json` and `llama-server.log`.
   - **The `llama-server.log` handling is a 3b-2 item.** The log carries prompts and sits in clear on TASL-7 for the
     table's span. 3b-2 must do one of two things:
     - seal the server run directory with access-logged handling; or
     - start the server with prompt logging off. This is an author decision, because it changes `server_argv`.
9. **G5-MEM B.** It runs twin campaigns per instance (`instance_<k>_<mode>`). For a cross-instance group, twins of
   the same instance count as one instance.
10. **Extra label-only diagnostics fields.** Beyond the counts §6 enumerates, the clear audit diagnostics carry
    `label_seed_runs` (ok, divergent and infrastructure on the label seeds), `runs_planned_label` and
    `runs_planned_evaluation`, `seeds_planned`, and in `wave_e5`: `partial_label`, `complete_label`,
    `parent_divergent_seeds`, `baseline_label_timeouts` and `baseline_label_divergent_other`. All of them are
    label-seed counts or planned counts; none is an evaluation-seed outcome count (review B1, m7).

## 9. Review round 2 (accepted) and what remains open

Round 2 accepted the unit with four non-blocking points and two rulings.
- **n1 (fixed after acceptance).** The engines' own stop text no longer reaches the clear files: the diagnostics and
  the job record carry a fixed reason (`ENGINE_STOP_CAMPAIGN`, `ENGINE_STOP_AUDIT`), and the engine's text stays sealed
  in `out.tar`. The test feeds an engine stop naming a seed and a value and checks that neither appears in any clear
  JSON of the attempt. The harness contract should still keep engine stop text free of values and per-seed outcomes.
- **n2 (open, by choice).** `close-attempt` meters the time from the attempt's start to its closing, so a crash noticed
  late overcounts. That errs toward the cap (STOP 9 may fire early, never late); the operator should close a crashed
  attempt promptly. Using the latest modification time under the attempt as the end is a possible refinement for 3b-2.
- **n3 (disclose).** `gpu_seconds`, a missed chunk deadline (STOP 9) and the campaign timing state are coarse signals of
  timeouts, which are divergent outcomes, also at evaluation seeds. §6 lists GPU-seconds as clear, so this is allowed;
  the T1 report discloses it.
- **n4 (note text).** `trackg/audit_g5.py` hosts both engine subcommands (campaign and audit). The note's P5 citation
  should say so, since P5 describes that file as the audit runner.
- **Ruling 1 (one infrastructure bit).** Acceptable, on the condition that the harness classes every edit-caused
  failure (non-finite values, no metric, timeouts, crashes of the edited code, an OOM kill caused by the edit) as
  divergent, never as infrastructure. This goes into the harness unit's contract and its smoke test.
- **Ruling 2 (G5-TASL-GPUH B meter).** The campaign-wall-time lower bound is acceptable for 3b-1, since no EVIDENCE job
  can launch before 3b-2 is reviewed and the note signed. 3b-2 must replace it with TASL-7's server spans
  (`server_record` start to `server_end`) or make the switch refuse G5-TASL-GPUH B.
