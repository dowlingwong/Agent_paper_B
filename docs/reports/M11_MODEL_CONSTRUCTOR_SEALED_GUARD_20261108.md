# M11 direct Track P model constructors: sealed guard

**Candidate for fresh independent review; no D8 authorization.** Based on the accepted factory/Laya guard review `9e7abaaf211ae93eaa8839f70c2a2b84f91796c7`, the direct `PointerWrapper` constructor can bypass `build_model` and pass its base and optional warm-start path to Kev loaders. It now checks both with the same existing `_guard_model_input` before superclass initialization or Kev import. The direct `LayaWrapper` constructor now checks path-like encoder and weights before superclass initialization and dependency imports; `_laya_core` remains independently guarded. The accepted helper rejects sealed roots/descendants and conservatively rejects existing root or directory symlinks, including nonsealed ones. Direct wrappers and factory dispatch can therefore inspect the same tree twice; this adds potential I/O cost and retains the documented symlink compatibility change.

Exact constructor source ASTs were run in isolation using a fake superclass which stops at the original constructor boundary, as the available Python lacks PyTorch. Synthetic tests show sealed base/warm-start and Laya encoder/weights and nested sealed alias refuse before that boundary; ordinary paths, remote-model identifiers and nonpath objects reach it. The new and existing model base/manifest/hash guard tests returned **16 passed** in an exclusive pytest base. This does not test real torch/PEFT/Kev/Laya constructors or loading, later third-party caches/aliases, or compatibility of every live model tree. No real model, host, network, sealed file, scientific data or GPU was accessed.

`StartLuxWrapper` and `BinTokenWrapper` receive already-constructed model/tokenizer objects and do not themselves resolve a path in their constructors; `ReasonThenBinWrapper` inherits that behavior. Their third-party objects' earlier loading is not attested by this unit. `_Wrapper.save` and other training/serving write paths are not covered; five author-held files, complete D8 gate, other generic readers and hardlink/concurrent replacement limitations remain separate. No sweep-2 read or host action is authorized.
