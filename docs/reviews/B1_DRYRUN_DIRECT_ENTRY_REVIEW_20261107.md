## Blocking finding: the newly early host check may itself delete a temporary file

Candidate `r1/exam/campaign.py:156–162` invokes `runtime.host_check(cfg, out)` before creating the requested output or copying a node, which improves the original ordering. However `host_check` calls `tempfile.gettempdir()` at `runtime.py:278` **before** it tests the forbidden host name at `:279–281`. In the exact local test interpreter, CPython 3.11.11 `/opt/homebrew/Cellar/python@3.11/3.11.11/Frameworks/Python.framework/Versions/3.11/lib/python3.11/tempfile.py`, `_get_default_tempdir` tests candidate directories by creating and writing a probe, then calling `_os.unlink(filename)` in `finally`. `gettempdir()` caches its result, so that path is conditional on the cache state and environment. The target host's Python source, its temporary-directory selection, and whether the cache is already initialized have not been verified. This finding does **not** assert that a real remote file was deleted.

Thus a direct DRYRUN job can enter a helper that may create and unlink its probe before the candidate refuses an approved exam host. On a development host the same helper may also perform the probe. The author's 7 November prompt §0.6 says never delete anything, and §0.5 separately says never delete remote files. The candidate's tests replace `tempfile.gettempdir` with a mock (`r1/tests/test_b1_dryrun_entry_unittest.py:19`), so their assertions that `Path.mkdir` and `shutil.copytree` were not called do not cover this indirect filesystem action. Moving the host-name check earlier would close the forbidden-host ordering but would not, by itself, remove the deletion risk from an allowed development-host DRYRUN.
