## 1. Checks performed

### (a) Spec/pin model and the sealed-output rule

The spec is a single JSON (`s2_c2_job/v1`) validated fail-closed before any network/CPU/GPU use: image digest must be
a `ghcr.io/...@sha256:<64>` reference; `versions_markers`/`llama_server_sha256`; paper/harness repo+commit;
model URL prefix `https://huggingface.co/` + sha256 + positive size + alias; server binary/ctx/ngl/port/extra_args
(`$` refused); collector node/mode/instances (`runs == 20`, `proposal_schema == manager_proposal/v1`,
`verify_split_policy == vary`); requirements (CloudSite exactly Nemo2, device exactly L40S, machine regex compiles,
min_cpus positive, `requires_etp_ceph` true); output root under `/ceph/srv/dwong/paperb/sweep2/<run_id>` and no
`r1_sealed` part; label resolved only from the authorization (see (b)). The dry-run ad (real `condor_submit
-dry-run`, rc 0) matches the rendered JDL: `JobUniverse=5`, `WantContainer=true`,
`ContainerImageSource="docker"`, `ContainerImage="docker://ghcr.io/dowlingwong/r1-htc-gpu@sha256:69b06b35…"`,
`RequestGPUs=1`, `RequestCpus=16`, `RequestDisk=30000000`, `RequestMemory=64000`, `+RemoteJob=true`, and the
requirements exactly as rendered. The `sweep2/dryrun/` copies of the lib/job/spec are byte-identical to the
`sweep2/` sources (same SHA-256), so the raw JDL/ad correspond to the reviewed code. **The fail-closed guarantee is
weakened by the sealed-path check (BLOCKING 1).**

### (b) Label rule and the R1-SWEEP1-CLASSIFY regression test

`resolve_label` takes the label only from the authorization note (path + SHA-256 pinned in the spec; the note must
contain `approved: true`, name the run id, and carry `label: EVIDENCE`) or defaults to `ENGINEERING_ONLY`; a
`label_source` containing `sweep_index_label`/`index_label` is refused, and the collector receives only the
resolved label (`--label`, plus the `c3_label_sweep.label` in the extra manifest). The test
`test_index_label_may_never_select_the_table_label` exercises both refused keys, and
`test_authorization_note_sets_evidence_label`/`test_authorization_must_be_approved_and_named` cover the positive
and negative authorization paths. This is the right rule for this unit and the defect path is covered for this
unit's label selection (the R1-SWEEP1-CLASSIFY table-builder fix itself is a different, already-reviewed unit —
the test name/docstring should say "this wrapper's label path" rather than claim the table defect globally). **The
EVIDENCE note itself is not transferable by the current JDL (MAJOR 4).**

### (c) Requirements/CPU class and the sealed `/ceph` route

The template pins `TARGET.CloudSite =?= "BwForCluster-Nemo2"`, `TARGET.GPUs_DeviceName =?= "NVIDIA L40S"`,
`TARGET.Arch == "X86_64"`, `TARGET.OpSys == "LINUX"`, `TARGET.Cpus >= 16`,
`regexp("^g36[0-9]{2}\.nemo\.privat$", TARGET.Machine)` and `TARGET.ProvidesEtpCeph =?= True`; the unit doc says
the ads carry no `CpuModel`, so the class is the proxy above (the NEMO2 L40S node family; `g3605`, `g3608`,
`g3612`, … with 16 CPUs each), with `cpu_model_contains` optional for ENGINEERING and required once S2-C4 records
the model. **This is a defensible proxy** for the class given `CpuModel` is absent and the runbook explicitly
allows a class pin "from `condor_status`; record it", but three things are missing: (i) no raw `condor_status`
capture is committed to substantiate the class or the `ProvidesEtpCeph` claim (BLOCKING 2); (ii) the
`machine_regex`/`min_cpus` are **spec-driven values** — the validator only checks that the regex compiles and
`min_cpus > 0`, so a spec with `machine_regex: ".*"`/`min_cpus: 1` renders requirements that no longer pin the
class, contradicting the "fixed requirements template" claim (MAJOR 2); (iii) the runtime wrapper records the CPU
model but does not verify the landed hostname against the spec regex, the CPU count against `min_cpus`, or
`/ceph` writability — so an off-class/off-ceph landing would only be caught by the JDL (MAJOR 3). Note also the
regexp matches the whole `g36[0-9]{2}` family, not only the enumerated L40S hosts; the L40S device requirement
narrows it, but a stricter/recorded host list (or the once-recorded `cpu_model_contains`) is preferable.

### (d) Fail-closed / STOP / no-retry / no-deletion and resume

The wrapper is a straight-line `validate_spec` → image → GPU → CPU → model fetch/sha → server start/health/build/
full-offload → collector; every failure raises `Stop` (exit 2) with the sealed directory and logs kept; there is
no retry loop and no `rm`/move; the entry script is `set -u`/`pipefail`/`umask 077` with a harness-python check.
Resume: if `run_dir` exists and the collector's `out/manifest.json` exists → `--resume <out>` (the collector's own
A.5 semantics, which re-runs a started-not-completed root whole); if the dir exists without a manifest → STOP
"no overwrite/retry". That matches the runbook's "resumable (A.5 semantics)" and "no ad-hoc retries". **Gap:** on
resume the wrapper does not verify that the existing record's pins (image/model/label/paper/harness/run id) equal
the current spec, so a changed spec could resume into a stale output (MINOR 1). The early-Stop path (before the
collector) leaves only the partial dir and the job stderr, no `job_record.json` (acceptable, but the doc should
say so).

### (e) Exam flags / image identity / GGUF

The server argv is the pinned binary with `-m <model> --host 127.0.0.1 --port <port> -c 16384 -ngl 99 -lv 4 --alias

the llama-server binary SHA; GPU identity comes from torch (`device name`/UUID/memory/CC) and `/proc/driver/nvidia`

(the I3 v3 evidence suggests the line exists; a mismatch would false-STOP) and the GGUF is 19.6 GB, which the
wrapper reads fully into memory for the SHA-256 (stream the hash; MINOR 2).

### (f) Dry-run JDL evidence and the "off-L40S / off-class / outside-sealed" risks

Verified: the rendered JDL and the ad pin the container image by digest, L40S, Nemo2, Arch/OpSys, Cpus≥16, the

## 2. Findings

### BLOCKING (fix before any ENGINEERING run)

**B1 — the sealed-output check is lexical and can be escaped with `..`.** `validate_spec` computes
`root = Path(_get(out, "root"))` and accepts it when `root == SEALED_ROOT/run_id` or `SEALED_ROOT/run_id in
root.parents`; `pathlib` does not normalise `..`, so a spec such as
`/ceph/srv/dwong/paperb/sweep2/<run_id>/../../out` (or `<run_id>/../<other>` or a deeper `..` chain) has
`SEALED_ROOT/run_id` in its *lexical* parents and passes, while `Path.resolve()` points outside
`SEALED_ROOT/run_id` (up to `/ceph/srv/dwong/paperb/…` or further). The wrapper then writes `job_record.json`,
`SHA256SUMS` and the collector's `out`/`work` outside the sealed run directory. *Fix:* `root = Path(...).resolve()`,
require `root == SEALED_ROOT.resolve()/run_id or SEALED_ROOT.resolve()/run_id in root.parents`, refuse symlinks in
the chain, and add the traversal test. This is the unit's core "outputs go to a sealed path" guarantee.

**B2 — the NEMO2 `ProvidesEtpCeph` requirement is unverified and could match no slot.** The template requires
`TARGET.ProvidesEtpCeph =?= True` and the unit doc says it comes from `condor_status` on deepthought 16 Nov 2026,
but no raw capture is committed; the chain's committed NEMO2 slot capture (`raw/raw_container_attrs_nemo2.txt`,
14 Nov) records the four container attrs and the apptainer version but **not** `ProvidesEtpCeph` — only TOpAS was
measured with `ProvidesEtpCeph=true` (`raw/topas_etpceph_gpu_slots.txt`). If NEMO2 L40S slots do not advertise
the attribute (or advertise it under a different name), the job matches **no** slot and idles; if they do, the
sealed `/ceph/srv` route is fine. *Fix:* commit the raw read-only `condor_status` capture for the NEMO2 L40S slots
(CloudSite/Machine/Cpus/GPUs_DeviceName/ProvidesEtpCeph), and either keep the requirement (with the capture) or
verify `/ceph/srv/dwong/paperb` writability in the wrapper and drop/relax the requirement accordingly.

**B3 — `request_disk = 30000000` kB is too small for this job's sandbox.** The job fetches a 19.6 GB (18.3 GiB)
GGUF into the container-universe sandbox and pulls/extracts the 4.87 GiB gpu image there; the I3 NEMO2 evidence
(same image/route) measured the OCI cache in the job sandbox (≈11 GB) and a final `Image size of job updated` of
28,107,500 kB for a 4.35 GiB model. With an 18.3 GiB model the sandbox need is roughly 11 + 18.3 + overhead ≈
30–33 GB, i.e. above the requested 28.6 GiB (30,000,000 kB). *Fix:* raise `request_disk` (e.g. 45,000,000–
50,000,000 kB) or fetch the model to `/ceph` (sealed/scratch) instead of the sandbox; record the measured sizes
in S2-C4. Related: `request_memory = 64000` MB is plausible but unmeasured for a 19.6 GB model plus the
`read_bytes` SHA (18.3 GiB heap at fetch time) plus 16 workers — record the measured peak in S2-C4 and raise if
needed; the fixed memory/disk in the renderer should become spec inputs once measured.

### MAJOR

**M1 — harness pin differs from the B2 protocol pin.** The spec clones the harness at `897d83c8…` (the Stage-A
exam implementation / prospective C3 pin per `STATUS.md`/`EXAM_X_CODE_HANDOFF.md`), while the B2 handoff and the
B2 authorization pin the B2 harness at `a3fedbb…` (`docs/r1/proposals/B2_HANDOFF_EXEC_20261115.md`: "harness
`a3fedbb`, `cache_prompt: false`; use `AR_HARNESS_ROOT` = the staged harness"). Sweep 2's campaigns are the pick's
C3 labels and must reproduce the B2 protocol/stack; a different harness changes the campaign code. *Fix:* pin
`a3fedbb` (the B2 stack) or justify the `897d83c8` choice against the runbook/author and record it in the unit
doc/spec; add a test/check that the harness commit equals the pinned protocol harness.
**M2 — the "fixed requirements template" is partly spec-driven.** `requirements()` renders `min_cpus` and
`machine_regex` from the spec, and `validate_spec` only checks that the regex compiles and `min_cpus > 0`; a spec
with a broad regexp (`.*`) or `min_cpus = 1` passes validation and renders requirements that no longer pin the
class. *Fix:* validate the class constants (the reviewed regexp family and `min_cpus == 16`), or hardcode them in
the lib and refuse spec overrides; add the negative test.
**M3 — no runtime verification of the landed class / ceph.** The wrapper records the CPU model and GPU but does
not check the hostname against the spec regexp, the CPU count against `min_cpus`, or that `/ceph/srv` is writable;
an off-class or non-ceph landing is only caught by the JDL requirements. For EVIDENCE (and ideally ENGINEERING),
re-check at runtime and STOP (the runbook §4 makes an off-class landing a STOP). Also record the **host name** in
the job record — the runbook requires "record per campaign the host, GPU name/UUID, driver, CPU model, image
digest, harness and paper commits, label string"; the current record has GPU/driver/CPU/image/model/server/
collector but no host.
**M4 — the EVIDENCE authorization note is not transferable by the rendered JDL.** `resolve_label` reads the
authorization note at spec-validation time from a path in the spec; the JDL transfers only `s2_c2_job.sh`,
`s2_c2_lib.py`, `s2_c2_spec.json`, so unless the note happens to be on an absolute path visible in the job (e.g.
`/ceph`), an EVIDENCE spec STOPs with "authorization note missing" and the EVIDENCE label is unreachable. *Fix:*
render the note into `transfer_input_files` when the spec pins one (and use a job-relative path), or reference a
path guaranteed on the job. (The ENGINEERING default path is unaffected.)
