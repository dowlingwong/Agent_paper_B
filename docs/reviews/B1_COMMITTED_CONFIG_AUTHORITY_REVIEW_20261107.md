# Independent review — B1 committed configuration authority

**Verdict: NOT ACCEPTED as a complete production B1 checkout-input binding.** Candidate `66466d018687df94237fa01bacf0557d3e22dcb9` is a useful check of the JSON configuration itself: the CLI checks the canonical pathname, clean HEAD, committed blob, worktree bytes and parsed settings; `ExamRunner.start` repeats that check and compares its HEAD with the author-gate HEAD before output creation and GPU lease acquisition. The review did not run tests, launch a host or worker, use a model or GPU, signal processes, or delete anything. No real B1 configuration substitution is asserted to have occurred.

## Blocking: the actual registry is not bound by the new config check

1. `r1/exam/runtime.py:457-462` accepts `ExamRunner(cfg, out, registry_path=...)` and chooses that override in preference to the committed config's `registry` key. `start('b1')` at `:488-499` revalidates the in-memory `cfg`, then the note and HEAD, but does not compare `self.registry_path` or the already-read `self.registry` against the configured path or the committed registry blob. A direct caller that supplies the expected `b1_config_head` and unchanged canonical config can therefore have the new config checks pass while the runner actually uses a different registry. `spec_order()` at `:564-569` draws the candidate specs from that selected registry, and `r1/scripts/exam_runner.py:340-355` uses those specs to construct eligibility and check template repairs; these checks do not by themselves bind every selected registry field to the reviewed checkout. The candidate report acknowledges general registry provenance limits, but its direct-caller description does not disclose this override path.
2. The ordinary CLI does not expose `registry_path`, but it still calls `Path(cfg['registry']).resolve()` without anchoring the relative configured path to `REPO`. The new `--config` check accepts the canonical absolute config path even if the process working directory is elsewhere. Thus, subject to the other gate paths being made resolvable (the author-note path is separately resolved and must be committed), the CLI can read a different relative registry from its working directory while the host checkout stays clean. Merely hashing that registry into `self.binding` at `:462` records the substituted bytes; it does not establish their reviewed identity.

For the minimal correction, define the production B1 registry relative to the checked checkout, reject any production override that differs from that canonical path, and verify its worktree bytes and regular committed Git entry against the same authorized HEAD before any output or lease. Recheck the actual registry object/digest used by the runner so that post-construction mutation does not silently bypass the check. Other relative input paths should be inventoried for the same cwd issue; a narrowly scoped registry correction alone should not be described as a complete input-provenance proof. Add both direct-override and non-checkout-cwd tests; test that the usual reviewed path still works and that Stage A/DRYRUN behavior remains intentionally scoped. An independent review must examine the exact proposed correction, and a new paper-code pin and final combined-checkout review remain required.

## Verified scope and limitations

- The candidate addresses the original source-level alternate-`--config` gap for production B1. A same-UID concurrent repository writer remains outside its point-in-time guarantees, as its report discloses; the clean-status check plus HEAD reread is not a lock against a file or HEAD changing and changing back. The config path's symlink checks and byte comparison provide useful refusal coverage, but the nine tests mock `Path.resolve`, `Path.is_symlink`, file bytes and Git, so they do not independently exercise real path topology, committed tree modes or hardlink/concurrent-writer behavior.
- The report's nine-test success is implementation-reported; its output is not retained as a separate log and was not rerun in this review. Both author-gate approval and canonical-config checks remain required: the draft `docs/r1/proposals/AUTH_DRAFT_trackx_b1_20261107.md` still says `approved: false`, and the actual phase note is not thereby approved. This review does not waive the note-order STOP or any host, scientific, recovery, no-deletion or STOP-preservation condition.
