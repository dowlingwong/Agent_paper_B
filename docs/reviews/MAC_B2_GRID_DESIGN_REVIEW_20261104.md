# Independent review: proposed B2 grid verifier (4 November 2026)

**Verdict: NOT ACCEPTED as an implementation-ready specification.** This is a design review only, by an independent Codex agent. Reviewed `docs/r1/proposals/B2_GRID_VERIFIER_DESIGN_20261104.md`, SHA-256 `b8030268f20f5aaca0b0378f85fb4ea956a7e735915218143da9d3e71a1f9023`, against `5fcea74`'s runner, `runtime.author_gate`, `runtime.verify_campaign`, v2 analysis, RUNBOOK X.4–X.7, and the current integrated PLAN. No model, server, GPU, experiment or real label was run. The B2 ranking STOP remains in force.

## Major 1 — The authority anchor is named but not operationally specified

The proposal correctly rejects a self-asserted `approved: true` and calls for author-committed note and PLAN decisions, yet does not specify how an implementation obtains and authenticates the authoritative revision, how it determines that the decision is the applicable one, or which row/cell/fields must be checked against the note and config. A caller-chosen commit, a locally fabricated Git commit with an author string, or a caller-provided SHA is not evidence of author authority. Existing `runtime.author_gate` confirms note bytes equal `HEAD:<path>`, then reads the **working-tree** PLAN and searches for a line containing the rule SHA and `R1-EXAM-RULE`; it does not itself prove that PLAN bytes came from an accepted, author-designated commit or that a power-plan decision was made. Do not use it alone as the proposed authority check.

Specify the trust root (for example a separately authenticated, author-designated published commit/ref and exact byte hashes), how the relevant dated §10 table rows are located and checked without matching prose/other columns, how superseding decisions are handled, and how a note's author approval and B1/rule/node/count fields are bound to that authority. Define a fail-closed result when the trusted reference or the necessary decision/format is absent. This is a trust-model specification request, not a demand to invent a power-plan decision or create a new authorization.

## Major 2 — Root receiving hashes lack an independent trust chain

The document requires verified roots and correctly says that hashes are meaningful only relative to a trusted binding, but does not identify the independent immutable evidence that supplies the expected root-manifest and `post_check` digests, nor how that evidence is captured and authenticated. `runtime.verify_campaign` checks a job hash and evidence hashes contained in the campaign manifest, then checks the neighboring `post_check.json` for the same computed manifest hash and a binding. The binding is derived from the configuration and registry/rule/grid hashes, and `post_check.json` itself is written by `ExamRunner.root`. If all these colocated files and their self-reported digests are replaced consistently, this check alone cannot detect it. `batch_state.json` contains manifest and post-check hashes for the resume path, but it too needs a separately trusted seal. The existing candidate-level aggregate stores root paths, not independent root digests.

Specify an independently established received/sealed artifact (including its authoritative source, capture time relative to the run, exact SHA-bound fields and failure behavior) that binds the launch config, run binding, candidate aggregates, every root, its `job.json` and `post_check.json`, and the B1/authorization identities. Add synthetic tests that rewrite the root, job and post-check **together** with internally consistent hashes, and tests for a changed/untrusted seal. If such an artifact cannot currently be obtained, explicitly retain STOP and report the requirement; do not create a seal after observing arbitrary files and claim it establishes preexisting provenance. The reviewer is not asserting that an actual run was modified.

## Other required clarifications

1. **Tie-break inputs.** The rule ranks ties by lower GPU-hours. Define how GPU-hours are verified against recorded server intervals and how `None`, non-finite, Boolean, negative and interrupted/upper-bound values are handled. Current summary sorts the supplied `gpu_hours`; an unverifiable or NaN value can affect the winner independently of grid completeness. Tests must include manipulated, missing and invalid costs and equal-Y ties.
2. **Numerical types and tolerance.** Require actual finite numeric values, not booleans or coercible strings, for all ten metrics and reported Y; specify the exact tolerated equality, including relative vs absolute behavior. The present `math.isclose(..., abs_tol=1e-12)` retains Python's default relative tolerance, so saying only “existing numerical tolerance” is ambiguous. Require valid exact seed types and order.
3. **Controls and compatibility.** Keep primary, thinking-on and schema-free results disjoint and verify their applicable evidence. The design appropriately disallows using sensitivity rows to fill primary coverage. Precisely define eligible finalist role, uniqueness, per-candidate grid and optional Track G decision/evidence. It correctly requires the latest host amendment rather than resurrecting an obsolete host. The design's instruction “preserve v1 behavior” should state the comparison point: the earlier M2 fix already made the default CLI refuse unstamped historical v1 B2 manifests, although the no-rule API still accepts them. Do not silently broaden that behavior or remove the v2 safety check.
4. **Feasibility and tests.** Positive synthetic fixtures must model the authority and receiving trust anchors—not merely declare them trusted—and cover missing authority, fabricated same-author commit, worktree-only PLAN edits, altered decision context, all-files-rehashed root tampering, false/missing evidence labels, swapped or reused roots, incomplete or duplicate finalists and equal-total wrong grids. State the threat assumptions, including what is not provable from local files. Retain the unconditional STOP until the design, implementation and evidence bindings are independently reviewed.

## Findings verified as sound

The candidate set is taken from the sha-bound B1 analysis rather than observed B2 results; the proposal rejects missing, extra and duplicate finalists. Its Cartesian grid uses the author-decided count and nodes, fresh instance seeds 9011+, and exact 9201–9210 ten-seed audits. Matching canonical IDs against expected pairs rather than splitting arbitrary node names addresses delimiter ambiguity. The optional Track G branch requires an explicit author decision and current host/fit prerequisites, and sensitivity outputs cannot contribute to the primary ranking. These are design requirements, not proof that the current implementation provides them.

Review scope does not accept any code, evidence, B1/B2 execution, author decision or rule freeze. Synthetic positive examples are not real author authorization. Re-check this design with the same reviewer after the trust boundaries and numerical/cost treatment are made concrete.

## Re-check of revised design — accepted as a conditional proposal only

The same independent reviewer re-checked the revised design, SHA-256 `9d09e6771a8dd2c69620662dba80e726902505483ce5eddbba45d751fcefc0a2`. Both major findings are addressed at the **design/proposal level**:

- The proposed authority snapshot requires an instruction authenticated independently from the evidence bundle, an exact author-controlled publication/ref and immutable commit, pinned PLAN and note bytes, structural dated §10 row parsing, and resolution of later supersession. Missing authority, ambiguous rows and unestablished current applicability STOP. Git author metadata, a caller-picked commit and worktree-only PLAN changes are explicitly insufficient. The document does not claim that such an author designation, power-plan row or B2 authorization already exists.
- The proposed independently designated receiving process and externally authenticated immutable inventory bind the run/config/rule/registry/B1/authorization identities, candidate aggregates, root/job/post-check digests, referenced evidence and server intervals. The proposal correctly distinguishes post-receipt integrity from proof of pre-receipt provenance, requires externally authenticated independent attestations, and retains STOP if any required trusted record is absent. Tests include rewriting all colocated files with internally consistent hashes against a fixed external commitment.

The draft also spells out exact audit/seed types, unique finalist/grid requirements, the optional Track G author and host conditions, primary/sensitivity separation, GPU-hours inputs and v1's current compatibility boundary. It labels both absolute-only `1e-12` comparison proposals as **new proposed validation choices**, explicitly noting that current audit comparison includes Python's default relative tolerance. They are not established thresholds or author decisions. The proposed strict refusal of interrupted GPU-hour upper bounds is likewise not settled; the appropriate treatment requires independent review and any substantive policy choice the author must make. Exact data types, cost comparison precision and path identity/alias handling still need concrete implementation tests; the design is not proof of their correctness.

**Verdict: accepted only as a conditional, reviewable proposal.** This does not authorize an implementation to claim an existing trust root, launch B2, freeze a rule, accept evidence, or enable ranking. The author must decide the relevant power plan, B2 authorization, authority snapshot and independently designated receiving arrangement; the implementer must substantiate current applicability, the actual committed record and run provenance, or fail closed. The verifier, numerical/cost choices, direct/CLI paths, fake trust anchors and full tests need a fresh independent review before the unconditional ranking STOP can be removed. No real evidence or server was accessed for this re-check.
