## 1. P4-T1CHARGE A: T1 in the probe charge

**The rule as built.**

*Input.* `probe-record` takes `--t1-wallclock <json>` (schema `trackp_p4_t1_wallclock/1`), in the same evidence form
as the probe wall clocks:

```
{"schema": "trackp_p4_t1_wallclock/1",
 "record_dir": "docs/r1/reports/trackp_p4_cluster_<date>/T1_versions",
 "jobs": [{"cluster_id": "<ClusterId>", "remote_wallclock_s": <condor_history <ClusterId> -af RemoteWallClockTime>}]}
```

*Binding to T1's committed record* (`t1_record`, `t1_charge`; the `check_cluster` pattern):
- The record directory must hold T1's `versions.jdl` and `versions.sh`.
- Every `*.submit` file in it is a `condor_submit` output. Each must hold a line
  `1 job(s) submitted to cluster <C>.` (T1 queues one job per submission). Those ClusterIds are T1's jobs.
- When the record holds submit outputs, the jobs given must be exactly those ClusterIds. A missing job, an extra
  job or a mismatched id is a STOP.
- When the record holds none, the ids cannot be checked. The charge is accepted and marked
  `cluster_check: "unverifiable (no condor_submit output in T1's record)"`, as `check_cluster` does for a record
  without a ClusterId. On `main` the record holds `versions.submit`, so the check is `match`.
- A test reads the committed directory and gets ClusterId 760065, with a synthetic wall clock.

*Required.* The record STOPs without T1's charge. The first record must give `--t1-wallclock`; without it the CLI
returns 2 and writes nothing. A rebuilt record (§5 step 6's re-run, or the round-3 recovery) takes T1 from the base
charge file and must not be given it again.

*Exactly once:*
- T1 is stored only in the base charge file `_wallclock.json` of the record's own run, as `t1_gpu_hours` with
  `t1: {jobs, record, cluster_check}`.
- A supplement (`_wallclock.<n>.json`) carrying either key is refused.
- If the record's run already has a base file, so that T1 could not be stored, that is a STOP.
- `probe_charges` applies T1 from the file by default.
- Each of these is a STOP:
  - T1 given while a charge file holds it;
  - T1 in two charge files;
  - a T1 ClusterId equal to a probe attempt's;
  - a T1 job id given twice in the input.
- A file whose `t1_gpu_hours` does not follow from its `t1.jobs` is a STOP.

*Launch.* `check_probe_ledger` (in `assemble` and the switch's `check_cap`) also STOPs when no charge file holds T1.
With T1, the re-derived charge equals the record's `p4_probe_gpu_hours` (tested on the CLI output and in the
end-to-end test).

*Record.* `probe_records.json` carries `t1_charged: true`, `t1_gpu_hours` and `t1` (source, jobs, the record's
ClusterIds and sha256s, and the check). Its `rule` cites P4-T1CHARGE A. The printed Markdown lines are unchanged:
T1 is inside `p4_probe_gpu_hours`.

*Note.* `gpu_hours_cap:` must cite P4-T1CHARGE A (`p4_switch.check_binding`). The draft's line now says that T1 is
included. A dated status bullet was added to the draft, which stays `approved: false`. The spec's and the probe
template's `caps.probe_gpu_hours_comment` say the same, changed identically in both files.

**Decision: every T1 job is charged** (the conservative reading). A repeat or a STOP attempt of T1 is its own job,
with its own submission and ClusterId. Each is charged its `RemoteWallClockTime` (seconds / 3600, rounded to 4
decimals as the probe attempts are). A job removed before it ran is listed with its `condor_history` value, which may
be 0.

There is no walltime floor for T1. The 7200 s floor is the probe's rule for an attempt whose record is unreadable.
T1 has no record to read: `condor_history`'s RemoteWallClockTime is its only and complete measure, and HTCondor
accumulates it over restarts of the same job.

The binding makes the charge complete: every submission committed in T1's record must be charged.

**Unchanged:**
- P4-EXTRAPROBE A (the first STOP-free attempt by submission order is used; extras are listed and charged);
- the killed-attempt charge, max(7200 s, RemoteWallClockTime);
- `probe-charge` supplements.

**For the cluster (replaces §5 step 6's `--t1-wallclock <seconds>`).** When T1 has left the queue:
1. Commit, in T1's record directory, its outputs and `condor_history 760065` (the plan's T1 "Committed" list).
2. Write `t1_wallclock.json` from that `condor_history` output, with one entry per `*.submit` in the directory.
3. Commit it beside `wallclock.json`.
4. Give `--t1-wallclock t1_wallclock.json` to the first `probe-record`.

If T1 is resubmitted, its new `condor_submit` output must be committed as another `*.submit` file. It is then
charged too.

## 2. T4 STOP: tokenizer staging in the GPU job

**Finding.** Tokenizer staging has no CPU route.
- On deepthought, transformers 5.19.0's `AutoTokenizer` lazy import calls `torch.accelerator.current_accelerator()`
  and fails without a device.
- The v2.2 CPU image has no env3 (job 760071, rc 127).

**What the job already does.** Step 6, `p4_lib.stage`, already stages the pool tokenizers inside the GPU jobs, both
the probe (`run_probe`) and the P.4 job (`run_job`). It runs env3 in the v2.2 GPU image, after identity, clone, env3
freeze and configs (and `inputs` in the P.4 job), and before the data build, the memory sampler and any `sft-dev`.
The step was never CPU-only: T4 was a desk-side preview of it.

**The minimal change.** The step's call and order are unchanged. It now records what it staged and fails closed:
- The env3 script (`TOKENIZER_STAGE`) still calls `serialize.load_tokenizer` for every `POOL` entry at its pinned
  revision. It now prints `huggingface_hub`'s cache path and the pool it used, in place of the bare count.
- `tokenizer_record` writes `staging.tokenizers` into the job record. For each pool tokenizer: repo, pinned revision,
  subfolder, and every file of its hub snapshot at that revision, with size and sha256 (symlinks resolved to their
  blobs).
- These are the pins the CPU staging would have used: `serialize.POOL`'s revisions at `paper.commit`, loaded through
  the same function.
- STOPs, each raised before any GPU work:
  - the step's non-zero rc (as before);
  - no pool record printed;
  - a hub cache outside the job's `HF_HOME` (R1-TRACKP-P4-RUNNER-DECISIONS (2));
  - a revision that is not a 40-hex commit;
  - no snapshot at the pinned revision;
  - a snapshot file resolving outside the cache;
  - no `tokenizer*` file in the snapshot (in its subfolder for `laya`).
- A test confirms that a staging STOP ends the probe with the record written, before any sampler, data build or
  `sft-dev`.

**T1 does not stage.** T1 reads `/opt/r1/VERSIONS.txt` and runs two `nvidia-smi` queries. It uses no tokenizer,
clone or network. Its reviewed bytes are already queued as job 760065, and a change would need a new pre-submit
review and a resubmission. Staging in T1 would test, outside the job's code path, the same step that the first
probe (`kev-0.8b` alone, T7) runs inside it before any other GPU job. The coordinator's "before T1 or the probe" is
therefore met by "before the probe's GPU work", and T1 stays minimal.

**Test plan.** A dated status note records that T4 is a STOP with no CPU route, that the step moves to T7 and the P.4
jobs, and that T1 does not stage.
