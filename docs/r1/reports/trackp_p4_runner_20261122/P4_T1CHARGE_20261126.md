## 1. P4-T1CHARGE A: T1 in the probe charge

**The rule as built.**

*T1's record is pinned* (`t1_record`; review round 1, M1):
- **Folder:** `T1_RECORD_DIR = docs/r1/reports/trackp_p4_cluster_20261125/T1_versions`. It is resolved against the
  repository root of the `p4_lib.py` checkout (`Path(__file__).parents[4]`), never the cwd.
- **Job files:** `versions.jdl` must have sha256 `fa7ec821ca1fd597184691117f0f846df139c0a40df32db4afb2553d2d33c97d`
  and `versions.sh` must have `125342d1cfed4fd435d68bbc0c5e7655845318d7522c7c9bd64536e1b3432025`. These are the bytes
  accepted in `P4_T1_VERSIONS_JOB_REVIEW_20261125.md`.
- **Submissions:** every `*.submit` file in the folder is a `condor_submit` output with one line
  `1 job(s) submitted to cluster <C>.`. Those ClusterIds are T1's jobs, and 760065 must be among them. There is no
  "unverifiable" case any more: a folder without a submit output is a STOP.
- **Rule for submissions:** every T1 submission is committed inside the pinned folder (`versions.submit`,
  `versions.2.submit`, and so on). A `*.submit` file in any other `T1_versions*` folder under `docs/` is a STOP. The
  test plan's 26 Nov status note states this rule.

*Input.* The first record takes T1's wall clocks in one of two ways (mutually exclusive):
- `--t1-history`: the entry is built from the committed `T1_versions/condor_history.txt`. That file is the output of
  `condor_history <ClusterId> -af ClusterId ProcId JobStatus RemoteWallClockTime`: one line per job, space-separated,
  with the wall clock as a float. This is the `-af` form that
  `docs/r1/reports/htcondor_prep_20261114/probes/parse_queue_times.py` reads with `line.split()`. Every line must
  have ProcId 0 and JobStatus 3 or 4 (the job has left the queue). The ClusterIds must be exactly the pinned submit
  set, each once.
- `--t1-wallclock <json>`: `{"schema": "trackp_p4_t1_wallclock/1", "jobs": [{"cluster_id", "remote_wallclock_s"}]}`.
  A `record_dir` key, if present, must be the pinned folder. When `condor_history.txt` exists, the JSON must agree
  with it.

Either way, the jobs must be exactly the pinned ClusterIds. A missing job, an extra job, or a job given twice is a
STOP. The base charge file holds the record's ClusterIds, the sha256s of the submit files and `condor_history.txt`,
and the source of the wall clocks.

*Required.* The record STOPs without T1's charge. The first record must give `--t1-history` or `--t1-wallclock`;
without either, the CLI returns 2 and writes nothing. A rebuilt record (§5 step 6's re-run, or the round-3 recovery) takes T1 from the base
charge file and must not be given it again.

*Exactly once:*
- T1 is stored only in the base charge file `_wallclock.json` of the record's own run, as `t1_gpu_hours` with
  `t1: {jobs, record, cluster_check}`.
- A supplement (`_wallclock.<n>.json`) carrying either key is refused.
- If the record's run already has a base file, so that T1 could not be stored, that is a STOP.
- `probe_charges` applies T1 from the file by default.
- Each of these is a STOP:
  - T1 given while a charge file holds it;
  - T1 in two charge files;
  - a T1 ClusterId equal to a probe attempt's;
  - a T1 job id given twice in the input.
- A file whose `t1_gpu_hours` does not follow from its `t1.jobs` is a STOP.

*Launch.* `check_probe_ledger` (in `assemble` and the switch's `check_cap`) also STOPs when no charge file holds T1.
It also re-reads the pinned record (`check_t1_record_charged`, review round 1, M1 point 5 and m1), and STOPs when:
- the record names a ClusterId that the stored charge does not hold (a T1 job submitted after the probe record; the
  chat decides);
- the record is no longer valid;
- `condor_history.txt` has changed since the record.

A rebuilt record runs the same check.
With T1, the re-derived charge equals the record's `p4_probe_gpu_hours` (tested on the CLI output and in the
end-to-end test).

*Record.* `probe_records.json` carries `t1_charged: true`, `t1_gpu_hours` and `t1` (source, jobs, the record's
ClusterIds and sha256s, and the check). Its `rule` cites P4-T1CHARGE A. The printed Markdown lines are unchanged:
T1 is inside `p4_probe_gpu_hours`.

*Note.* `gpu_hours_cap:` must cite P4-T1CHARGE A (`p4_switch.check_binding`). The draft's line now says that T1 is
included. A dated status bullet was added to the draft, which stays `approved: false`. The spec's and the probe
template's `caps.probe_gpu_hours_comment` say the same, changed identically in both files.

**Decision: every T1 job is charged** (the conservative reading). A repeat or a STOP attempt of T1 is its own job,
with its own submission and ClusterId. Each is charged its `RemoteWallClockTime` (seconds / 3600, rounded to 4
decimals as the probe attempts are). A job removed before it ran is listed with its `condor_history` value, which may
be 0.

There is no walltime floor for T1. The 7200 s floor is the probe's rule for an attempt whose record is unreadable.
T1 has no record to read: `condor_history`'s RemoteWallClockTime is its only and complete measure, and HTCondor
accumulates it over restarts of the same job.

The binding makes the charge complete: every submission committed in T1's record must be charged.

**Unchanged:**

- the killed-attempt charge, max(7200 s, RemoteWallClockTime);
- `probe-charge` supplements.

**For the cluster (replaces §5 step 6's `--t1-wallclock <seconds>`).** When every T1 job has left the queue:
1. Commit T1's outputs in the pinned folder (the plan's T1 "Committed" list).
2. In the same folder, commit `condor_history.txt`: for each submitted ClusterId, the output of
   `condor_history <ClusterId> -af ClusterId ProcId JobStatus RemoteWallClockTime`.
3. Give `--t1-history` to the first `probe-record`.

A resubmission of T1 before the record has its `condor_submit` output committed inside the pinned folder as the next
`versions.<n>.submit`, and it is charged too. T1 is not resubmitted after the probe record: if it is, the launch

## 2. T4 STOP: tokenizer staging in the GPU job

**Finding.** Tokenizer staging has no CPU route.
- On deepthought, transformers 5.19.0's `AutoTokenizer` lazy import calls `torch.accelerator.current_accelerator()`
  and fails without a device.
- The v2.2 CPU image has no env3 (job 760071, rc 127).

**What the job already does.** Step 6, `p4_lib.stage`, already stages the pool tokenizers inside the GPU jobs, both
the probe (`run_probe`) and the P.4 job (`run_job`). It runs env3 in the v2.2 GPU image, after identity, clone, env3
freeze and configs (and `inputs` in the P.4 job), and before the data build, the memory sampler and any `sft-dev`.
The step was never CPU-only: T4 was a desk-side preview of it.

**The minimal change.** The step's call and order are unchanged. It now records what it staged and fails closed:
- The env3 script (`TOKENIZER_STAGE`) still calls `serialize.load_tokenizer` for every `POOL` entry at its pinned
  revision. It now prints `huggingface_hub`'s cache path and the pool it used, in place of the bare count.
- `tokenizer_record` writes `staging.tokenizers` into the job record. For each pool tokenizer: repo, pinned revision,
  subfolder, and every file of its hub snapshot at that revision, with size and sha256 (symlinks resolved to their
  blobs).
- These are the pins the CPU staging would have used: `serialize.POOL`'s revisions at `paper.commit`, loaded through
  the same function.
- STOPs, each raised before any GPU work:
  - the step's non-zero rc (as before);
  - no pool record printed;
  - a hub cache outside the job's `HF_HOME` (R1-TRACKP-P4-RUNNER-DECISIONS (2));
  - a revision that is not a 40-hex commit;
  - no snapshot at the pinned revision;
  - a snapshot file resolving outside the cache;
  - no `tokenizer*` file in the snapshot (in its subfolder for `laya`).
- A test confirms that a staging STOP ends the probe with the record written, before any sampler, data build or
  `sft-dev`.

**T1 does not stage: a reinterpretation of the request, pending the user's decision.** The request said to stage
the tokenizers "before T1 or the probe". As built, they are staged only in the probe and the P.4 job, before their GPU
work. T1 is unchanged and stages nothing. The user is being asked whether that is acceptable; until then it stays as
built. The reasons: T1 reads `/opt/r1/VERSIONS.txt` and runs two `nvidia-smi` queries. It uses no tokenizer,
clone or network. Its reviewed bytes are already queued as job 760065, and a change would need a new pre-submit
review and a resubmission. Staging in T1 would test, outside the job's code path, the same step that the first
probe (`kev-0.8b` alone, T7) runs inside it before any other GPU job. The coordinator's "before T1 or the probe" is
therefore met only as "before the probe's GPU work", and T1 stays minimal. The first real run of the staging step
is the first probe (T7).

**Recommended cluster step before the first probe (optional; deepthought, no GPU, no HTCondor job).** This checks
the network route, the pinned revisions and the new tokenizer record ahead of time. It downloads the six POOL
tokenizer snapshots with `huggingface_hub.snapshot_download` at their pinned revisions and runs
`p4_lib.tokenizer_record` on the result. It does not load `AutoTokenizer`, which fails on a CPU host (T4). It runs
in env3 of the v2.2 GPU image, with the shell of plan §3.2 (`D`, `C` at the commit under test, `SIF`, `PY`):

```
cd "$C"
mkdir "$D/T4b_tokenizers"
$PY - "$D/T4b_tokenizers" <<'PYEOF' | tee "$D/T4b_tokenizer_record.json"; echo "rc=${PIPESTATUS[0]}"
import json, os, sys
from pathlib import Path
job = Path(sys.argv[1])
os.environ.update(HF_HOME=str(job / "hf"), HF_HUB_OFFLINE="0", TRANSFORMERS_OFFLINE="0")
from huggingface_hub import constants as C, snapshot_download    # after HF_HOME is set
sys.path.insert(0, "r1/scripts/htcondor/trackp_p4")
import p4_lib as L
from r1.c3.train import serialize as S
for name, (repo, rev, sub) in S.POOL.items():
    snapshot_download(repo, revision=rev, allow_patterns=S.TOKENIZER_FILES)
printed = json.dumps({"hub_cache": C.HF_HUB_CACHE, "pool": {n: list(S.POOL[n]) for n in S.POOL}})
print(json.dumps(L.tokenizer_record(job, printed), indent=1))
PYEOF
```

Pass: rc 0, `"count": 6`, and every pool entry listing its files with sha256. A STOP or a download error here shows
before the probe that the probe's step 6 would STOP. Commit `T4b_tokenizer_record.json`; the snapshot stays under
`$D`. This step needs the commit under test to contain this unit.
