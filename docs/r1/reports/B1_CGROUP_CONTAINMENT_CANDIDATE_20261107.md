## Directly wired behavior and boundary

For production B1, the candidate creates a new direct-child, unaliased exclusive batch directory and a fresh per-batch cgroup-v2 subtree beneath the runner's current UID-owned delegated cgroup. No cgroup directory is removed. It acquires the GPU lease before starting an outside-subtree guardian; the guardian is passed the same lease FD and a runner pidfd and is checked with `/proc` plus ancestor-to-descendant `kcmp` before work starts. Parent death is detected via pidfd rather than depending solely on control-socket EOF. On runner death or STOP the guardian requests a subtree freeze and keeps the inherited lease; the parent may independently attempt freeze if guardian communication fails. The parent waits for the kernel's `cgroup.events` `frozen=1` before treating the requested freeze as established. A failed or timed-out freeze is explicitly NOT CHECKABLE, not a claim of quiescence.

Server and worker children use an isolated Python `-I -S -B` bootstrap. It writes `0` to a pre-opened `cgroup.procs` FD, reports enrollment while its output remains DEVNULL, waits for an explicit one-byte grant, then attaches the owned log and `exec`s the intended binary in the same PID. The parent checks cgroup membership and same lease OFD before grant and checks intended process argv before using that PID. Worker and server use separate newly-created leaf cgroups; successful worker leaves must become empty, and a normal server shutdown targets its retained pidfd with SIGTERM and waits for the server leaf to become empty. Completed leaf descriptors are closed; their cgroup directories remain. STOP intent and the grant byte/normal server signal share a short lock; record/log writes are serialized against freeze, and the monitor's disk check publishes intent under that grant lock. A grant already issued before STOP intent may run until the asynchronous freezer reports completion; the actual delay is not measured. The inner candidate cleanup and loading monitor route production B1 failures through freeze rather than the old numeric-PID tree signal. Failure paths preserve original-error reporting on a best-effort basis.

Normal production B1 refuses any pre-existing batch, including non-STOP crash recovery. Its runner lock is retired only after exact inode/UID/content checks, into a newly-created `_to_delete/` directory with Linux `renameat2(RENAME_NOREPLACE)`; no replacement or deletion is intended. The final batch state is saved while the guardian and runner still hold the lease; guardian finish then requires the owned subtree to be empty. An exclusively-created `STOP.json` records B1 errors without replacing a previous STOP record, and the batch verifier refuses any existing STOP path (including a symlink). This does not make the many normal `write_json` atomic replacements, pinned harness pending-guard unlink/truncation, or all other production cleanup compliant with the author's literal no-deletion instruction.

## Important limitations and required review

* These mechanisms are cooperative, not a same-UID security boundary. Linux documents that processes may enter **or leave** a frozen cgroup: [kernel cgroup-v2 core interface](https://docs.kernel.org/admin-guide/cgroup-v2.html). A process joining a frozen group is stopped, but the subtree's membership metadata may change after STOP. Parent/delegation identity, controller permissions, all child migrations, concurrent writers and launcher ancestry need independent review and site qualification. The self-migration `0` mechanism is described by the [Linux man-pages manual](https://www.kernel.org/pub/linux/docs/man-pages/book/man-pages-6.17.pdf). An already submitted GPU operation or DMA is not proven quiescent merely by `frozen=1`.
* The guardian retains the lease but has no independently verified durable STATUS/publication channel if the parent dies; freezer failure may leave the workload unverified despite STOP reporting. Guardian and parent simultaneous failure, Python/runtime startup side effects, same-UID interference, a real kernel's cgroup/descriptor race and process scheduling are not established by mocks. `fstatfs` and kcmp rely on Linux x86-64 ABI; unsupported/denied capability is intended to STOP. Site tests must use uniquely owned processes and preserve any STOP scene.
* Direct invocation of `r1.exam.campaign` has separate unresolved inside-tree ownership, parent authentication and server URL binding; this candidate does not close that route. Parent crash/timeout, leaked pipe descriptors, slow or failing cleanup, final COMPLETE/guardian/lease ordering, partial STOP-file writes, and all state races require fresh adversarial review. A pre-existing STOP or any failed gate must never be retried automatically.
* `runner.save()` and other `write_json` consumers still replace prior snapshots, and the pinned harness may unlink or truncate pending guards. The candidate does not authorize running a test or B1 under the current no-deletion rule. The frozen Q2 reference and its 99% interval are untouched. Actual parent/worker handshake and server identity must be checked independently.

**Known unresolved completion ambiguity:** an exclusive FINALIZED or external exit-receipt file can become fully visible before its `fsync` fails; if STOP evidence also cannot be persisted, a reader may see apparently valid receipts even though the writer STOPped. The supervisor retains the flock while alive, but that does not solve its subsequent death. Neither this candidate nor state-preservation `21b128f` solves this storage/observer failure, and the combined implementation must not be accepted or used until the failure semantics and a verifiable resolution are independently reviewed. Independent `waitpid` alone does not prove the later receipt write succeeded durably.

The proposed resolution is a pre-existing ACTIVE sentinel which the independent verifier refuses, followed by a successfully fsynced receipt and directory while the supervisor holds the lease. Atomic no-replace retirement of ACTIVE is the final publication operation and the logical completion point; after it, process exit releases the lease without a further required write. This requires actual work-directory qualification for local atomic rename and the explicit assumption that failed rename has not taken effect; a later crash restoring ACTIVE is a safe false rejection. Signal handlers are blocked during the completion call, but unmaskable death, Python exceptions, rename return semantics and filesystem recovery require independent review. In particular, requiring post-rename directory fsync failure to mean STOP reintroduces the ambiguity. The coordinated helper is not present on this branch and the proposal remains untested as a combined implementation. `unittest_r13.txt` repeats 31 pure mock tests successfully; it does not exercise publication or real rename.
