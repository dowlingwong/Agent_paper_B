## Revision: release before success publication

The revised supervisor calls `_release_then_publish`: after actual runner wait and finalization verification it sends RELEASE and requires the guardian's RELEASED reply **before** the existing waited-success publication. Release send failure, receive failure, or a wrong acknowledgement cannot reach the publication call; even if the subsequent best-effort STOP record cannot be written, ACTIVE has not been retired by this path and the existing reader refuses success. While the supervisor remains alive it retains the lease. The modeled success point is the atomic ACTIVE retirement in `_retire_active_last`; after that point the run is classified as normal completion, including supervisor death after commit, and cleanup cannot turn it into STOP. This point depends on the documented cooperative writer and qualified local filesystem semantics, as well as the existing `_publish_or_reconcile` behavior. It is a proposed interpretation of normal completion for independent review, not an author decision or accepted policy.

**Residual risks / STOPs:** After the guardian acknowledges release and exits, but before ACTIVE retirement, supervisor death can lose the last lease reference. At that instant the guardian has observed the owned subtree empty, and ACTIVE remains reader-visible unless retirement has occurred; neither fact establishes that a lease is retained, nor proves GPU quiescence or storage crash durability. The failure window is real and unresolved, not a claim that it occurred; reviewer and operator must assess it against the actual STOP requirements. Any non-atomic or ambiguous filesystem failure after an effective rename combined with inability to verify or record STOP also remains unresolved; a mount label alone cannot establish its absence. The supervisor could also die concurrently with guardian release after a poll snapshot. It cannot publish before receiving RELEASED; after a committed publication this revision defines success, before commit the reader should refuse while ACTIVE remains. This ordering does not prove retention against simultaneous deaths of all lease holders or guardian abnormal death. No production-run authorization follows.

## Revision: explicit unverified commit disposition

If success publication raises and immediate reconciliation cannot verify the committed receipt, the supervisor now exclusively creates `B1_COMMIT_UNCERTAIN.json` **inside the batch**, then reports STOP and retains its lease. The actual waited-success verifier rejects the presence of that name before and after reading the receipt. Partial or symlink names also block; a permission or other lstat error is propagated rather than interpreted as absence. A post-publication exception with a successfully verified commit remains terminal completion and does not create a contradictory STOP. A release failure still precedes any success publication.

This does **not** solve all simultaneous storage failures: if a valid commit exists, reconciliation fails and the uncertainty name cannot be created at all, the supervisor reports that reader exclusion is NOT CHECKABLE. Once reads recover, a reader can accept that valid receipt because no in-batch record survives. The test deliberately models and exposes that limitation. A concurrent reader could also observe a committed receipt before the supervisor has detected and persisted a later uncertainty; both checks reduce the observation window but are not an atomic transaction. `SUPERVISOR_STOP.json` in the separate supervisor directory is still not consumed by the batch verifier; the new in-batch uncertainty name is the reader binding for this specific publication exception path, not a general replacement for STOP evidence. No claim is made that an ext4 label cures those limits.

## Revision: supervisor error boundary and verification timing

The supervisor outer exception path now treats every error after entry to the release/publication phase as a potentially committed outcome: it checks the actual receipt; a confirmed commit is terminal success, while an unconfirmed outcome creates the in-batch uncertainty record before entering STOP. Existing uncertainty names are retained and block readers. This includes a queued exception after `_publish_or_reconcile` returned but before `main` returned, the gap identified in R3.

A newly created, retained `B1_PUBLICATION.lock` is exclusively flocked by the supervisor before the release/publication phase. The public waited-success verifier requires a nonblocking shared flock on that same owned regular file for its entire read, so it refuses while the supervisor is publishing or retained on STOP. The supervisor's own reconciliation calls the private unlocked validator because it already holds the exclusive lock. This enforces the runbook's post-supervisor verification timing for cooperative users on a filesystem with qualified flock semantics; it is not cryptographic authority, does not prevent callers bypassing the public verifier, and does not establish behavior for copied batches, other filesystems, remote caches, or uncooperative same-UID writers. The lock file is retained, never deleted. A missing/unopenable/unsafe lock file refuses the public verifier. Actual host qualification remains necessary.

If uncertainty persistence and supervisor STOP persistence both fail, the running STOP supervisor still holds the publication lock, preventing an ordinary cooperating concurrent reader; if the last holder is subsequently killed and no disposition survived, a valid committed receipt may be accepted after lock release. The earlier lease-loss window after guardian RELEASED also remains. These combined-failure and uncatchable-death limits are explicit; no claim of universal durable STOP is made. Before successful commit ACTIVE remains, so the reader refuses when the supervisor dies. A crash after terminal retirement follows the documented terminal-success classification, subject to site filesystem semantics. The final rename still lacks a post-rename directory fsync and its crash durability is not proven.
