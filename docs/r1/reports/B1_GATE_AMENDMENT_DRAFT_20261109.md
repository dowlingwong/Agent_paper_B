## 3. Diagnosis

Class **D**, resting on **H2** (incumbent-relative increment not monotone in proposer quality); H1 (the two anchors cannot be ordered) not supported; H3 (power) supported; H4 (engineering) not supported; D7 PASS. The H2 signal: `random_valid`'s pooled standardised increment falls by 0.756 σ_joint from the first to the second half of each root's audited sequence; the fall comes from digits_mlp (−2.31 σ_joint there; without it, −0.036 σ_joint pooled); `scripted` shows no fall (+0.030 σ_joint). The code checks (`reports/B1_STOP_CODE_CHECKS_20261109.md`) found no engineering defect. Both anchors are random proposers: `scripted` is the E1b stand-in (one numeric symbol × a log-uniform factor in [1/3, 3], 30 % categorical switch on OpenML nodes) and `random_valid` draws a uniform active key and a uniform grid value; no pilot ever tested that one beats the other.

## 4. Amendment (R4)

- **Removed:** the anchor-ordering STOP. `scripted − random_valid` is still computed by the same code and recorded in the batch state as a descriptive field (`scripted_minus_random`, with `scripted_minus_random_role` = `descriptive_only (R1-EXAM-B1-ANCHOR-R4; ordering STOP removed post hoc)`). In the run outputs it is in `batch_state.json` (the anchor-gate record), not in `b1_summary_verified`; the B1 report reads it from there.
- **Kept unchanged:** the 7B duplicate-rate STOP and its pinned interval; all other B1 STOPs; the frozen B1 rule `x5_rule_v2` (which carries the ranking); seeds, budgets, pins and nodes.
- **Reported:** the three anchors' increments next to the candidates in the B1 table; and, descriptively for every candidate and anchor, the audited increment in the first vs second half of each root (`r1/scripts/b1_candidate_halves.py`), which enters no ranking, finalist choice or STOP.
- **Not done:** no replacement ordering gate was chosen. Any new ordering criterion chosen after seeing these anchors would not be a test.

**Reason.** The gate was meant to show that the exam can separate proposers, but its design compares two random proposers, a pair no pilot had shown to be ordered. On these data the two are not shown to be unordered either (H1 not supported; the point estimate favours scripted on all three nodes, with an interval including 0, H3). What the diagnosis did find is H2: on one anchor × node the incumbent-relative increment fell over the run, consistent with (not established as) a faster-improving proposer facing a better incumbent. That questions the anchor ordering as a test of discriminating power. It also bears on the ranking quantity of the frozen B1 rule, `pooled_audited_mean_proposal_increment`, which is the same incumbent-relative increment; the rule was fixed before Stage A and is kept unchanged, the H2 signal rests on a single anchor × node, and the first- vs second-half table is reported for every candidate so that a reader can see whether the effect recurs.

**Decision.** The author chose R4 on 9 Nov 2026, conditional on a design issue (PLAN §10 `R1-EXAM-B1-ANCHOR-R4`), and on 11 Nov 2026 extended it to the diagnosed class D resting on H2 with D7 PASS (`R1-EXAM-B1-ANCHOR-R4-H2`). ## 5. Appendix text (draft)

> **Post-hoc amendment to the anchor check (B1).** The pre-specified B1 procedure required that a random-valid proposer be shown to be worse than a scripted random proposer (paired instance bootstrap on the audited mean increment, lower 95 % bound above zero) before any candidate ran. In the first B1 run this check failed: scripted − random-valid +0.0046 [−0.0006, +0.0089] on 12 instance pairs, with scripted ahead on all three nodes on average. A read-only diagnosis found no implementation defect. It found that the incumbent-relative increment of the random-valid anchor fell from the first to the second half of its runs by 0.76 noise-floor units pooled over the three nodes, driven by one node (2.3 units on digits_mlp; at most 0.06 units on the other two; no fall for the scripted anchor), consistent with a proposer that improves faster facing a better incumbent later, though these data do not establish it. Because the check compares two random proposers that no pilot had shown to be ordered, and its statistic can be affected by this incumbent dependence, we removed the ordering as a stopping condition after seeing these anchor results and before any candidate had run, and report the anchors descriptively instead. The duplicate-rate check on qwen2.5-coder:7b was kept unchanged (0.496, interval [0.424, 0.580]). The candidate ranking quantity of the pre-specified B1 rule, the pooled audited mean proposal increment, is the same incumbent-relative increment; we kept the rule unchanged and report, for every candidate, the increment in the first and second half of its runs (Table ⟨Y⟩). The B1 run was restarted from scratch under a new run identifier; the stopped run is preserved. Table ⟨X⟩ lists the original check, its numbers and the amended procedure.
