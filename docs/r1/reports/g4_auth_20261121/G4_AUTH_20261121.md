## The defect

The G.1b note review (READY 75) found that `g4_tasl.launch` used `g1b_lib.verify_launch`. That binding can never be
satisfied by a note on `main` that names the launch commit, because the launch commit would have to descend from the
`main` that names it. `serve` (on TASL-7) checked only the note, with no launch binding at all. `check_note` also did
not bind the spec's `run_id` or harness commit, although R1-T1-TASL-ENV requires "harness at the commit the signed note
names".

## What changed (`sweep2/t1_tasl/g4_tasl.py`)

- `launch` (run-node, TASL-2) now defaults to `g1b_tasl.verify_launch_tasl(repo, spec, PLAN_ROWS, spec_path=...)`, the
  binding of R1-G1B-TASL-DECISIONS LB A. `g1b_lib.verify_launch` is no longer used.
- New `serve_launch`, called by the `serve` CLI, puts `serve` behind the same gate before the GPU lease is taken:
  - the note, with the spec;
  - both keys;
  - the same TASL launch binding.
- `check_note(..., spec=)` changes:
  - requires `run_id` and `harness_commit` to equal the spec's;
  - P3 must cite a signed G.1b note (`g1b_t1_tasl_`), not the word "G1B";
  - any field still containing `<FILL` is refused, so an unfilled template cannot pass.
- The module docstring gains a Launch paragraph. The G.4 block of `g1b_tasl_authorization.template.md` gains
  `run_id`, `harness_commit` and the new P3 wording.

## Tests (`r1/tests/test_t1_tasl_g4.py`)
