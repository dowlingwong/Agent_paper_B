# B1 worker parent handoff — candidate, 7 November 2026

AI-assisted (Codex). **Not accepted; independent implementation, host and final-checkout reviews required.** A direct production worker could previously accept an arbitrary in-tree `job.out` and caller-selected `base_url`, without demonstrating that the reviewed runner supplied its inherited lease or selected the server. The earlier accepted worker input checks bind config, registry, selected job fields and output to the approved work tree, but not ownership within that tree, process parentage or the endpoint. No actual forged job, real B1 run or host effect has been observed.

## Candidate behavior

A production B1 batch output must now be an **absent direct child** of the configured work tree, created exclusively after the existing config, author and worker-environment checks and before acquiring the lease. An existing batch path is refused and left untouched. This deliberately does not resume any existing production B1 batch, including an unrecorded non-STOP crash; an operator must choose a fresh reviewed run path. A campaign root is exclusively created inside that newly created batch; an existing root is refused. This is an additional operational restriction introduced to avoid touching pre-existing trees and needs independent review against the runbook and the author's no-retry/preservation instructions. DRYRUN, Stage A and B2 take the previous paths.

The parent creates an anonymous pipe, passes its read end and the existing B1 lease FD through `Popen`, then records the child in the batch state. Before sending a job-bound release record, it checks the parent lease file's identity, the child FD observed in `/proc`, and, for LLM candidates, the current server process, its lease FD and the URL from the runner's `service` object. It records parent/child start ticks, new root dev/inode/uid, the job digest and the observed server identity. On `Popen`, state-save or verification failure, the parent closes its pipe ends without sending a release; the child receives EOF or times out before entering the campaign. The pipe carries no file deletion and has no persistent receipt of its own.

Before `host_check`, authority recheck, node copy, manager creation, journal or worker initialization, the child waits for that release, checks its own PID, live parent PID/start ticks, own and parent FD dev/inode/uid, named lock identity, root path/dev/inode/uid, job digest and (for LLM candidates) server PID/start ticks/parent, FD identity and environment/job URL equality. Software anchors have no server URL. Production non-checkout cwd, different config, or different authority still STOP under the prior checks.

## Limits and STOPs

This is a cooperative parent/child protocol, not authentication against another same-UID process capable of forging a parent, pipe and record. `/proc` device/inode matches do **not** independently prove shared open-file-description identity, and the FD checks do **not** prove that a TCP socket/URL belongs to the server PID. In the intended parent code path, `Popen(pass_fds=...)` passes the parent's existing lease descriptor and the URL comes from its server instance, but these source facts and point-in-time snapshots do not exclude post-check races, hidden processes, a malicious same-UID peer, or in-flight GPU work. Existing site preflight must separately validate actual inherited lease/server behavior and Linux `/proc` capability; the target host has not been checked. Independent review must also assess whether parent-directed FD passing and current server instance checks are sufficient under the accepted cooperative policy. A stronger OFD or kernel socket identity proof is not claimed by this candidate.

The new batch output must not already exist and must be a direct child of the approved `work_dir`: the operator provides a new dated name and the implementer/reviewer verifies its runbook compatibility; choosing one is a quick operator step, but actual host ownership and no-new-start coordination are still unresolved. `/proc` or descriptor observation failure is STOP; the host operator must diagnose the capability with the independent reviewer and preserve the scene, effort site-dependent. No automatic retry is permitted after a B1 STOP. This handoff does not fix the existing B1 STOP quiescence, pending-guard deletion, test-suite deletion, full Stage A kill/resume coverage, author-note ordering, durable STATUS, or final checkout/host gates.
