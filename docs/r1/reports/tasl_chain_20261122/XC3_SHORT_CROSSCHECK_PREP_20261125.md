## 3. What the existing check does, and what "short" can mean

**The xc2 check** (`g1b-tasl-20261121-b-xc2`, note `g1b_xc_t1_tasl_20261123.md`, memo
`TASL_XC2_STEP1_RESULT_MEMO_20261122.md`) runs, per TASL-7 node, the default part (10 runs) on each host under a spec
derived from the signed G.1b spec, then `compare --mode xc`. **That is 20 runs and two jobs per node.**
`compare --mode preassembly` compares the node's **G.1b attempt** (TASL-7) with the cross-check's TASL-2 attempt;
its three step-2 PASS verdicts are on `main`.

**The PASS criterion** (`compare`, unchanged by this unit): every default and default_repeat outcome of c0..c4 is
present on both sides and identical (`g1b_lib._outcome`: the metric bit-identical when ok, the same failure when
failed), and both sides are deterministic. Otherwise STOP with a reason: `incomplete`, `nondeterministic:<host>` or
`cross_host_mismatch`.

| option for "short" | runs per node | criterion | supported as is? |
|---|---|---|---|
| fewer configs or one condition | < 10 | **changes** the reviewed criterion | no; rejected |
| xc2's design for these nodes | 20 (10 per host) | unchanged | no: `load_xc` admits only the G.1b TASL-7 nodes |
| **the TASL-7 job against the node's sealed G.1b TASL-2 attempt** | **10, all on TASL-7** | unchanged | no: `preassembly` fixes the G.1b side on TASL-7 |

**Chosen (decision XC3-SHORT, option A):** the third. The node's G.1b TASL-2 attempt already holds the same default
part (same 10 runs, seeds and harness), sealed, deterministic and complete. Comparing a cross-check attempt with a
sealed G.1b attempt is the reviewed `preassembly` comparison with the hosts swapped. It halves the runs, needs no
TASL-2 job, and compares TASL-7 with the very measurement the noise floor comes from. Option B is xc2's design (20
runs, a TASL-2 job per node).

## 4. The code change, and why

The existing code could express neither "short" nor the house-price case:
- `load_xc` admits only the G.1b TASL-7 nodes and both hosts;
- the comparison modes fix which attempt each host's side must be;
- the derived spec cannot give TASL-7 the CSV path that `mlgym_houseprice`'s `setup_command` needs, which the G.1b
  spec declares for TASL-2 only.

All changes are in `g1b_crosscheck.py`:

1. **A second schema**, `g1b_tasl_crosscheck_short_spec/1` (`is_short`, `_validate_short`):
   - `nodes` are distinct G.1b TASL-2 nodes; `hosts` is exactly `["TASL-7"]`; `rule` cites R1-G5-AUDIT-TWO-CARDS;
     no `env_python_additions`.
   - `g1b_tasl2_attempts` declares each node's sealed G.1b TASL-2 attempt: attempt number, the sha256s of
     **`job_record.json`, `out.tar` and `SHA256SUMS`**, the spec sha256 its record carries, and the signed G.1b note
     it ran under. That note must be signed, of run `g1b-tasl-20261121-b`, at the pin, with that `spec_sha256`. The
     predecessor spec `060aac91…` is admitted only outside R1-T1-DATA-MANIFEST's corrected nodes.
   - **Consistency:** `SHA256SUMS` must be what the job writes from the other two pins (`out.tar`, then
     `job_record.json`; `g1b_lib._write_sums`). A pin that names the wrong file is refused at `validate`, which is the
     round-1 BLOCKING finding.
   - `verdicts`: each node's own path `docs/r1/reports/…_<node>_<YYYYMMDD>.json`.
   - `caps.max_gpu_hours` in (0, 10] and the projection within it.
2. **`extra_env_additions`**: a host may gain an `extra_env` entry that the G.1b spec declares for the other host,
   with the same value, never one it already has.
3. **`compare --mode short`**:
   - TASL-7 is the cross-check attempt (derived spec sha256 recomputed);
   - TASL-2 is the declared G.1b attempt, checked by run id, spec sha256, attempt number, and the `job_record.json`
     and `SHA256SUMS` pins. With `sha256sum -c`, the `SHA256SUMS` pin also fixes `out.tar`;
   - the mode must match the spec kind both ways;
   - **the PASS/STOP logic is untouched**. A short verdict carries `rule: R1-G5-AUDIT-TWO-CARDS`, and its `on_stop`
     keeps the node's audits on TASL-2 and re-measures nothing.
4. **The note** (`check_xc_note`):
   - the short note has its own name (`g1b_xc_short_t1_tasl_<YYYYMMDD>.md`) and P1 cite;
   - **the author's choices are bound key lines** (`short_decisions`): `xc3_fail` A|B, `xc3_cap` R1-G1B-CAP|G5-CAP,
     `skip_nodes` `none` or some, not all, of the nodes;
   - `draft=True` (CLI `check-xc-note --draft`) checks the unsigned note; only P4 may be PENDING.
5. **The launch** (`launch_xc`):
   - `launch_rows` adds R1-G5-AUDIT-TWO-CARDS;
   - a node in `skip_nodes` is refused;
   - in strict mode, once the author's PLAN row `R1-XC3-FAIL-READING` is on `main`, the note's `xc3_fail` must equal
     the option in the row's sentence "The xc3 note carries xc3_fail: A|B." (`xc3_fail_row_option`). A row present
     twice, or without exactly one such sentence, refuses;
   - **before each GPU job `short_cap_gate` adds the lease hours of the run's earlier GPU attempts (from their job
     records) to that job's projection, and refuses beyond the cap.** An attempt without a job record, or with a
     finish before its start, refuses.
   - `check-note2`, `assemble` and `summarise` refuse a short spec.
6. **`short_verdict_status`** (CLI `verdict-status`, §6):
   - a PASS must be one in every part: `complete` true, every row `identical`, both sides deterministic;
   - it refuses when `origin/main` does not resolve;
   - it refuses when `docs/r1/reports/` on `main` holds any file named `G1B_XC3_SHORT_VERDICT_*` other than the bound
     paths. A capture keeps its copy of a verdict as `captured_verdict_<node>.json`, so G.5's reading by name cannot
     meet a near-miss.
7. **Stable helpers for G.5:** `short_decisions(fields, xc)`, which gives the author's choices, and `check_xc_note`.
   The note path rule is unchanged: `docs/r1/authorizations/g1b_xc_short_t1_tasl_<YYYYMMDD>.md`.

**Unchanged:** the xc2 spec (sha256 `a9e6b463…`, bound by its signed note and by `g5_tasl.py`); its derived specs,
byte-identical (`test_t1_tasl_xc3.py` recomputes all six committed xc2 verdict bindings); `run_xc`, the job, the
seal, `_sealed_rows`, the gated assembly, `g1b_tasl.py` and `t1_tasl_node.sh`.

## 8. What PASS and FAIL do; decision XC3-FAIL (an author PLAN row); houseprice

**PASS:** TASL-7 reproduces the node's G.1b default part bit-identically under the reviewed criterion, and only then
may that node's G.5 audit chunks run on TASL-7. It is not a new noise floor.

**Non-PASS** (a STOP verdict, a refusal, or no verdict yet):
- the node's audit chunks run on TASL-2 only;
- nothing is re-measured: there is no TASL-2 re-measure, and XC-REMEASURE does not apply;
- the node's G.1b record is unchanged.

**XC3-FAIL: does a non-PASS remove the node from G.5?** It fixes how R1-T1-D21-SCOPE ("passed U2, G.1b fixed-seed
determinism and, where run, the cross-host check") is read for C3's node set. That is a PLAN-level reading, as
R1-G1B-JOIN was, so it needs an **author PLAN row before signature**, and the note's `xc3_fail` line must name the
same option.

- **A (recommended): placement only.**
  - The cross-host check in R1-T1-D21-SCOPE is read as the one that gates a node's G.1b (R1-T1-TASL-ENV; xc2 for the
    three TASL-7 nodes).
  - The four nodes' G.1b and G.5 can run entirely on TASL-2.
  - Running this check can only add TASL-7 as an audit host; it cannot remove a node.
- **B: the literal reading.**
  - R1-G5-AUDIT-TWO-CARDS itself calls this check "a cross-host check PASS for that node". It is run under the same
    `g1b_crosscheck.py` and decides by the same criterion.
  - So a node whose short check is run and does not PASS has not passed "where run, the cross-host check": it leaves
    G.5 and PRE-T1's node set.
  - This is the more literal reading of two rows written on the same day. Its cost: a voluntary placement check can
    remove a node that would otherwise enter, and the most exposed node is `mlgym_houseprice`.

Proposed row texts (id `R1-XC3-FAIL-READING`; the author chooses one):
- **A:** "R1-T1-D21-SCOPE's 'where run, the cross-host check' is the R1-T1-TASL-ENV check that gates a node's G.1b
  (xc2 for the three TASL-7 nodes). The short cross-check of R1-G5-AUDIT-TWO-CARDS (xc3) decides only where a node's
  G.5 audits may run: a non-PASS keeps them on TASL-2 and does not remove the node from G.5 or PRE-T1. The xc3 note

**houseprice (`houseprice` line of the note).**
- **Little gain.** `mlgym_houseprice` is CPU-only, so its audit chunks need no GPU: TASL-7's RTX 4090 adds no
  capacity for it. TASL-7 could add only free cores, and under G5-SLOT A that is at most a scheduling gain, likely
  small.
- **Most likely to fail.** Its CPU metrics must be bit-identical across two CPU models.
- **D21.** It is one of the two nodes that qualify under D21 (mean P(wrong) 0.315).
- **Risk by option.** Under A a non-PASS costs it only TASL-7 placement; under B it would leave G.5.
- **Author choice:** `skip_nodes: mlgym_houseprice` removes it from the run. `launch_xc` then refuses its job; it has
  no verdict, its audits stay on TASL-2, and it is unaffected under either option.
- **Recommended:** keep it under A, skip it under B.
