### 4.3 Finding (procedure/code, not the CPU set)

The reviewed §12.3 procedure says "3 sealed attempts of the node's G.1b default part … the loop's attempt numbers
assume no attempt failed". On published `main` `a1597f70` that loop is **not executable**: all three attempts share
one check run id (`CPUSET_RUN` allows one `tasl2-cpuset-<node>-<YYYYMMDD>`, so one run root, one derived-spec
sha256), `run_node_job` creates the next attempt only through `next_attempt`, and `next_attempt` refuses any new
attempt after an attempt whose `stop_class` is `None` (a complete run) — by design for G.1b (one attempt per node
per run). Only an infrastructure STOP may be retried, and a retry chain cannot produce three **clean** attempts
either: once a clean attempt exists in the node directory, no later attempt can start. Meanwhile `cpuset_verdict`
requires at least three attempts with distinct attempt numbers, each carrying the same check run id and spec
sha256, and `check_cpuset_record` requires exactly that PASS record on `main`; duplicate attempt numbers and
per-attempt run ids are refused. So the three sealed attempts 1/2/3 the record needs cannot be produced with
`dry_run_node.py`/`g1b_tasl.py` as published — the gate for houseprice's TASL-2 jobs cannot be cleared. (The
revision-13 tests exercised `cpuset-verdict` with synthetic sealed attempts and `cpuset-spec` on the host side was
never run, so this gap was not visible at the desk.)

This is **not** evidence against CPUs 0-7: attempt 1 is complete, deterministic, bit-identical to the sealed G.1b
TASL-2 reference on all c0–c4 × default/default_repeat rows, and its slowest run (3.877 s) is well inside the
9.486 s budget (and inside the engine's 20.382 s timeout). The STOP is the missing multi-attempt mechanism.

### 4.4 Decision needed

The author (or a follow-up code unit the lead schedules) must either (a) amend the check's mechanism so a G.1b node
may produce N clean repeats for this check (e.g. a check-specific run/attempt path in `g1b_tasl`/`dry_run_node`
that does not go through `next_attempt`'s G.1b one-attempt rule, or an explicit repeat count in the derived spec),
or (b) re-specify the check. Until then the houseprice `G5_TASL2_CPUSET_CHECK_…` PASS record cannot exist and
`check_cpuset_record` refuses every houseprice TASL-2 job — i.e. **houseprice's TASL-2 jobs wait**. No PASS record
was written, and the STOP verdict is kept only in the captures (record-shaped copy named
`G5_TASL2_CPUSET_CHECK_mlgym_houseprice_20261126.STOP.json`), not at the canonical `main` record path, because the
gate requires a PASS. Nothing in
the G.5 spec, code, gate or preregistration was changed here.
