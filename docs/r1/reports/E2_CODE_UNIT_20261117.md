## Before the operator can run B.2

1. **Merge order and the `PLAN.md` freeze** (review round 1, finding 2). The classification guard requires the
   checkout's `docs/r1/PLAN.md` to be byte-identical to `origin/main`'s, and the provenance guard requires the checkout
   to be at the reviewed code commit. So:
   1. this branch already merges `author-decisions-20261117b` @ `45fb94cc` and `ops-e1-replay-amend-20261117` @
      `52992b22` over `main` `26177d82`; its `PLAN.md` is `45fb94cc`'s;
   2. the author **fast-forwards `main`** to the accepted e2 commit (no other `PLAN.md` change in between; if `main`'s
      `PLAN.md` has moved, the branch is merged again and the merge re-reviewed);
   3. the e2 review record is committed on top (it does not touch `PLAN.md`) and `main` fast-forwarded to it; the
      addendum is committed the same way;
   4. **no `PLAN.md` change is pushed to `main` until the audit has started**, as `c3_sweep1_20261027.md` did for the
      sweep-1 launch. Consumption later runs from a current checkout and is not affected.
2. The e2 review file on `main` must contain the exact lines `Code-Commit: <the full 40-character accepted commit>`
   and `Verdict: ACCEPTED`, which `evidence_paper_provenance` requires.
3. The author commits the B.2 addendum: Part 3 of `proposals/AUTH_DRAFT_b2_20261104.md` is filled for that, apart from
   the author's date and words and the accepted commit.
4. The operator runs on deepthought from the batch venv, with `AR_HARNESS_ROOT` set to the batch harness and the batch
   wrappers first on `PATH`, as for e1, with `PYTHONDONTWRITEBYTECODE=1` (the shared venv stays unchanged, as in e1),
   and without the batch `env.sh` `PYTHONPATH` (the provenance guard's import-path allowlist refuses it). The
   co-tenancy floor of ≥ 10 free cores is checked by the operator before launch, as in e1. The code still refuses more
   than 16 workers or a number at or above the CPU count.

## Open points

- **The addendum guard is new.** It enforces R1-B2-GO's stated precondition ("the author commits the B.2 authorization addendum (Part 3 filled)"). If the author prefers not to have it in code, it can be dropped without touching the B1/B4/B6 parts.
- **"Its environment checks" is read as re-running `check_environment` at audit start**, with the replay's recorded values as the reference. The other reading, accepting the report's past checks alone, would leave the audit environment unchecked on the day of the audit.
- **The package identity is now the replay's canonical package list** (sha256 `c09242ac…`), not a freeze bound to the launch. This is the disclosure every record carries (`ENVIRONMENT_BASIS_DISCLOSURE`).
- **The harness's untracked files** (round 1, finding 1). The previous check refused any untracked file and would have
  STOPped on the e1 harness, which has the six OpenML caches and one report file untracked. The new check accepts
  exactly the files the e1 record names, with the caches bound to the e1 post-run tree digests. This narrows a STOP to
  what the reviewed e1 run accepted; the reviewer marked it as needing the author, who may instead prefer another way
  to supply the audited caches.
- **R1-SWEEP2-SETTINGS (3)'s "fixed HTCondor CPU class" is revised by R1-B2-GO for this audit (deepthought CPU).** The
  code now also checks the host name (`deepthought`), as the e1 driver did.
- **Not added** (round 1, finding 8): an end-to-end test of `evidence_classification` at the code commit; the merge
  order above removes the condition, and `_verify_published` keeps its own tests.
- **Outside R1-B2-GO's scope** (reviewer's note): the B.2 worker runs of the OpenML nodes have no network denial; the
  caches are present and bound by digest, but a cache miss would try to download.
