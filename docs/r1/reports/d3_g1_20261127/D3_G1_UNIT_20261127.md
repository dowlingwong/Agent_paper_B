## 1. What this unit implements

worker wrapper that counts every charged run and writes `snapshots/w{5,10,15,20}.json` at the exact `w`, failing

The snapshot payload carries the design's fields (`schema, stage, arm, node, repetition, instance_id, w,
w_actual, incumbent_config, start_config, last_kept_trial_index, worker_runs, llm_calls, ended, config_sha256,

E1 decision, as the design says; verify runs carry the same E1 state with `pending_action=verify`.

## 3. Pre-code blockers found (they stop the full G1 runner, not this snapshot unit)

### 3.1 The pinned harness's verify seeds collide with the D21 noise-floor block

`campaign.py` at the pin (`_run_verify`, line 721) hardcodes

```python
seeds = [1000 + base_budget_index * 10 + index for index in range(verify_runs)]
```

With `verify_runs = 2`, budget indices 1–20 use **1010–1209**. D.3's pre-declaration §4.2 declares the D21 noise-floor
namespaces **1001–1030**, **2001–2030** and **3001–3030** as disjoint from every D.3 seed. Budget indices 1–3
(1010–1031) intersect 1001–1030. The design's P10 verify-seed check therefore fails at this pin for every arm with
verify (A1, A2, A3, A5, A6). G1 cannot change the rule without a new reviewed harness pin (or a decision that the
harness rule is the declared D.3 rule and its intersections are excluded). This is a design/level-2 item: it changes
what evidence is collected. No workaround was coded.

### 3.2 FIXR3 and EGATE are not harness controllers

`r1/c3/d3_replicate.py` (branches `mac-d3-fixr3-20261127`, `mac-d3-egate-20261127`, `mac-d3-ladder-20261127`) gives
`Fixr3Engine` and `EgateEngine` a `step(config_sha256, run, counter)` protocol, not `Controller.decide(view, mask)`.
They cannot be passed to `run_real_campaign(controller=...)`, and their replicate seeds (6501–6679) are outside the
harness's E1/E2 actions. Running them inside the harness needs either a new reviewed harness action that charges
and snapshots each replicate run, or a G1-specific loop outside `run_real_campaign` that still produces the same
ledger/snapshot records. Both are design changes; none was coded. The snapshot wrapper itself would support the
second route (it counts `run_trial_at_seed` calls), but the E1/E2 controller state and the record layout would need a
new contract.

### 3.3 The A1/A2/LADDER constants file does not exist

Pre-declaration §5.0 requires a reviewed constants file and §14 still reads
`constants_file_sha256: <pending>`. `r1/c3/arms_constants.py` produces only A1/A2; the LADDER η search (G2) is
explicitly not in it. The real D.3 adapter cannot be pinned until that file is produced and the revision-4
pre-declaration is signed. A0/A0R need no constants.
