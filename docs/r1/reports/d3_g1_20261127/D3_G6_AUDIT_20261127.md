## What it adds

The G1/G6 design §3 audit, reading the sealed G1 snapshots and no proposal metric:

- **Seeds.** Instance seed `s` (6201–6218) and index `k` (1–10): `a_k = 6700 + 10·(s − 6201) + k`, the declared
  block 6701–6880. A seed outside the instance's range is a STOP.
- **Outcome.** For each audited point `w`, the incumbent and start configurations run on the ten seeds:
  `y_raw(w) = (1/10) Σ_k [m(c, a_k) − m(c0, a_k)]`, `Y(w) = y_raw(w) / σ_node`. `Y_final` is the final incumbent
  at the campaign's actual `w_final`; the w = 5/10/15/20 rows are descriptive. A missing w point is `missing_w`, never
  imputed.
- **w = 0 or incumbent = start.** No audit runs; `Y = 0` by rule, with the rule named in the row.
- **Records.** `<out>/<stage>/<arm>/r<rep>/w<w>/<instance>.json` holds the ten runs, both config shas, per-seed
  deltas, `y_raw`, σ_node, `Y`, cache flags and each run's sha256. `Y_final.jsonl` (one primary row per campaign),
  `Y_w.jsonl` (one row per point, `missing_w` included) and `SHA256SUMS` sit at the audit root. An existing record is
  refused: a rerun takes a new output directory.
- **w20 alias.** When `final.json` has the same config as `w20.json`, the primary row references the w20 record
  (`alias_of_w: 20`); no duplicate audit record is written (design §3.3).
- **Cache.** Key `(node, config_sha256, audit_seed)` for both configurations, shared across arms, repetitions and w
  points, append-only JSONL. A cached run is reused only with its `run_sha256`; a missing provenance is a STOP. Cache
  hits are disclosed per row. `sha256` uses the snapshot module's own `config_sha256`, so the audit key is the
  snapshot's key.
- **Runner.** `harness_runner(tmp)` wraps `r1.c3.audit.run_config` (the B.2 audit mechanism: an isolated node copy,
  the configuration's file texts, the node's own train command at each joint seed). A failed or non-finite seed run is
  a STOP, never retried. The unit is launcher-neutral; tests inject a synthetic runner.

## What it does not do

- No parallel pool: the launcher runs one audit job per `(stage, arm, repetition)` and may parallelise the 18
  instances itself. The append-only cache is safe for that; the two JSONL row files are not locked, so the launcher
  must serialise their appends or merge per-instance rows. This is stated for the G6 launcher unit.
- No `last_improving_run` audit of every kept incumbent (design §7.5 (d)); that needs the campaign's kept-trial list
  and is a later unit.
- No G7 outcome-table builder and no analysis; this unit writes only the audit rows.
- No environment preparation (deepthought Python 3.13 / sklearn 1.8.0 / 16 workers / ≥10 free CPUs): the audit job
  unit owns the host checks.

## Tests

- `r1/tests/test_d3_audit_g6.py`: **7 passed** with a synthetic runner.
  - seed block endpoints 6701/6880 and a refusal outside 6201–6218;
  - snapshot self-hash refusal;
  - a campaign with w5 and final w7: `Y(5) = 0.5/σ`, `Y_final = 0.7/σ`, `missing_w` for 10/15/20;
  - w = 0: `Y = 0` with zero runner calls;
  - cache reuse across two audits with zero runner calls and 10 + 10 hits;
  - final at w20 aliases the w20 record;
  - a failed seed and a missing seed are STOPs.
- Full `r1/tests` with `--continue-on-collection-errors` at the tip and its base is recorded in the review report;
  this unit adds only new files, so no existing test changes.

## Decided alone

- To key the cache by the snapshot module's `config_sha256` (per-file digests), not by a hash of the text map, so a
  cached run and a snapshot name the same configuration.
- To refuse an existing per-instance audit record instead of overwriting; a rerun is a new output directory (the
  same rule as G1).
- To write the w20 primary row as a reference to the w20 record when the configs are equal, as the design's §3.3
  alias rule states.
- To leave the parallel audit job, the host checks and the `last_improving_run` extension to later units; this unit
  is the record/audit core only.
