## 2. Design

**In the table** (`g5_assemble.node_rows`). For every tabled ledger line (decisions `kept`, `discarded`,
`discarded_divergent`, `not_run_inert`, `not_run_duplicate`):
- `proposal_diff`: the line's `proposal.diff`, as a JSON string. The table stays ASCII JSON (`_dumps` escapes
  non-ASCII), sorted keys, one row per line, as before.
- `proposal_diff_sha256`: sha256 of the text's UTF-8 bytes with `surrogateescape`. This is the rule of the harness's
  `diff_support.apply_diff` (`diff_sha256`), so on a ledger the harness wrote, the row's hash equals the run
  provenance's `diff_sha256`.
- `build.json` gains `proposal_diff` (field names, source, hash rule, the deciding row) and `schema` becomes
  `g5_t1_table/2`.
- STOP if a tabled line has no text `proposal.diff`, or the text cannot be encoded.

The full text goes into the table, not the excerpt. So the D7-LEN constants stay in the prompt form
(`serialize_t1`), not in the frozen table bytes.

**In the prompt form** (`serialize_t1`). The table decides the input, never the caller:
- **B**: `build.json` has the `proposal_diff` record (schema `/2`) and every row has a text `proposal_diff` with a
  lower-case hex `proposal_diff_sha256` equal to `diff_sha256(text)`.
- **A**: no record (schema `/1`) and no row has either field.
- Anything else is refused: a `/2` build without the record, a `/1` build with it, an altered record, an unknown
  schema, a row with the field in an A table, a row without it in a B table, or a row whose text and hash disagree.

`table_prompts` passes each row's own text and hash to `t1_prompt`. That function refuses a text whose hash is not
the row's (the binding), then applies the unchanged §3 excerpt rule and length rule. `meta.diff.sha256` is
therefore the row's `proposal_diff_sha256`. History lines still show `(diff)` for earlier steps, never their text. The
`diffs=` argument of `table_prompts` is removed, so no diff text can come from outside the table.

**In the data build** (`sft_data._t1_forms`). For every T1 prompt:
- the prompt shows a diff exactly when its table row carries `proposal_diff`;
- when it shows one, `meta.diff.sha256` must equal the row's `proposal_diff_sha256`.

The manifest's `t1.diff_shown` is `true` under B and `false` under A, as before. `check_t1_manifest` now requires
`diff_shown` to be a boolean. It takes an optional expected value, for the evidence-phase runner or the record check
to compare with the D7-DIFF option the author signed.

**`G5LabelSource`** makes labels, not prompts, so it needs no diff. It reads the same table rows. The new keys are not
label or evaluation keys, so `arms_freeze.check_table_rows` accepts them.

## 3. Which diff text, and why

There are three texts of one proposal:
1. **`proposal.diff` on the ledger line.** This is the `diff` field of the manager's reply as
   `proposal_v2_diff.parse_v2_diff_reply` parsed it (JSON, a leading `<think>` block removed, nothing else).
   `campaign_v2_diff` writes it into the step's entry before `run_with_retries` applies anything (52e3c0b0,
   `campaign_v2_diff.py`).
2. **The run record's `diff.diff_text`.** This is the text passed to `apply_diff` (its provenance). At 52e3c0b0 it is
   the same string as (1).
3. **A recounted copy.** Under R1-G5-DIFF-RECOUNT, the harness may apply the diff after recomputing each hunk header's
   line counts (`git apply --recount` semantics).

**The table carries (1).** It is the proposal as the manager wrote it, which is what A5 should judge: wrong hunk-header
counts and all. It is fixed before execution. Reading it needs no run record. (2) and (3) are the harness's handling
of the proposal and can depend on how it applied. `PROPOSAL_DIFF["source"]` states this in `build.json`. A test gives
executed runs a provenance `diff_text` that differs from `proposal.diff` (a recounted header) and checks that the row
carries `proposal.diff`.

**The recount harness unit: not found.** On `/tmp/pb/harness`, the local branches and the remote
(`git ls-remote gh`, 24 Nov), the G.5 heads are still G5-7 `52e3c0b0` and G5-AR `00829da1`. The two differ only in
`node_lib/ar_isolated.py`. No branch carries a recount change; `diff_support.parse_unified_diff` at both heads refuses
wrong hunk counts (`malformed_hunk`). What this unit assumes of that future unit is item O1 in §11.

## 4. Rows without a diff

- **Not tabled, so no row.** Invalid replies (`invalid_proposal`, including R1-EXAM-B1-TRUNCATION-INVALID),
  refused diffs (`not_run_refused`), final infrastructure failures, and, under the `leave_out` reading, campaign-
  divergent runs. They appear in later prompts' history as `(no tabled proposal); no valid metric`, unchanged.
- **Tabled rows always have a diff.** Every tabled decision comes from a parsed reply, and the harness writes
  `proposal` for every parsed reply (not-run inert and duplicate lines included). So on a B table, `null` is never
  written, and a tabled line without a text `proposal.diff` STOPs the assembly.
- **An empty diff is a diff.** The harness calls an empty diff inert (`empty_diff`). It renders as
  `Diff (unified; lines shown 0 of 0):`.
- **A fallback-A table** has no field in any row. The form shows `Diff: n/a (not carried by the G.5 table)`.

The synthetic ledger fixture of `test_t1_g5_seal.py` had no `proposal` on its not-run lines. That is not how
`campaign_v2_diff` writes them, so the fixture now writes `proposal.diff` there too. No other fixture bytes changed,
and every test of that file passes.

## 5. Leakage analysis

**When the text is written.** The diff is written by the manager before its step runs. `proposal_diff` reads only
`entry["proposal"]["diff"]`: not `final_outcome`, `runs`, `decision`, `best_after` or a later line. A unit test
changes all of these and checks that the row's diff is unchanged.

**What it can contain.** Anything the manager wrote: code, comments, numbers. The manager's prompt
(`manager_v2_diff.build_prompt`, 52e3c0b0) shows:
- the incumbent's editable files;
- the metric name and direction, and the run budget;
- in the `history` mode G.5 runs (R1-G5-MEM-E4), up to 12 earlier steps of the same campaign, each with its summary,
  decision and validation value (`final_outcome.value` at the campaign seed, printed `.6g`).

So a diff can quote absolute campaign values of earlier steps of its own campaign, and the metric name. A test puts
"val 0.45" in a diff, and the prompt shows it verbatim. The form does not filter content, and should not: filtering
code text would change the proposal.

**What it cannot contain** (except by coincidence of digits):
- **Labels and evaluation values.** These are measured at the audit seeds 7001–7010, in audit jobs that run after the
  campaigns. No manager ever sees them, and they do not exist when the diff is written.
- **The sealed test metric.** `manager_view` removes the sealed block from every run record. The history value is the
  validation metric.
- **This step's own outcome**, which comes after the diff.
- **Another instance's information.** Each campaign has its own manager context.

**Leak paths checked in the prompt:**
- A step's prompt shows only its own diff. Earlier steps show `(diff)`. Later steps' diffs, which may quote this
  step's outcome, are never read. A test changes every later row's diff (and the own row's outcome fields), and the
  prompt and `meta` are unchanged. Changing the own diff does change it.
- `train.run.EVAL_COLUMNS` and `sft_data`'s evaluation-name check scan keys, not values. So a diff that mentions, for
  example, `seed=7006` is neither refused nor a leak; it is code text.

**What B adds beyond A** (these belong in FL2, §10):
1. **The code change itself.** A3 does not see it. This is FL2 as stated in the D7 report.
2. **Absolute campaign values and the metric name, when the manager quotes them.** The T1 form otherwise shows `n/a`
   for both (D7-WORDING). These are pre-execution values of earlier steps of the same campaign, not information about
   this proposal's outcome.
3. **Exact recognition of repeats across instances.** Identical diff text in two instances usually means the same
   (incumbent, candidate) group, which carries one shared label. The D7 report gave this as the reason not to show
   code-state hash prefixes (D7-WORDING alternative). Diff text allows it too.
   - PRE-DUP A's primary test population already leaves out test proposals whose (node, incumbent, candidate) occurs
     in train or dev (`sft_data.dup_key`, `test_proposals_seen_in_train_or_val`).
   - The secondary (full) population keeps them. There, part of A5's T1 advantage over A3 could be recall of a
     training label.
   - A3's features carry only within-campaign code-state flags.

**Sealed data and the release path:**
- The diff text comes from the sealed campaign ledgers. The assembly reads those through `g5_seal.SealedTree` under
  its declared purposes (`assembly traindev:` / `assembly test:` / `release integrity …`), and it already parsed whole
  ledger lines (`g5_job.parse_ledger` reads `proposal.diff` for every executed step). No new sealed-tree purpose, kind
  or member is needed, and `SealedTree.ledgers` has no field filter.
- The table opens with R1-T1-LABELS-UNSEAL, as before. It now also carries the diff text of every instance, test
  instances included, as it already carries their features and campaign Δ̂. A diff is not a label.

  --budget-w 20 \
  --out docs/r1/reports/arms_t1feat_20261123/T1_HISTORY_DROP_<YYYYMMDD>.json

**What it reads.**

or a test release.

**What it renders.** Prompts for the P3 train and dev instances only (`--splits` is fixed). The table file also
holds the test instances' campaign rows; they are loaded with the file (the whole-table row-count check counts them),
but no prompt of a test instance is rendered or counted.

**What it writes.** Counts only, written once, schema `trackp_t1_history_drop/1`, ENGINEERING_ONLY. Per node and in
total:
- prompts;
- prompts with history lines dropped, and history lines dropped (with the distribution);
- prompts with diff lines dropped for length, and diff lines dropped;
- prompts whose excerpt rule cut the diff;
- prompts that raise `PromptTooLong`.

It also records the table sha256, the receipt sha256, the tokenizers, the token budget (896), the excerpt constants
and B or A. Exit 1 if any prompt is too long: that is a STOP (D7 report §9).

**Where it is committed.** At the path above, by the cluster agent on its ops branch, then merged with its review.

**It is descriptive.** D7-LEN is signed as built. Changing the constants after reading this report would be a
post-hoc author decision and would have to be disclosed.

> On T1 (G.5) nodes, A5's prompt includes a bounded excerpt of the proposal's own unified diff: the text the
> proposing model wrote, before execution, cut to at most 40 lines, 1,200 characters and 160 characters per line,
