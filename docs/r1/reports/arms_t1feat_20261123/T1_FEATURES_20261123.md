## 2. The T1 features, field by field

**What a G.5 ledger holds.** The harness `trackg/campaign_v2_diff.py` writes ledger schema
`trackg_v2_diff_campaign_ledger/v1`; the G.5 engine writes the G.4 ledgers per instance and mode
(`g5_job.engine_contract`). Its contents:
- Step 0 is the baseline run.
- Steps 1..W (W = 20) are one charged manager call each (G5-W A: W counts manager calls).
- Each step has a `decision` (`kept`, `discarded`, `discarded_divergent`, `not_run_inert`, `not_run_duplicate`,
  `not_run_refused`, `invalid_proposal`, `infrastructure_failure_final`).
- Each step has the proposal's unified diff and the run records (`manager_view`). For a diff, a record's `diff` field
  holds the pre-execution provenance of `diff_support.apply_diff`: the normalised and raw code-state hashes of the
  incumbent and of the candidate.
- Each step has `final_outcome` and `best_after`.

There is no structured key/old/new edit, no model-type field and no dataset descriptor.

**The missing-value convention.**
- A numeric field with no T1 source is NaN. The table writes it as the JSON token `NaN`, as the T0 tables already do
  for `log_ratio` and similar fields.
- A categorical field with no T1 source is −1. LightGBM treats a negative categorical value as missing, and T0 already
  uses −1 in `new_cat_code`.
- Every row carries every v3 key, so `arms.feature_matrix` and `arms_freeze.training_rows` (which refuses a row that
  lacks a key) take T1 rows unchanged.
- A test fits A3 (`LGBMPrior`) on mixed T0 and T1 rows.

**Leakage.**
- The features of step n read the lines of steps < n.
- From step n's own line they read only `proposal_side`: the step number and the candidate's normalised and raw code
  states. The harness computes these from the diff before anything runs, just as T0 computes features from the edit.
- Step n's decision, outcome, `best_after` and every later line are not read.
- `test_t1_features_do_not_read_the_own_or_later_outcomes` changes them for every n and checks that the features of
  steps ≤ n do not change.

**Two counts per node in `build.json`** (`nodes.<node>.features`):
- `raw_state_missing`: featurized steps whose two raw-state fields are NaN because a record lacks raw code states. The
  real runner always writes them; the existing synthetic fixtures do not.
- `flag_mismatch`: tabled rows where the harness's verdict disagrees with the code-state fields, in both directions:
  `noop` ≠ (`active_equals_incumbent` = 1); a `duplicate` with `active_seen_before` ≠ 1; an executed row (`kept`,
  `discarded`, `discarded_divergent`) with `active_equals_incumbent` = 1 or `active_seen_before` = 1. The 3b-2 fixture's
  "duplicate" repeats the incumbent's state (the harness would call that inert), so it counts 12 there; on records shaped
  as the runner writes them it is 0 (`test_assembly_on_realistic_records`).

Both counts should be 0 on the real table (§6). They are counts, not STOPs; whether a non-zero count should STOP the
assembly is decision D9.

**Tier.** PRE-JOINT A reads "node and tier as features". The tier is carried by `node_code`: T1 codes are ≥ 11, and
`g5_features.tier_of_code` gives it. A separate tier column would add a key to every T0 feature dict and break T0 byte
identity, so none is added. This is decided by R1-ARMS-DECISIONS (ARMS-T1FEAT A, "the tier carried by the node code";
§5, D5). Consequence for the leave-one-suite-out folds: a held-out suite's node codes are unseen in its fold's
training, so they carry no tier signal there.

**Wiring.** For each ledger, `g5_assemble.node_rows` calls `g5_features.featurize_ledger` with:
- the node and the suite its node spec names (read at the G.5 commit by `node_metric`);
- the metric sign and σ_node;
- `spec.campaign.W` and `W_semantics`;
- the ledger's mode.

Each tabled row gets its step's features. A tabled row without a candidate code state is a STOP. A featurizer refusal
(an undeclared node, a suite other than the declared one, a non-contiguous ledger) is a STOP. The features come from
the same sealed ledgers in both stages, so the test stage re-derives them with the table. A test changes one feature
value in `proposals.jsonl` and checks that the test stage STOPs, then checks that the unchanged table passes
byte-identically.

## 3. The T1 noise input of the gate run (δ_n)

**What the builder takes.** `gate_input_builder.build(..., noise=...)` takes {node: {"delta_n", "sigma_node"}}. It
refuses a node without a positive δ_n, and a node whose table rows carry another σ_node.

**T0.** The caller takes both values from `dataset.noise_table` on the pinned noise source: σ_node is the median
`sd_joint` over material edits, and δ_n is max(0.002, 0.25 × median `sd_joint` over all edits).

**T1 (`g5_noise.derive(spec, row, run_dirs)`).**
- **σ_node** comes from `g5_assemble.noise_by_node`, the function the table uses: the G.1b summary the train/dev row
  cites, checked against the spec's REL-T1-G1B copy (path and sha256), field `sigma_joint`. So it equals the table rows'
  `sigma_node` by construction. This is the 3b-2 default and is not changed here; which definition T1 uses is an author
  decision (D6-σ, §5).
- **σ_node by T0's definition, reported only.** The record also carries `sigma_node_t0_definition`: `dataset.noise_table`'s
  rule (the median `sd_joint` over material edits, over all edits with an sd if none is material; material as in
  `e1_report`: resolved (|Δ̂_J| > 2 se, or Δ̂_J ≠ 0 when se = 0) and |Δ̂_J| ≥ 0.002), computed from the same bound
  `runs.jsonl`, with `n_material_edits`. `builder_noise` does not use it. A test checks it against `e1_report`'s edits.
  It lets the author see the factor between the two definitions per node before deciding. Switching the table to it
  would need a change in `g5_assemble.noise_by_node` (reading the bound run beside the summary copy) and a new spec
  field; that is not small, so it is not built: if the author chooses T0's definition, that change must land on main
  before the launch.
- **δ_n is D18, unscaled** (PRE-DELTA A): max(0.002, 0.25 × the median over edits of the joint paired sd).
- **The G.1b summary does not carry that median.** Its verdicts have `sigma_joint`, `sigma_train`, `sigma_split`,
  `n_edits` and the per-edit paired-seed counts `paired_joint_n`, and nothing more (3b-2 report §5 item 3).
- **So the median is computed from the G.1b run's `runs.jsonl`**, by `r1.noise.e1_report`'s definitions:
  - per edit k, the sd (numpy, ddof 1) over the joint seeds of m(c_k, s) − m(c0, s);
  - only successful runs with a metric;
  - at least three paired seeds;
  - the median over the edits that have such an sd.
- **It is bound to the copy by sha256.** The copy's `assembly_sha256` must equal the sha256 of the run directory's
  `ASSEMBLY.json`, and that file's `runs_sha256` must equal the sha256 of `runs.jsonl`. The edit count and every edit's
  paired-seed count must equal the summary's `n_edits` and `paired_joint_n`.
- A test checks that the value equals `e1_report.summarise(...)["median_sd_joint"]` exactly; another derives a
  low-noise run and checks that δ_n is D18's floor 0.002.
- **Inputs and the seal guard.** `derive` reads an assembled G.1b run directory (ASSEMBLY.json, runs.jsonl): under D6
  A the reviewed repository copy, under D6 B the G.1b run directory on the T1 host (the sealed G.1b tree, which holds
  noise-floor runs only). Every read goes through `r1.c3.analysis_guard.refuse_sealed`, as `dataset.noise_table` does
  (`r1_sealed` paths, the label seal, are refused).
- **The record** (`g5_t1_noise/1`) holds, per node: σ_node, δ_n, the median, `sigma_node_t0_definition`, the edit
  counts, and the summary path and
  sha256, the assembly sha256 and the runs sha256. It also holds the train/dev row id and its decision sha256.
- `write_record` writes the record once under `docs/r1/reports/` and returns its sha256.
- `builder_noise(record)`, or `builder_noise({}, sha256=..., raw=...)` for the committed bytes, gives the builder's form.
- `merge_noise(t0, t1)` joins the two tiers and refuses a node that is in both.
- A test builds a T0 + T1 gate input with the frozen builder. The inputs are the synthetic T0 world of
  `test_gate_input_builder`, the assembled synthetic G.5 table with its label and evaluation blocks, this noise and the
  mapped suites. The T1 node comes out with suite `MLAgentBench` and the derived δ_n; without the T1 noise the builder
  refuses the node.

**Two things to note.**
- **The two tiers define σ_node differently, as built.** T0's σ_node is a median paired-difference sd. T1's is
  `sigma_joint`, the sd of the baseline's own runs over the joint seeds (the 3b-2 unit's reading of PRE-DELTA, reviewed
  but not signed: PRE-DELTA's "by `dataset.noise_table`'s definitions" attaches to the T0 clause). σ_node scales
  `recorded_gain_z`, the soft-label width and g, all in table bytes; the two definitions differ by a node-dependent
  factor of about √(2(1−ρ)). This is now decision D6-σ (§5).
- **D18's floor of 0.002 is in metric units**, which differ on T1. For example, `mlgym_houseprice` is an RMSE in
  dollars and autoresearch is val_bpb. Ruling (review round 1): the floor is applied as preregistered; the same 0.002
  threshold (`MIN_EFFECT`) already decided which T1 nodes qualified in G.1b, and whether it binds is visible from the
  record's median.

`g5_features.SUITE_NAMES` is the one place: `mlagentbench` → `MLAgentBench`, `mlgym` → `MLGym`, `autoresearch` →
`autoresearch`. The left side is the node specs' `suite:` line; the right side is `gate.SUITES`.

| mlab_imdb | mlagentbench | MLAgentBench | 12 |

**Where the suites come from.** The node-spec suites were read from the harness checkout `mac-trackg-t1-tasl-20261121`
@ `c025f89a` (read-only). The assembly checks them again at the G.5 commit: the suite `node_metric` reads must equal the

**Use.** `build.json` records each node's `suite` and `gate_suite`. `g5_features.tier1_suites({node: suite})` gives
`Tier1.suites` for the arms-frozen record, with the build's nodes or the frozen T1 node set.

**Tests check:**
- the mapping's values equal `gate.SUITES`;
- its keys equal the declared suites;
- an unknown name (including a gate-style name such as `MLAgentBench`) is refused;
- the eight nodes equal the G.5 spec's nodes (in order) and the P3 split file's T1 nodes.

## 5. Author decisions needed

These can go in one PLAN row. **Deadline: before the G.5 launch.** `sweep2/t1_tasl` is frozen on main from the launch
to the T1 test release (3b-2 report §5 item 6; §6 item 4 below), and the features and σ_node are table bytes computed
by that code. So D1–D4, D6-σ, D8 and D9 must be final, and the code that implements them on main, before the launch,
not merely before the assembly. D6 (the copy step) must be settled before the gate run's noise is built, and D7 before
the arms-frozen record. The rulings of the independent review (round 1) are given with each item.

- **D1 — fields without a T1 source:** 18 fields (§2), NaN for numeric fields and −1 for categorical ones. NaN for
  fields that do not apply is already decided by R1-ARMS-DECISIONS (ARMS-T1FEAT A); the −1 convention for the three
  categorical fields is new.
  - Recommended: accept. *Review ruling: accept* (LightGBM treats a negative categorical value as missing; T0 already
    uses −1 in `new_cat_code`).
  - Alternative: give the four dataset descriptors per T1 node from cited sources. This needs a source for each node,
    and `n_classes`/`minority` have no meaning for three of the eight nodes (regression, RL, language model).
- **D2 — the four code-state counterparts** (`cfg_equals_incumbent`, `active_equals_incumbent`, `active_seen_before`,
  `full_seen_before`), with the T0 difference of `active_seen_before` disclosed (§2: divergent states count as seen).
  - Recommended: accept, since they are the harness's own inert and duplicate rules. *Review ruling: accept* (checked
    against `diff_support`, `runner` and `campaign_v2_diff` at `c025f89a`).
  - Alternative: NaN.
- **D3 — `budget_frac_left` = 1 − (n−1)/W in manager calls** (W's unit under G5-W A, signed in R1-G5-DECISIONS-2).
  - Recommended: accept. *Review ruling: accept* (1/W at n = W, like T0).
- **D4 — `invalid_so_far`** counts invalid replies, refused diffs, divergent or timed-out runs and infrastructure-final
  steps; it does not count inert or duplicate diffs.
  - Recommended: accept. *Review ruling: accept.*
- **D5 — tier carried by `node_code`, no separate tier column: decided** by R1-ARMS-DECISIONS (ARMS-T1FEAT A, "the
  tier carried by the node code"). Disclosed consequence: in a leave-one-suite-out fold the held-out node codes are
  unseen, so they carry no tier signal.
- **D6 — the source of T1 δ_n**, decided together with **D6-σ** below. D18 needs `runs.jsonl` of each G.1b run, and
  REL-T1-G1B names only the summary copies. Options:
  - **A (recommended):** an author row amending REL-T1-G1B's copy list, so that a reviewed copy of each G.1b run's
    `ASSEMBLY.json` and `runs.jsonl` is committed beside the summary copy (noise-floor data, ENGINEERING_ONLY: G.1b
    runs.jsonl holds validation metrics only, at G.1b seeds 1001–1030, 2001–2030, 3001–3030 and default runs, disjoint
    from the label and evaluation seeds 7001–7010), and `g5_noise.derive` run on the copies. *Review ruling: A is
    acceptable, with that author row.*
  - **B:** `derive` run on the T1 host against the G.1b run directories, with the record committed and reviewed (the
    reads pass `refuse_sealed`; m6). *Review ruling: workable.*
  - **C:** a δ_n from the summary alone, for example max(0.002, 0.25 × σ_joint). Not D18, not built; it would amend
    PRE-DELTA A. *Review ruling: reject unless the preregistration is amended.*
  - The floor: *ruling: D18's 0.002 floor is applied as preregistered* (§3).
- **D6-σ — the T1 σ_node definition** (review M2). σ_node scales `recorded_gain_z`, the soft-label width and g.
  - **A (as built, 3b-2 default):** σ_node = the G.1b summary's `sigma_joint` (sd of the baseline's own runs over the
    joint seeds). Nothing changes.
  - **B:** T0's definition (`dataset.noise_table`: median `sd_joint` over material edits, over all edits if none is
    material), computed from the same bound `runs.jsonl` (needs D6 A or B). `g5_noise` already reports it per node
    (`sigma_node_t0_definition`) so the two can be compared; making the table use it needs a change to
    `g5_assemble.noise_by_node` and a spec field, reviewed and on main before the launch (not built).
  - No recommendation is made here; the default code is unchanged until the author decides.
- **D7 — A5's input on T1.** A5 (Kev) reads a prompt from `train/serialize.py`, which is built for structured edits and
  T0 `NODE_INFO`. The feature dict reaches A5 only as the sidecar row's `features`. A T1 prompt form for A5 is not part
  of this unit. **Consequence:** `gate_input_builder.TEST_SERIES` requires A3 and A5 predictions for every non-inert
  test proposal of a supplied node, so without a T1 A5 input T1 cannot be in the read at all (PRE-T1 A then freezes an
  empty T1 set). It must be settled before the arms-frozen record. *Review ruling: correct.*
- **D8 — `memory_on` for T1's `history` mode** (review M1). R1-G5-MEM-E4 discloses `history` as different from both T0
  modes.
  - **A (as built):** 1.0, beside T0's `append_only_summary` (a memory is shown).
  - **B:** NaN (not comparable with either T0 mode). A one-line change in `g5_features.featurize_ledger`.
