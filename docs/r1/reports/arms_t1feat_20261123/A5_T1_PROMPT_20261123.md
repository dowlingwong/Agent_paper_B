## 2. What was found first

**How A5 is trained and served.**
- A5 is Kev-0.8B or Kev-4B with LoRA and a belief head, trained by the Track P SFT pipeline (R1-C3-POOL; Qwen
  controls kept as secondary rows).
- Training data comes from `sft_data.build_sft_data`. Its inputs are table rows, a label source and `{proposal_id:
  (DecisionPrompt, features)}` from `sft_data.sweep_prompts`. That function replays T0 ledgers through
  `serialize.serialize_view` (`trackp_prompt/v2`) and binds each prompt to its table row by `features_hash`.
- Phase 1 of P.4 trains on sweep 1 only and is readiness only (R1-TRACKP-P4-DECISIONS). Its runner
  (`r1/c3/train/p4_phase1.py`, arm pin `trackp_p4_arm_pin/v2`) is on branch `mac-trackp-p4-runner-20261122` and is
  **not on main**.
- The evidence phase is not drafted. That phase must train the PRE-POOL variants, score PRE-SELECT A, pin the
  checkpoint (ARMS-A5CKPT A) and predict every gate-source proposal. The readiness report (§4 item 3) says there is no
  predict-only path yet.
- The online sidecar (`serve.py`) answers any row that carries `prompt = {state, proposal}`, so a T1 row needs no
  serving change.
- The arms-frozen record binds each A5-family entry to one run of its P.4 arm pin (`a5_pin_binding`). The pin binds
  the data directory's `sft_data.json`, and that manifest names the prompt version(s).

**Prompt length.** TRACK_P spec §2.2 says "one text template, ≤ 1,024 tokens (Laya's limit), fixed bin names and
order". In code this is `types.MAX_TOKENS = 1024` minus `serialize.FRAMING_RESERVE = 128`, so the neutral rendering
gets 896 tokens under every tokenizer in `serialize.POOL`. When a prompt is too long, the oldest history lines are
dropped first. If it still does not fit with no history, `PromptTooLong` is raised. The pool tokenizers need
`transformers` and the pinned snapshots. Neither is available here, so this unit uses character bounds and fake
tokenizers (§9).

**A5 is not trained on T0 only.** PRE-JOINT A (signed): "each arm is one model over all nodes of both tiers (node and
tier as features) … leave-one-suite-out retrains it without the held-out suite". So:
- The primary A5 learns the T1 form from G.5 train rows.
- A leave-one-suite-out fold A5 (ARMS-A5FOLD A) learns it from T0 and the other two T1 suites, then reads the held-out
  suite.
- The T1 form is shared by all T1 suites. In a fold, the held-out suite's prompts differ from the training suites'
  only in the node name, suite, metric direction, σ_node and history. Nothing in the form is suite-specific.
- Compatibility with T0 still matters, because both tiers train one model. The T1 form therefore keeps T0's sections,
  line order and wording wherever the meaning is the same.

**What the G.5 table and sidecar actually hold** (`g5_assemble.node_rows`, `g5_features`).
- A table row has: `proposal_id`, `instance`, `instance_seed`, `node`, `source`, `memory_mode`, `budget_index`,
  `wave`, `decision`, `noop`, `duplicate`, `inert`, `rule_skip`, `incumbent_hash`, `candidate_hash`, `delta_hat`,
  `sigma_node`, `sigma_cmp`, `audit_group`, and `features` (the 30 v3 fields).
- `build.json` gives each node's `metric_direction`, `suite`, `gate_suite` and `sigma_node`, plus the featurizer
  description.
- **There is no diff text in the table.** The manager's unified diff is the ledger's `proposal.diff`, inside the
  sealed G.5 tree.
- `g5_seal.SealedTree` opens the sealed tree only for the purposes `assembly traindev/test`, `release integrity
  traindev/test` and `server log`. No purpose exists for building A5 prompts, and the runs-tree copies are not to be
  opened after the seal.
- The code-state hashes are in the table (`incumbent_hash`, `candidate_hash`, the normalised states). Their equality
  relations are in the features: `active_equals_incumbent`, `active_seen_before`, and the raw-state pair.
- The sidecar's `features` dict is the table row's `features`.

**Gate coverage.** The frozen builder computes A5 only in the **test** block (`TEST_SERIES`). There,
`_series_rewards` requires an A5 prediction for every row that is not a no-op, including within-campaign duplicates
(the rule layer later skips them). Under the PRE-DUP primary population it does not ask for the test repeats it
leaves out. So the T1 form must render duplicates too. `serialize_t1.missing_for_gate` checks a superset of the
builder's requirement: every non-no-op row of every split. An empty result guarantees coverage for every split and
both populations.

## 3. Design

**Why a sibling module and not `serialize.py`.**
- `serialize_view` replays a T0 ledger through `features.featurize_view` with a `NodeContext`. Both refuse T1 nodes.
- Its node block formats `features.NODE_INFO` numbers, which T1 nodes do not have.
- A T1 proposal exists for A5 only as a G.5 table row. Rendering it is a different input path.
- A sibling leaves `serialize.py` untouched, so every T0 prompt is byte-identical by construction. A golden test
  checks this too.
- The module imports the shared pieces from `serialize.py` rather than copying them: `fmt`, `state_text`,
  `render_text`, `fit_history`, the pool, `FRAMING_RESERVE`, `QUESTION`, `BIN_OPTIONS`.
- It is not under `sweep2/t1_tasl/`. A5's prompt is not part of the table bytes, so it does not belong under the G.5
  freeze.
- It loads `sweep2/t1_tasl/g5_features.py` by path (that module imports only `math`). This way it uses the
  featurizer's own node table, suite mapping and missing-value convention. If the featurizer changed, the form would
  refuse rows rather than drift.

**What it reads** (`ROW_FIELDS`, `HISTORY_FIELDS`).
- From the proposal's own row: `proposal_id`, `node`, `memory_mode`, `budget_index`, `sigma_node`, `features`.
- From rows of the same campaign with a smaller `budget_index`: `proposal_id`, `budget_index`, `decision`,
  `delta_hat`. The table's Δ̂ is campaign data at campaign seeds, the same quantity as T0's `delta_vs_best`.
- From `build.json`: the featurizer description and each node's direction, suite and σ_node.
- It never reads the row's own outcome (`decision`, `delta_hat`, `audit_group`, `wave`, `noop`, `duplicate`) or its
  hashes. It never reads a later row, a label or an evaluation value. A test changes all of these and checks that
  the prompt does not change. Changing an earlier row's Δ̂ does change the prompt.

**The NA rule.**
- A field with no T1 source is shown as `n/a`. This is the token T0's template already prints for a gain it cannot
  compute.
- It is never shown with a T0 value.
- The form requires each field of `g5_features.NO_T1_SOURCE` to be NaN (numeric) or −1 (categorical) and refuses
  anything else. If D1 changed and gave T1 dataset descriptors, the form would stop with an error until updated. It
  would not render them unseen.

**Template** (`trackp_prompt_t1/1`). Same sections and line order as `trackp_prompt/v2`:

| T0 line | T1 line | T1 source |
|---|---|---|
| `Node: <node> (<family> family; R rows, F features, C classes, minority share m)` | `Node: <node> (<gate suite> suite, tier T1, code-level diffs; n/a rows, n/a features, n/a classes, minority share n/a)` | node; `build.json` gate suite; D1 (no descriptors) |
| `Metric: <name> (higher is better); noise level sigma_node = s` | `Metric: n/a (higher|lower is better; z is signed so that positive is better); noise level sigma_node = s` | `build.json` direction; row σ_node (D6-σ decides its definition) |
| `Memory: <mode>` | `Memory: history` | row `memory_mode` (G5-MEM A) |
| `Budget: trial b; worker runs used k of W` | `Budget: trial b; manager calls used b−1 of W` | step; W = G.5 `campaign.W` (G5-W A), checked against every row's `budget_frac_left` (D3) |
| `Incumbent configuration (active keys): k=v, …` | `Incumbent configuration (active keys): n/a (code-level node; no structured configuration)` | none |
| `Incumbent metric: m; recorded gain since the first valid trial: z = +x.xx` | `Incumbent metric: n/a; recorded gain since the first valid trial: z = +x.xx` | `recorded_gain_z` (the baseline is step 0, the first valid trial) |
| `History (oldest first):` + `t<b>: KEY old -> new; kept, z +x.xx` | `t<s>: (diff); kept|discarded, z ±x.xx` / `(diff); no valid metric` (divergent, Δ̂ = −∞) / `(diff); not run (inert)` / `(diff); not run (duplicate)` / `(no tabled proposal); no valid metric` (a step with no table row) | earlier rows' `decision`, `delta_hat / σ_node` |
| `Edit: KEY: old -> new (file F)` | `Edit: n/a (code-level diff; no structured key edit)` then `Diff: n/a (not carried by the G.5 table)` or the excerpt (§4) | D7-DIFF |

The T1 form drops two T0 values without a T1 counterpart: the absolute incumbent metric (the table has none) and the
metric name (neither the table nor `build.json` carries one). It does not show the code-state hashes themselves (D7-WORDING).

**Diff excerpt rule** (`diff_excerpt`). Applied only when diffs are supplied (D7-DIFF B):
1. Line ends are normalised to `\n`. A trailing empty line is dropped.
2. A line longer than 160 characters is cut to exactly 160, ending in ` [cut]`.
3. Whole lines are kept from the top while at most 40 lines and 1,200 characters are used. Characters are Unicode
   code points, and each line's newline counts.
4. The header is `Diff (unified; lines shown k of n):`.
5. No tokenizer is involved. The same text always gives the same excerpt, and the kept part is always a prefix of
   the diff.

**Length rule.** The T0 rule, extended:
1. The neutral rendering must fit 896 tokens under every tokenizer given (default: the pool).
2. If it does not, the oldest history lines are dropped first.
3. If it still does not fit with no history, diff lines are dropped from the bottom: the largest prefix that fits,
   found by bisection.
4. If neither fits, `PromptTooLong` is raised.

`meta` records `history_total`, `history_dropped`, the diff counts and `lines_dropped_for_length`.

## 5. The data path

The current path is `build_sft_data(table_rows, label_source, prompts, out_dir, split_cfg=…)` (training, validation
and selection rows), with `sft_test_eval` for the phase-1 test read. T1 rows enter it as follows:
- **Prompts.** `serialize_t1.table_prompts(rows, build, budget_w=W, tokenizers=…)` returns `{proposal_id: (prompt,
  features)}`, the shape `sweep_prompts` returns. It covers every row of a G.5 table (no-ops included, as T0 training
  includes them), and each prompt is bound to its row by `features_hash`. A joint T0+T1 build passes
  `{**sweep_prompts(...), **table_prompts(...)}`. `table_prompts` must get the **whole** table, because the history
  reads every earlier row. It compares each node's row count with `build.json`'s `counts.rows` and stops on a
  mismatch, so a caller that filtered rows (for example dropped the no-ops) cannot silently change prompts.
- **Labels.** `G5LabelSource(release_root, receipt_sha256=…, table_rows=…, t1=Tier1, table_sha256=…)` reads what A3's
  training reads:
  - `arms_freeze.load_traindev`: the receipted `g5` train/dev partition, receipt pinned, no evaluation field or seed,
    no test label;
  - then `arms_freeze.training_rows`: the gate builder's own validation, the tier's seeds, K = 6 under R1-BX-D3,
    complete and partial labels, the complete population.

  It produces these records:
  - `rule_noop` for no-ops;
  - `audit` with the released `k_label`, so a partial label keeps its k;
  - nothing for a `divergent` label (it has no soft label, as in A3's training), counted in the provenance;
  - nothing for duplicates.

  `soft_target` then gives exactly A3's soft label. A test checks this row by row.
- **Joint build** (PRE-JOINT A). `CompositeLabelSource([T0 source(s), G5LabelSource])` joins the label sources and
  refuses a proposal id labelled twice.
- **Form check.** A T1 row needs the T1 form, and a T0 row refuses it. The diff is shown on every T1 prompt or on
  none.
- **Manifest.** Only when T1 rows are present does `sft_data.json` get a `t1` record: prompt version, T1 featurizer,
  `diff_shown`, and T1 row counts per split. `label_seeds` then becomes per tier, `{"T0": [7001…7005] or null,
  "T1": <the G.5 source's label seeds>}`, because T1 under R1-BX-D3 uses 7001–7003. `load_sft_data` and
  `sft_test_eval.read_data_dir` check both. A T0-only build keeps the flat list.
- **No `sweep2/` for T0.** `sft_data` recognises T1 rows by `p3_split.T1_NODES` and the version string in `types.py`.
  It imports `serialize_t1`, which loads `sweep2/t1_tasl/g5_features.py`, only when a T1 row is present. A test runs
  the T0 golden build with `serialize_t1` made unimportable.
- **T0 unchanged.** A T0-only build is byte-identical to the base commit: the T0 prompts, `rows.jsonl`, `splits.json`
  and `sft_data.json`, checked against hashes computed on `14f19a09` before any change. In a joint build the T0 rows
  carry exactly their `trackp_prompt/v2` prompts.
- **Inference.** The model wrappers take any `DecisionPrompt`, and `sft.predict_logits` is tier-agnostic. For the gate
  read, the evidence phase must predict on `table_prompts` for G.5 ids and on `sweep_prompts` for sweep-2 ids, then
  apply the temperature. `missing_for_gate(rows, predictions)` must be empty; that is stricter than the builder
  needs (§2).
- **Not changed.** The `trackp.py sft-data` CLI is single-table and ENGINEERING_ONLY, and the P.4 runner is not on
  main. The multi-table evidence-phase runner (PRE-POOL variants over sweep 1, sweep 2 and G.5) is the evidence-phase
  unit's job. That unit should call `table_prompts`, `G5LabelSource` and `CompositeLabelSource`.

## 6. F1: a blocking finding outside D7 (fixed in a separate commit, for review)

- `g5_assemble.group_label` writes `divergent_seeds` on **every** G.5 `audit` and `divergent` label row. These are the
  label seeds where the candidate or the parent diverged.
- `arms_freeze.check_label_rows` refused any label row with that key, because it is in `EVAL_KEYS`.
- So `training_rows` refused every audited G.5 label: neither A3 nor A5 could train on T1. No existing test fed
  G.5-shaped label rows to `arms_freeze`. This unit's data-path test found it ("a label row carries an evaluation
  field" on the synthetic world's first audited row).
- **Fix** (commit `39856cb0`): the key is admitted only on an `audit` or `divergent` row, and only as a list of
  integers within the row's own `seeds`. Those seeds are still checked against the evaluation seeds. Still refused:
  any other evaluation field, the key on a no-op row, an evaluation seed, a seed outside the row's own, a non-list.
  Tests are in `test_c3_arms_freeze.py::test_training_rows_refusals`.
- **Author decision F1.** Two ways to make the reader and the label rows agree:
  - **A: accept this fix** (commit `39856cb0`). It narrows one input check in `arms_freeze` and changes no table or
    label byte and no preregistered rule. It leaves the G.5 label rows as they are.
  - **B: remove or rename the key in `g5_assemble`.** `divergent_seeds` on a label row is undocumented: the G.5 code part 3b-2 report
    (`G5_CODE_3B2_20261123.md`, line 121) declares it only for the evaluation block, and T0 B.2 label rows do not
    carry it. B would therefore bring G.5's label rows in line with the documented shape and with T0, and
    `arms_freeze` would stay as it was. `g5_assemble` is not frozen yet (the G.5 launch has not happened), and it is
    the other author's unit. B changes the G.5 label-block bytes and needs a review before the launch. If the
    information is wanted, it could move to a documented field name or to the completion counts.
  - Recommended: A, because it is reviewed here with tests, keeps the label-seed divergence visible to readers, and
    does not wait on the G.5 change set. B is equally sound, and preferable if the G.5 author wants the label-row
    shape to match T0's exactly. Either way it must be on main before A3 or A5 trains with T1 rows.

## 7. Author decisions and flags

Nothing in the frozen preregistration changes. No PRE-* row names A5's input: the preregistration was searched for
prompt, serialisation and input, and A5's input is not mentioned. A5's input is declared in Track P documents instead:
TRACK_P spec §2.2 ("one text template"), `trackp_prompt/v2` (author, 14 Nov, W2-1), and the P.4 phase-1 note's
`table_pin` (`c3_features/v3, trackp_prompt/v2`). The items below may change declared scientific content. They can go
in one PLAN row and are due before the arms-frozen record. D7-DIFF B is due before the G.5 launch.

**The task's "diff provenance".** In the repository's vocabulary, diff provenance is the pre-execution code-state
hash record that `diff_support.apply_diff` writes into each run record (`g5_features.py` lines 20–21 and 37,
`g5_assemble.py` line 422). Option A below meets that through the code-state flags derived from those hashes
(normalised and raw state equal to the incumbent, seen before in the campaign). Option B, the manager's diff text,
goes beyond the task's wording.

- **D7-FORM: adopt `trackp_prompt_t1/1` as A5's T1 input.** This is a second template version beside
  `trackp_prompt/v2`. It amends spec §2.2's "one text template" for T1 rows.
  - A (recommended): as built. Same sections and lines as T0, `n/a` where T1 has no source. Disclose it in the paper.
  - B: render T1 through T0's template code with the features as text. Not built. It would show T1 rows with T0
    field meanings, which is what D7 asks to avoid.
  - C: no T1 A5 input. Then `TEST_SERIES` cannot be met for any T1 node, PRE-T1 A freezes an empty T1 set, and
    leave-one-suite-out is lost.
- **D7-DIFF: the diff text in A5's T1 input.**
  - A: no diff text (as built, the default). The proposal is described by the code-state flags only. Buildable now,
    changes no frozen code. FL1 applies and must be disclosed.
  - B: a bounded diff excerpt (§3 rule). The diff would have to reach the table: a reviewed change to
    `g5_assemble.node_rows` adding the step's own `proposal.diff` to each row (pre-execution content, leak-free, like
    the features' `proposal_side`). The caller would then pass `diffs={pid: row[<field>]}`. The change is in
    `sweep2/t1_tasl`, so it must land on main before the G.5 launch, with D6-σ and D9. A new sealed-tree purpose for
    A5 is the other route, and it is worse: it reads the seal for an arm. B makes the T1 input the same in kind as T0
    (the proposal's content). It also gives A5 information A3 cannot use (FL2), and long diffs push history out of
    the 896-token budget. Each supplied diff's sha256 is recorded in the prompt's `meta.diff`, so `rows.jsonl` (bound
    by `rows_sha256`) binds the exact text.
  - Recommendation: B, **if** it can land in the same pre-launch G.5 change set as D6-σ and D9. Otherwise A, with FL1
    disclosed. This is a scientific choice for the author.
