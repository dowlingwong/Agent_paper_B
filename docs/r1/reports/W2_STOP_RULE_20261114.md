# W2 difference on sweep 1 — what the campaign's stop rule counts (14 November 2026)

**AI-assisted (Claude, Mac-local agent). Code reading only: no data, table, ledger or label was read or changed.** Trigger: the read-only W2 identity check on sweep 1 (cluster agent, deepthought) found **14 of 288** `root_trials.jsonl` ledgers where the worker-run count differs from `b − 1`. Every differing row is a precheck rejection. Question: does the campaign stop after a number of **worker runs** or a number of **trials** (precheck rejections included)? Code at harness `a3fedbb` (the sweep-1 and B1 pin); paper references at `mac-int-20261107`.

## Finding: the stop is set by worker runs; the trial count is only a backstop at 2W

**1. How sweep 1 calls the campaign.**
- `r1/scripts/c3_label_sweep.py` sets `runs: 20` (l. 123) and STOPs on any other value outside DRYRUN (l. 213–214). It passes `--runs` to `r1.headroom.e1b_collect` (l. 1462).
- `e1b_collect._run_root` calls `run_real_campaign(…, budget=runs * 2, …, compute_budget=ComputeBudget(max_worker_runs=runs), verify_runs=VERIFY_R, …)` (`r1/headroom/e1b_collect.py` l. 260–265). `--runs` is documented as "compute budget W (worker runs) per campaign" (l. 411).
- So each sweep-1 campaign has a **trial budget of 40** and a **worker-run cap of 20**.

**2. Two counters, and the loop stops on either** (`src/autoresearch/control_plane/campaign.py` at `a3fedbb`):
- `budget_state = BudgetState(total_trials=budget, consumed_trials=len(existing_records))` (l. 1258): the trial counter.
- `while not budget_state.exhausted and not compute_budget.exhausted:` (l. 1303).
- `ComputeBudget.exhausted` is true once `worker_runs >= max_worker_runs` (`control_plane/budget.py` l. 77–80).

**3. What each kind of row consumes:**

| Row | Trial (`budget_state.consume_one()`, l. 1970, once per loop pass) | Worker run (`compute_budget.consume_worker_run`) |
|---|---|---|
| executed proposal | 1 | 1, after `worker.run_trial` (l. 1683) |
| precheck rejection (`_precondition_failure_result`, l. 1516–1531; record `worker_mode` `<mode>_precheck`, `worker_skipped: True`, `_structured_failure_result` l. 1006–1031) | 1 | **0**: the branch at l. 1520 sets `worker_result = precondition_result` and never calls `consume_worker_run` |
| a precheck failing again after an E1b revision (l. 1663–1665) | 1 | 0 |
| control-plane skip (E1 skip or D25 inactive-key skip, `_skipped_record`, l. 600 and l. 1713) | 1 | 0 |
| KG verify re-runs | (inside the trial) | 1 each (l. 731, l. 743) |

**4. The view the controller sees** (`_budget_view`, l. 238–243) carries both `trials_remaining` and `worker_runs_remaining`. The `ComputeBudget` docstring (budget.py l. 44–56) states that the campaign counts every worker run, including verify re-runs.

**Consequence.** A sweep-1 campaign ends when it has made 20 worker runs, unless it reaches 40 trials first. A precheck rejection uses a trial slot and an LLM call, not a worker run, so it **extends** the campaign by one trial. On the 14 ledgers, the trial index `b` therefore overstates the worker runs used, and the old feature `budget_frac_left = 1 − (b − 1)/W` understates how much of the campaign's real budget was left. The W2 definition `1 − worker_runs_used/W` (`r1/c3/features.py`, `row_worker_runs`: `_precheck` rows count 0, l. 319–332 on `mac-w2-budget-20261109`) is the one that matches the stop rule.

**One edge to note.** A campaign with more than 20 non-run trials would stop at the 40-trial cap with fewer than 20 worker runs. Its worker-run count still drives the feature correctly. The read-only check's per-ledger row counts would show whether any of the 14 reached 40 rows. Nothing here suggests one did, but the code reading alone cannot rule it out.

## Recommendation (the stop rule counts worker runs)

Adopt the W2 definition, as it was implemented and accepted on 9 Nov (R1-SEQ-BUDGET-FIELDS):
1. **Rebuild every feature table and prompt set under `c3_features/v3`.** That covers sweep 1 and, later, sweep 2, so that offline training data and online decision records use one definition. Execute-all campaigns (274 of 288 sweep-1 ledgers by the check) are bit-identical under v3. Only the 14 ledgers with precheck rejections change, and only for the views after the first rejection.
2. **Disclose it** in the data section: the remaining-budget feature counts worker runs, as the campaign's stop rule does; 14 of 288 sweep-1 campaigns contain precheck rejections, which use a trial but not a worker run; tables were rebuilt under v3 before any analysis that uses them.
3. **No change to any ledger or label**: the ledgers are the record. The rebuild is derived data, done in a separately reviewed unit that needs label-free access only for these fields (the check script reads only `budget_index`, `decision`, `worker_mode` and `extra.control`).
4. **Prompt version.** Under the 13 Nov answer to Q7, `PROMPT_VERSION` stays `trackp_prompt/v1` until the first Track P data with skips is built. Rebuilding sweep-1 prompts for these 14 ledgers is exactly that event. So the rebuild should bump it (e.g. to `trackp_prompt/v2`) together with v3, or the author confirms that v1 stays for precheck-only differences.

The alternative options for a trial-counting rule (show both remaining quantities in the feature, or count a precheck as 1) do not apply, because the code counts worker runs.
