# M3 listener HUP and withdrawn notifications — source blocker

AI-assisted (Codex), 7 November 2026. **STOP: source inspection, not a kernel or site qualification and not a replay authorization.** This is a bounded answer to whether a minimal supervisor change can safely treat listener hangup as normal completion. No process was started on a host and no model, loader or numerical replay was run. Public upstream source was read; the target site's kernel version and patches remain unknown.

## Verified upstream behavior

- In the public upstream [Linux v6.6 `seccomp_notify_poll`](https://raw.githubusercontent.com/torvalds/linux/v6.6/kernel/seccomp.c), lines 1685–1710, the listener reports `EPOLLIN` for an initial queued notification, and it reports `EPOLLHUP` when the filter's users count is zero. The [v6.12 implementation](https://raw.githubusercontent.com/torvalds/linux/v6.12/kernel/seccomp.c), lines 1703–1728, has the same relevant conditions. **Inference:** normal final filter-user exit can yield HUP, so the candidate supervisor's unconditional HUP STOP may refuse normal completion. This does not establish behavior on the target host.
- In [Linux v6.6 `seccomp_do_user_notification`](https://raw.githubusercontent.com/torvalds/linux/v6.6/kernel/seccomp.c), lines 1032–1112, an initial notification is queued, the notifying task can wait interruptibly, and the interruption path removes its notification from the list before returning. The [upstream seccomp user-notification documentation](https://github.com/torvalds/linux/blob/master/Documentation/userspace-api/seccomp_filter.rst) likewise describes notification withdrawal when a notifying process is interrupted before receipt. **Inference:** a prohibited attempt may be interrupted and removed before the listener consumes it; subsequently seeing HUP without readable notification cannot by itself prove that no such attempt occurred, including when application code handles the interruption and exits normally.
- The same v6.6 source, lines 1026–1029 and 1062–1079, makes the killable-wait condition depend on the notification already being in the sent state; it is not a demonstrated remedy for interruption before receipt.

## Consequence for the existing supervisor

The reviewed proposal requires every prohibited attempt to be durably recorded and to cause STOP, even if the workload swallows errors (`docs/r1/proposals/C3_REPLAY_OFFLINE_BOUNDARY_DESIGN_20261104.md`, “Concrete candidate launcher and trust boundary” and “Required tests and qualification before reconsidering STOP”). In `r1/c3/offline_supervisor.py`, the current candidate records readable notifications and conservatively STOPs on listener error/HUP; it can still return `COMPLETE_UNQUALIFIED` on child readiness without an independently qualified proof of zero lost attempts. That status is explicitly not a production pass.

Simply accepting a bare HUP after a zero exit and empty cgroup would not establish the reviewed invariant. Nor does a single synthetic HUP observation prove the target kernel cannot withdraw an unreceived notification. No defensible one-line normal-HUP success change is made. Keep the existing OpenML replay STOP, preserve the candidate's unqualified scope, and do not infer authorization from this report.

## Exact unblock

1. **Implementation and independent review:** establish an observation mechanism or protocol that can detect prohibited attempts even when user notifications are interrupted or removed before receipt, and distinguish monitor loss from normal final closure. Bound its trust assumptions and crash cleanup; include counterexamples for swallowed interrupted notifications. Owner: Mac implementer and fresh independent reviewer. Effort: more than a local HUP branch fix; approximately 1–several engineering days, uncertain until an acceptable mechanism is selected.
2. **Ordered site qualification:** after supervisor code is accepted under the author's 7 November instruction, an authorized operator verifies the target kernel/patch behavior and the complete reviewed negative and positive synthetic cases, including descendants and monitor failure. Owner: operator and independent reviewer. Effort: site-dependent; no access was attempted in this unit.
3. **All 16 cases:** prove configuration-dependent offline executability and exact preflight-to-execution bindings without numerical replay, or seek an author decision on a protocol alternative if that proof cannot be established. Owner: Mac implementer/reviewer, then author only if a protocol change is necessary. Effort: multiple engineering days and separately authorized host qualification.

The site listener probe accepted on `mac-m3-listener-20261107` is useful for observing a fixed pair of lifecycle scenarios, but it explicitly does not receive notifications after exit, exercise the above interrupted-and-swallowed case, or qualify the full supervisor. A host result from that probe must not be reported as closing these three items.
