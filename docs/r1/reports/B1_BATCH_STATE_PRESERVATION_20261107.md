# B1 batch-state preservation candidate — 7 November 2026

AI-assisted (Codex). **Candidate, not accepted and not B1 launch authority.** The current production B1 `ExamRunner.save` calls `campaign.write_json`, which opens a fixed `batch_state.json.tmp` with truncation and atomically replaces `batch_state.json`; an earlier current inode can thus lose its last pathname, and a pre-existing temporary file can be truncated. This was not observed in a real B1 run, which has not started.

The proposed B1-only publisher retains the existing canonical `batch_state.json` path and JSON format used by current monitoring, resume checks and `b1_batch.verify_batch`. It encodes and fsyncs a new uniquely and exclusively created file under the batch's `_to_delete/`. The first publish uses Linux `renameat2(RENAME_NOREPLACE)` to install it without clobbering an existing state. Each subsequent publish checks the expected old device/inode, then uses `RENAME_EXCHANGE` to atomically swap the completed candidate with the current path: the prior state is retained under that unique `_to_delete/` name. Both directory FDs are fsynced; no hard links, unlink, truncation of an existing file, or cleanup is used by the new publisher. Errors leave any unpublished candidate in place. Ordinary Stage A, B2 and DRYRUN continue using the prior writer; the Stage A lease guardian completion contract is not changed.

The candidate tracks the last published identity on the runner and verifies an existing production B1 state's identity before and after its resume read. It refuses non-regular or unowned state, unsafe batch/retirement directory modes, a different device, a changed expected inode, candidate collisions and unsupported rename operations. `RENAME_EXCHANGE` and `RENAME_NOREPLACE` have the specified atomic semantics in the [Linux rename(2) manual](https://man7.org/linux/man-pages/man2/renameat2.2.html); filesystem support is not established here. The first-publication and exchange syscalls are distinct; neither permits ordinary overwrite. This is a cooperative point-in-time check, not exclusion of same-UID or repository writers: a pathname can still be raced between its identity check and the syscall, and the runner's own batch-ownership proof is separately unresolved.

Crash or fsync failure after an exchange can leave a new current inode and the old version retired, while the runner's in-memory expected identity is stale: a later save then STOPs rather than overwriting; a durable STOP status is not assured by this unit.

This does **not** fix B1's other repeated `write_json` destinations such as `audit_cache.json`, fixed-harness pending-guard unlink/truncation, runner-lock removal, inside-work-tree ownership, inherited worker/server/lease identity, asynchronous STOP coordination, the full-suite no-deletion problem, or Stage A kill/resume coverage. It also does not prove that no state publication can occur after an asynchronous STOP. An implementation of STOP coordination needs its own independent review and must preserve the pre-existing STOP scene while publishing status.

Every state update retains an entire previous JSON file; size and inode use grow throughout the batch. Before launch, the implementer and reviewer must estimate worst-case disk and file-count use and define monitoring; the host operator must test supported NOREPLACE/EXCHANGE semantics on a newly created agent-owned same-filesystem directory without deleting any file, verify permission/ownership and check failures (effort site-dependent, expected short engineering check if ownership and tooling are available). The implementer and independent reviewer must also resolve STOP/publication ordering and the other deletion paths (effort unknown). The final integrated checkout and code pin need fresh independent review. An unsupported filesystem or unresolved ownership is STOP; this candidate does not infer permission to access TASL-7 while another operator may hold it.
