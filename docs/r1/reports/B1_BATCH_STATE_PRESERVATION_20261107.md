# B1 batch-state preservation candidate — 7 November 2026

AI-assisted (Codex). **Candidate, not accepted and not B1 launch authority.** The current production B1 `ExamRunner.save` calls `campaign.write_json`, which opens a fixed `batch_state.json.tmp` with truncation and atomically replaces `batch_state.json`; an earlier current inode can thus lose its last pathname, and a pre-existing temporary file can be truncated. This was not observed in a real B1 run, which has not started.

The proposed B1-only publisher retains the existing canonical `batch_state.json` path and JSON format used by current monitoring, resume checks and `b1_batch.verify_batch`. It encodes and fsyncs a new uniquely and exclusively created file under the batch's `_to_delete/`. The first publish uses Linux `renameat2(RENAME_NOREPLACE)` to install it without clobbering an existing state. Each subsequent publish checks the expected old device/inode, then uses `RENAME_EXCHANGE` to atomically swap the completed candidate with the current path: the prior state is retained under that unique `_to_delete/` name. Both directory FDs are fsynced; no hard links, unlink, truncation of an existing file, or cleanup is used by the new publisher. Errors leave any unpublished candidate in place. Ordinary Stage A, B2 and DRYRUN continue using the prior writer; the Stage A lease guardian completion contract is not changed.

The candidate tracks the last published identity on the runner and verifies an existing production B1 state's identity before and after its resume read. It refuses non-regular or unowned state, unsafe batch/retirement directory modes, a different device, a changed expected inode, candidate collisions, group/other-writable state and unsupported rename operations. `RENAME_EXCHANGE` and `RENAME_NOREPLACE` have the specified atomic semantics in the [Linux rename(2) manual](https://man7.org/linux/man-pages/man2/renameat2.2.html); filesystem support is not established here. The first-publication and exchange syscalls are distinct; neither permits ordinary overwrite. This is a cooperative point-in-time check, not exclusion of same-UID or repository writers: a pathname can still be raced between its identity check and the syscall, and the runner's own batch-ownership proof is separately unresolved.

## R1 finding and R2 candidate: no false success from a failed runner

Independent review `B1_BATCH_STATE_PRESERVATION_REVIEW_20261107.md` did not accept the first candidate. If state exchange succeeds and a following fsync or identity check fails, `save()` retains its old in-memory inode. A later STOP save can fail the expected-inode check, leaving a canonical `RUNNING` or `COMPLETE` state. On the original runner path that could allow a false resume or complete-batch verification. The previous text's observation that durable STOP was not assured did not fully describe those consequences.

R2 imposes a **production-B1-only fail-closed recovery restriction**: the batch must be a new direct child of the configured work directory, created exclusively, and an exclusive, fsynced `B1_ACTIVE.json` records the runner PID and authorized checkout HEAD before state/work begins. Any existing B1 batch, including a crash with no recorded STOP, is refused for automatic resume; the author may later inspect it. DRYRUN retains its existing behavior. This is a conservative engineering restriction, not an author decision or permission to retry a STOP. Missing or partial sentinel creation leaves the new directory in place and stops before lease/work.

The cooperative supervisor must actually wait for its runner. `publish_after_wait(child, batch, head)` writes an exclusive `B1_EXIT_RECEIPT.json` only after `child.wait()` returns integer zero, the active sentinel names that child and HEAD, the state is COMPLETE/EVIDENCE, no `STOP.json` path exists, and `b1_finalization.verify_finalization` accepts the separate guardian `FINALIZED.json`. The receipt hashes the exact sentinel, state and FINALIZED bytes. `b1_batch.verify_batch` now refuses an absent, malformed, stale or mismatched waited-exit receipt and repeats the state digest check. Thus a simulated post-exchange failure followed by a STOP-save failure and nonzero waited exit cannot be accepted merely because the canonical state still says COMPLETE; no successful receipt is published on a failed/signalled runner. STOP-record absence itself is not treated as proof of success.

The containment branch is responsible for the **single** canonical supervisor/launcher, holding the GPU lease and producing its independently checked FINALIZED record. Its unaccepted candidate must be integrated with these functions and reviewed as one. This branch deliberately has **no second launcher**; an earlier passive-launcher draft was retired locally under `_to_delete/b1_state_drafts/`, not deleted. The containment `b1_finalization` module is absent here, so receipt publication and verification fail closed until that reviewed component exists. There is no real process, guardian or kernel proof in this unit. Another same-UID writer can fabricate the process receipt under the existing cooperative trust model; direct unreviewed callers, parent/lease/OFD and server ownership, guardian-only STOP or notification failure, and concurrent mutation remain separate unresolved launch blockers. If an exit-receipt write is fully visible but its subsequent fsync fails, the wrapper may report failure while valid bytes are visible; the receipt still describes a zero waited runner and validated finalization, but filesystem durability and operator handling of that ambiguity are **not** established. This must be addressed in the integrated review and site qualification; do not claim complete fault-tolerant finalization from these mocks.

## R2 finding and R3 publication candidate: ACTIVE as the final barrier

Independent review `B1_BATCH_STATE_PRESERVATION_R2_REVIEW_20261107.md` rejected R2: a full receipt could be visible when `fsync` failed, and a later verifier could accept it if a STOP marker also failed. This was a source-supported possibility, not an observed B1 event. R3 retains ACTIVE until the receipt file and batch directory have both been fsynced; any error before that point leaves ACTIVE in place, and the verifier first refuses any existing ACTIVE path, including a dangling link. After validating the receipt inputs and requiring catchable signals blocked, the final publication operation is `renameat2(RENAME_NOREPLACE)` of ACTIVE to the deterministic `_to_delete/B1_ACTIVE.completed.json` path. There is no mandatory post-rename directory fsync or other post-commit STOP-gated I/O; directory FD close errors are ignored. The caller must keep catchable signals blocked until it exits. The verifier accepts only when ACTIVE is absent, the retired sentinel is present with matching receipt/FINALIZED/state hashes, and no STOP record exists. A crash that loses the final rename should leave ACTIVE and therefore refuse, under the qualified filesystem semantics below.

The code reads `/proc/self/mountinfo`, selects an unambiguous most-specific mount, checks its device numbers against the batch directory, and refuses filesystem types other than `ext4` or `xfs`. This conservative code check is **not** proof that the backing device is physically local, that the target filesystem supports both requested rename flags, or that I/O error semantics are reliable. Linux `rename(2)` documents atomic exchange and ext4/xfs NOREPLACE support; the [kernel ext4 documentation](https://docs.kernel.org/6.9/filesystems/ext4/globals.html) describes journaled metadata. A site operator must inspect the actual batch filesystem and backing device, verify both flags and permission/ownership in a fresh agent-owned directory while preserving all probe files, and an independent reviewer must assess the resulting evidence. Do not infer the `work_dir` filesystem from a separate `df` of `$HOME`.

**Material unresolved fault-model STOP:** the Linux manual explicitly warns that NFS may report rename failure after it already occurred; the type check rejects NFS, but ordinary successful tests or an ext4/xfs label cannot establish behavior for every possible EIO, Python callback already pending before the signal mask, privileged concurrent mount change, or guardian/supervisor death around the final rename. If the rename took effect but the publisher reported a STOP and STOP recording also failed, the static on-disk bytes could be indistinguishable from success. An independently reviewed external/live witness or a specifically justified restricted fault model and site qualification is still needed before this can be called a complete fail-closed publication protocol. The B1 implementer and reviewer own that integration; the site operator verifies local capabilities, and effort is unknown. The candidate does not claim this risk has been closed.

The unmodified single supervisor from the separate containment work must integrate these functions, hold the GPU lease through the publication point, and be reviewed along with guardian FINALIZED semantics and its own death/STOP paths. The retained pure mocked `unittest_r10.txt` failed with two fixture errors: its fake `os.stat` did not accept pathlib's call after the filesystem guard was added; no real filesystem syscall, deletion or STOP scene was involved. Corrected retained `unittest_r11.txt` reports 34 passing tests, SHA-256 `4a15ba566a1b414f6f30c2a0403e02bc63439a9c5b693b316f6a9999377b0c29`.
