**The job** (`run_job`; CLI `g5_tasl.py run --job … [--server-record …]`; wrapper `t1_tasl_node.sh g5 …`). One call
runs one campaign wave, or one audit chunk, of one node.

Order (§3; one worker slot):
1. campaigns-wave1 (instances 1–4).
2. audits-wave1, one chunk per call. The plan is made once.
3. The wave-1 checks (`wave_checks`), run automatically after the last chunk.
4. campaigns-wave2, refused unless the wave-1 checks have no STOP.
5. audits-wave2, then the checks again.

A job refuses if it is out of order, if the node has a STOP on record (node or timing class, in any job record or in
`wave_checks.json`), or if the consumed worker GPU-hours already exceed the cap (STOP 9).

Before an attempt directory is created, these run under the lease; a refusal goes to `_refusals/`:
- the engines are present at the family's G.5 commit;
- host, affinity, GPU and foreign processes, ptrace and the delegated scope;
- the family checkout (`harness_g5` or `harness_g5_ar`);
- the environment (for autoresearch under G5-ARPEND A, from the completion record the switch passes in);
- for campaigns, the server record and `/props` before the wave;
- for audits under G5-TASL-GPUH B, the proposer must be stopped;
- for audits, the K lock and the next chunk.

After the engine:
- for campaigns, `/props` again (a change is STOP 12, re-run as a new attempt);
- the diagnostics;
- `out.tar` is written, then `out/` is removed;
- `job_record.json`, `diagnostics.json` and `SHA256SUMS` are written.

Attempts follow G.1b's rule: only an infrastructure STOP may be followed by a new attempt.

**Audit planning.**
- The planner reads the completed campaign attempt's `out.tar`, verified against SHA256SUMS. Each opening writes a
  line to the access log.
- For each ledger it re-materialises:
  - the baseline state;
  - for every audited step, the parent (the last kept state) and the candidate (the kept chain plus the candidate
    diff).
  The ledger's incumbent hash must equal the chain's last state, or the job STOPs (integrity).
- Which steps are audited:
  - G5-AUDIT A: kept, discarded and divergent, timed-out ones included.
  - G5-AUDIT B: `ok` steps only.
- Groups:
  - A group is keyed by (incumbent hash, candidate hash) and audited once across instances.
  - A wave-2 group already audited in wave 1 is carried, not re-run.
- Units:
  - Under `reuse_parent_runs`, a unit is a code state, run once per audit seed within the node. Wave-1 units serve
    wave 2.
  - Otherwise each group has its own candidate and parent units.
- Chunks fit the walltime: runs × census run time × 1.25 × 1.5 within 24 h − 1 h.
- The plan shows which diffs the campaign kept, so it is stored in `plan.tar`. Only `plan_index.json` (counts and
  hashes) is in clear.

**E5** (per group, label seeds only):
- divergent: more than half of the label seeds diverged on the proposal;
- partial: some label seed diverged on the proposal or its parent;
- complete: otherwise.
Evaluation seeds never enter. A divergent baseline at a label seed is counted (it feeds STOP 8).

**STOP counters** (`evaluate_stops`, after each wave's audits, from diagnostics only):

| STOP | What triggers it here | Class |
|---|---|---|
| 1 | E5-divergent label share above the G5-DIV threshold (`g5_tasl.divergence_threshold`), from 40 audited groups; below 40, an early warning only | node |
| 2 | A `stop_unisolated` ledger line, or an audit row that is not effective with empty waivers and exceptions | node |
| 3 | Ran-of-valid below the liveness floor after wave 1 | node |
| 4 | Invalid share (invalid proposals plus replies at the cap that were not invalid) above 0.2 of the wave's manager calls; a prompt overflow | node |
| 4 | A reply at the cap that the engine did not mark invalid (engine contract) | infrastructure |
| 6 | `stop_integrity` or `stop_transport` | infrastructure |
| 6 | `baseline_failed` | node |
| 7 | Final infrastructure failures above 5 % of the node's proposals | node |
| 7 | Infrastructure rows in an audit chunk | infrastructure; the chunk becomes a new attempt |
| 8 | A baseline timeout in a campaign, or the baseline code state diverging at an audit label seed | timing |
| 9 | Consumed worker GPU-hours above the cap; a job past its deadline; audited groups after wave 1 × 3 outside the band (doubled under MEM B) | node |
| 10 | A seed outside the plan's K blocks, in a chunk file or a row; instance seeds outside 5101–5112 | node |
| 11 | An `out.tar` opening that is not by job code for a declared purpose (`check_access_log`) | — |

A further early warning: an in-campaign single-seed divergent share above 0.2.

STOPs 5, 13, 14 and 15 are the switch's (3a). STOP 12 is the per-wave `/props` check above.

## 2. The harness engines (a harness code unit, needed before any G.5 job can run)

The current harness cannot run G.5:
- `pilot_g4.py` accepts only the four pilot nodes, seeds 4001–4099 and `ENGINEERING_ONLY`.
- `noise_floor.py` runs only declared edits and reserves the audit seeds 7001–7010.

The G.5 harness commits (G5-7 and G5-AR, byte-identical G.5 code, checked by `g5_pin_check`) must add two engines.
`g5_job` defines their contracts, and `check_engines` refuses a G.5 commit that lacks them:
- **Campaigns:** `python -m autoresearch.trackg.pilot_g4 run-g5 --campaign <trackg_g5_campaign/v1> --harness-root
  <h> --out <dir> --gpu-uuid <uuid>`.
  - It writes `instance_<k>_<mode>/campaign_ledger.jsonl` (the G.4 ledger schema) and `campaign_record.json`.
  - `pilot_g4.py` is a v2-diff engine file outside P5's measurement path, so G.5 may change it.
  - A reply at the completion cap must be an `invalid_proposal`.
- **Audits:** `python -m autoresearch.trackg.audit_g5 run --chunk <trackg_g5_audit_chunk/v1> --harness-root <h>
  --out <dir> --gpu-uuid <uuid>`.
  - Units are given as the ordered diffs applied to the baseline, with the expected `code_state_sha256`.
  - Runs use training seed = split seed = s, with the `"vary"` split.
  - Every run goes through `WorkingCopyRunner` and `noise_floor.check_effective`.
  - It writes `rows.jsonl` (`trackg_g5_audit_row/v1`: unit, seed, executed, code_state_sha256, outcome, value,
    isolation) and `chunk_record.json`.
  - `audit_g5.py` is one of 3a's two declared trackg additions (P5).

`diagnostics_g5.py`, the draft's other proposed harness file, is not needed: the diagnostics are computed on the
paper side.

## 5. Open questions and inconsistencies found

1. **The harness engines (§2).** They do not exist, and they need their own reviewed harness unit. Until then
   `check_engines` STOPs every job.
2. **"12 baselines" in the projection.** The baseline is one code state per node, and every instance audits it at
   the same seeds, so under parent reuse it is audited once. The §8 projection is therefore conservative.
3. **STOP 4's "refusals".** These are read as model refusals, which the engine records as parse failures. Diff
   refusals (`not_run_refused`) count toward D4 liveness, not the invalid share. A reply at the cap that parsed and
   ran is a contract breach (infrastructure STOP).
4. **Audit-once across waves.** A wave-2 group audited in wave 1 is carried, not re-run; the draft states audit-once
   across instances. STOP 1's denominator and the band use groups (unique audited proposals); members are reported
   beside them.
5. **Baseline divergence in an audit.** A baseline code state diverging at an audit label seed is STOP 8 (timing).
   The draft states this only for campaigns.
6. **When K is fixed.** The table-wide K lock is written at the first audit job's preflight, slightly earlier than
   "the first audit chunk".
7. **GPU-hour accounting.**
   - The meter counts the whole job wall time, setup included.
   - The proposer card's hours (G5-TASL-GPUH; reported beside the cap) are not metered here. The campaign job
     records give the wave spans, and 3b-2 can sum them.
8. **What 3b-2 must seal.**
   - The audit plan (`plan.tar`) and its index.
   - The access log.
   - The node wrapper logs. They carry only scope lines and STOP messages, but they sit outside `out.tar`.
   - TASL-7's `llama-server.log`, which carries prompts.
9. **G5-MEM B.** It runs twin campaigns per instance (`instance_<k>_<mode>`). For a cross-instance group, twins of
   the same instance count as one instance.
