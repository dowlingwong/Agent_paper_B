# B1 audit STOP channel candidate — revision 2, 7 November 2026

AI-assisted (Codex). **Candidate awaiting fresh independent review, not B1 acceptance.** This supersedes the R1 wiring only where stated. R1 independent review `5fb7a58e` found that one failed writer could leave peers running while the executor waited, and that a read-before-exit race could miss the normal completion byte.

The runner now creates two separate nonblocking anonymous pipes and passes both writer descriptors in worker contract v3; both distinct descriptor numbers and distinct FIFO inode identities are required before task execution. On an audit failure or invalid writer check the wrapper attempts `S` on both. If one writer is broken, short or full but the other write succeeds, the runner's single monitor can receive STOP via the other pipe and invoke the owned guardian freeze before pool shutdown completes. Normal collector completion sends `D` to both, and a failed completion send also attempts STOP on both. The runner requires both normal completion markers, child exit 0 and the owned worker cgroup empty; marker evidence alone never accepts a batch. The monitor now drains both channels after observing collector exit, so an earlier empty nonblocking read cannot hide a byte already queued before exit, and any drained STOP still invokes freeze.

`python3 -B` ran 17 mock/in-memory cases: seven notifier, five executor/monitor, five selected existing contract/spawn cases. These include invalid primary writer while a simulated sibling remains active, primary write failure with backup success, both mocked writes failing with original audit failure as cause, an empty read followed by D then observed exit, STOP pending during exit drain, the actual AST-extracted collector executor branch notifying before fake pool shutdown, and actual monitor source calling a fake guardian. `git diff --check` passed. The tests did not make real pipes, fork, processes, model/GPU, cgroups, host accesses or filesystem artifact operations. Full suite and real Linux behavior remain untested.

**Limits and STOP:** two pipes reduce but do not eliminate common failure modes. Both writers can fail, the runner monitor can die, inherited writers can defer EOF, a successful write can be unread when the runner dies, and kernel or guardian freeze can fail. In particular, if both notifications fail and other tasks retain writer ends, the collector can still wait for executor shutdown and the runner may not promptly detect the failure; this revision does not claim to solve that case. This requires an independently reviewed out-of-band fallback or a justified supported channel fault model, plus a real two-worker Linux test; if both failures cannot be ruled out, preserve and do not launch. A node or peer may write during notification-to-confirmed-freeze delay. The channels share one monitor and kernel, and same-UID cooperation and pipe identity semantics are assumptions, not protection from an adversary. The producer and reviewer must assess fixed artifact metadata and audit success semantics separately. The author-pinned harness remains unchanged, and no actual formal B1 STOP occurred.
