## Findings and scope

- The script checks host and UID, reads the lock directory and complete STATUS files with before/after hashes, checks GPU UUID, utilization and compute-app census, verifies the lock path and existing inode without following symlinks, checks both evidence markers, and requests a nonblocking exclusive `flock` before starting its owned child (script lines 5–36, 53–102, 132–160). These are cooperative, point-in-time observations; STATUS prose and other operators' ownership are not parsed or settled by the script. An operator must inspect all applicable STATUS and complete the nonpreemption census before invoking it. The author's later instruction to proceed despite the observed processes does not authorize preempting a job, modifying another operator's work, or bypassing other STOPs.
- `pass_fds` gives the child the acquired lock descriptor and the two intended pipe ends; close-on-exec removes the other ends. The child writes readiness, then waits for EOF or a 15-second timeout and exits without unlocking (lines 113–127, 165–182). The parent closes its copy of the child-only pipe ends. On normal parent death, kernel closure of the sole remaining writer delivers EOF; the child's eventual exit closes its inherited lock descriptor. This assumes normal kernel operation and scheduling; it is not a guarantee under uninterruptible kernel sleep or broken process/descriptor semantics.
- The Linux x86-64 syscall uses number 312, `KCMP_FILE` type 0, parent PID and child PID, and the inherited FD number in each process (lines 195–206). Only return value zero passes; a matching inode alone does not. Both PID descriptors are checked against their `/proc/self/fdinfo` Pid values and polled for liveness, with process start ticks checked again after comparison (lines 169–170, 183–194, 207–210). This covers the selected parent/child comparison only, not a production guardian, worker or server chain.
- Cleanup closes the pipe writer, waits for the child and unlocks only after a confirmed wait (lines 211–233). On spawn/wait failure, no explicit unlock is issued until child exit is confirmed; closing the parent's own FD does not release a lock still held by the inherited open file description. No signal, kill, file creation, truncation, overwrite, or deletion appears in the host script. `Popen.wait()` is intentionally unbounded: the child timeout is cooperative, not an end-to-end execution deadline. If a wait is interrupted or fails, or output stalls, lock release is NOT CHECKABLE; preserve the scene and output, do not retry, preempt, signal, delete or proceed to B1. An operator must investigate the exact owned process and lease before any further action.
- `hostname`, `id`, `ls`, `sha256sum`, `cut`, `cat`, `nvidia-smi`, `awk` and `python3` are site dependencies; absence, failed commands, unexpected output or unavailability of `pidfd_open`/`kcmp` stops the check. The printed `command -v python3` and `sys.executable` identify the interpreter actually used, and the child uses the same interpreter.
