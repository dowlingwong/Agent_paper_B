# M3 cache-copy planning component — 5 November 2026

AI-assisted (Codex); candidate awaiting independent review. `copy_cache` creates a previously nonexistent destination under an existing directory, traverses source and destination paths with directory descriptors and no-follow flags, refuses symlinks, special files and multiply-linked source files, creates new regular-file inodes, and checks the bytes copied to each destination file against the bytes read from its source. It detects ordinary changes while an individual file or directory is being read. It leaves a partially created destination in place on every STOP. It does not enable or invoke replay.

Six synthetic filesystem tests pass: byte equality/fresh inode, existing destination refusal, symlink, hardlink, FIFO, path overlap and source mutation while reading. No host, model, numerical work, GPU or network is used. Output is labelled `IDENTITY_ONLY` and `NOT_ESTABLISHED`.

The helper is for a cooperative filesystem and cannot establish an atomic point-in-time snapshot: a file can change after its individual check, privileged or concurrent writers can race destination validation, and bind mounts or other aliases may evade lexical overlap checks. The source-root pathname can be rebound after its descriptor is opened. Some filesystems may not reliably implement metadata, exclusive creation or directory fsync as assumed. Source/copy hashes alone do not prove offline completeness, historic provenance, isolation, or that any case can execute; a later accepted workflow must address concurrent writers, source-root and copy identity, cache integrity immediately before/after use, runtime closure and the independently reviewed Linux boundary. Existing M3 and replay STOPs remain. Owner: implementer and independent reviewer; then separately authorized site operator. Estimate: one or more engineering days plus review and host-dependent qualification.
