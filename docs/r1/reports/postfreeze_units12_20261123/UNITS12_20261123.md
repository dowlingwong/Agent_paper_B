## 1. Unit 1 — the A1/A2 constants fitter (`r1/c3/arms_constants.py`, new)

**What it does.** Per node, it fits:

- **A2**: `gate_input_builder.fit_a2` itself. The unit builds the item list `fit_a2` takes and calls it.
- **A1**: `arms.ConstantPrior` on the row list `fit_a2` builds from the same items (`fit_rows` copies `fit_a2`'s
  comprehension; a test checks that `RulesPrior` on that list reproduces `fit_a2` bitwise).

The rows are those of A§3.1:

- the dev instances' label block of the gate sources: sweep 2 for all eight T0 nodes, G.5 for the frozen T1 nodes;
- both T0 memory modes (T1: its declared modes); a dev row of another mode is refused, as the builder refuses it;
- built by `arms_freeze.training_rows`, the builder's construction (tested against `_prepare`). A no-op gets the inert
  soft label. An `audit` label gets `soft_label(Δ_label, None, σ_node, "pooled_node", k_label)`. Within-campaign
  duplicates and divergent labels have no soft label;
- weights 1;
- sorted by `proposal_id` across sources, as `_prepare` sorts them. `arms._wmean` sums in row order, so this order is
  what makes A2 bitwise equal to `fit_a2`.

There is no pooled fallback. A required node without a labelled non-inert dev proposal is refused, and so are rows of
any node outside the required set.

**What it reads and refuses.**

- Labels come only from the receipted train/dev partition, through `arms_freeze.load_traindev`
  (`release.traindev_labels` with the receipt sha256 pinned). It refuses a receipt that is not train/dev or that counts
  evaluation rows, label rows with evaluation fields or seeds, and label rows of test instances.
- The table comes through `arms_freeze.load_table_rows` (`dataset.load_table` → `analysis_guard.guard_table`). It
  refuses table rows that carry label or evaluation values. The table must be the one the receipt released and, for
  sweep 2, the addendum's pin `379b17ca…97d9` (D.3 §5.0).
- It refuses sweep 1 (PRE-A2 C: gate sources only), raw, test and evaluation paths by name, and a dirty checkout.
- **Table and label rows are filtered to P3 dev instances first.** Train and test rows enter no computation; a test
  shows that a malformed train row changes nothing.

**What it writes.** One JSON file, written once (`r1_c3_rule_arm_constants/v1`):

- per node: the A1 and A2 12-bin vectors (JSON floats round-trip exactly), σ_node, the dev instance ids and row counts;
- the fitter's path, sha256 and code commit;
- per source: the receipt, train/dev partition, label block and table sha256s;
- the split file's and the builder's sha256s, and the T1 setting.

CLI: `python -m r1.c3.arms_constants fit --release-root sweep2=… --receipt sweep2=… --table sweep2=… [g5 + --t1] --out …`.

**Against the amendment.** It follows A§3.1 (the fit set), A§3.2 (all eight T0 nodes and the frozen T1 nodes) and A§8
row 1 (inputs; dev filter first; one JSON with vectors, σ, receipt, table and split sha256s). A§8 row 1's tests are
all present: bitwise equality with `fit_a2`; the `proposal_id` order (input order changes no bit); per-node vectors
unchanged when other nodes are added; no pooled fallback; refusal of test and evaluation rows.

**Against the D.3 draft (one unit serves both, for A1 and A2).** For the seven D.3 nodes the vectors are the ones the
D.3 draft's G2 would produce (§5.0):

- the same reader (`release.traindev_labels`, sweep 2, receipt pinned);
- the same table pin and receipt binding, opened through `guard_table`;
- the same dev-first filter and population (full dev population of sweep 2, both modes, labelled rows; sweep 1 out);
- and A2 equal to `fit_a2` per node, as §5.0's required test states.

Each node's vectors use only that node's rows. A test shows that the seven nodes' vectors are bitwise the same whether
the fit covers those seven alone (G2's population) or eight T0 nodes plus T1 nodes. Three points for the D.3 text
(none is a conflict with the amendment):

1. **LADDER η (§5.6) is not in this unit.** §5.0 asks G2 for one file with A1, A2 and LADDER. Either G2 = this unit
   plus a LADDER extension, or the D.3 constants file is this unit's file plus a separate LADDER file. The record
   checker accepts a D.3 file of this schema family that carries extra per-node fields; a test does this with a
   `ladder_eta` field.
2. §5.0 says "s = σ̂_node/√5". `fit_a2`, and therefore this unit, uses the label row's `k_label`, so a partial label
   (k < 5) gets σ/√k. This only matters if sweep 2's dev label block has partial labels. §5.0's own equality test with
   `fit_a2` settles it in favour of `k_label`.
3. As the amendment's follow-up says, the D.3 text should state that this unit (eight T0 nodes plus T1) is its G2 for
   A1 and A2.

## 2. Unit 2 — `r1/c3/arms_freeze.py` (changed)

**New record fields** (A§9), both added to `REQUIRED_TOP`:

- `amendments`: a list with exactly one entry `{path, sha256, plan_row}`. The path is under
  `docs/r1/authorizations/`. `plan_row` must be `R1-POSTFREEZE-READS` and an author row of PLAN §10, looked up in the
  same `author_rows` set the `REQUIRED_DECISIONS` rows use.
- `rule_arms`:
  - `A0`: `{rule: "r1.c3.offline_eval.rho", constants: null}`;
  - `A1` and `A2`: `vectors` for exactly the eight T0 nodes and the frozen T1 nodes, plus `fitter`
    `{path: r1/c3/arms_constants.py, sha256, code_commit}`, `constants` `{path, sha256}` (relative to the root the
    checker is given), `receipts` (sweep 2, and G.5 when T1 is frozen) and `fit_population`. A1 also carries
    `offline: "no rule layer; no verify offline"`. A1 and A2 must have identical provenance (one fit);
  - `d3_constants`: null, or `{path, sha256}`.

**Checks in `check_record`.**

- *Always:* the structure above. Each vector must be 12 finite non-negative bins summing to 1 within 1e-9, and A2's
  bin 0 must be exactly 0. The fitter's commit joins `code_commits`, so `verify_git` checks it.
- *With `constants_root`:* the constants file is re-hashed and parsed. The record's vectors must equal it bitwise. Its
  fitter, T1 setting, receipts, partitions and tables must equal the record's, i.e. `label_tables`. Each frozen T1
  node's dev instances must equal those in `t1.instances`. If pinned, the D.3 constants file is re-hashed and the
  seven D.3 nodes' A1 and A2 vectors must equal the record's bitwise.
- *With `verify_committed`:* the amendment is re-hashed as a committed file of the checkout (`release._committed`).
  Its final block (`release._final_block`) must read:
  - `frozen: true`;
  - `plan_row: R1-POSTFREEZE-READS`;
  - `amends: <preregistration path> sha256 <its sha256>`;
  - `constants_fitter_sha256` equal to the record's fitter sha256;
  - `arms_freeze_sha256` equal to the checkout's `arms_freeze.py`;
  - a `signed_by` and a `frozen_utc` that are not pending.

  This is A§12 item 22 (units 1 and 2 bound in A§13 before the record) made checkable.
- **Unchanged:** every existing check, and `arms == required_arms`. A0 and A1 are not arms of the record, and adding
  them is refused as "undeclared" (tested).

**Writer.** `postfreeze_fields` builds the two fields from the constants file's bytes; the vectors are copied
unchanged. CLI `postfreeze-fields` reads the file under `--constants-root` and the committed amendment, and runs the
same amendment checks before writing. The CLI `check` passes `constants_root` (`--constants-root`, default
`--artefact-root`) and `verify_committed` (off only with `--no-git`). `render` passes `verify_committed=True` and an
optional `--constants-root`.

**Why the file checks are opt-in in the Python API.** This follows review m3: the existing tests must pass with their
fixture extended by the new fields only. Two existing tests call `check_record` with `artefact_root` or
`release_roots`, and change `label_tables` receipts inside the test body. If the constants file were checked under
`artefact_root`, or the record's receipts were cross-checked against `label_tables` without a constants file, those
tests would fail. So these checks have their own keywords (`constants_root`, `verify_committed`). The CLI turns both
on, and the runbook uses the CLI.

**m3 compliance.** No existing test body changed. The `_record()` fixture gained `amendments` and `rule_arms`. The
module's `PLAN` fixture text gained one row, `R1-POSTFREEZE-READS`, which the new field cites. This second fixture
change is unavoidable, because every existing call passes that `PLAN`; the reviewer should confirm that it fits m3's
"fixture extended by the new fields only". The parametrized missing-item test now also covers the two new fields
(43 → 45 cases).

**The amendment's own sha256 cannot be a constant in the code.** A§13 pins this file's sha256, so pinning the
amendment's sha256 here would be circular. The record carries it instead, and `verify_committed` re-hashes the
committed file.

1. **Timing.** These units are reviewed (tier E, re-checked until "accepted") and merged into `main`. Their merged
   sha256s are entered in A§13. The amendment is signed (`frozen: true`) and committed on `main`. Only then does
   Run II's step 4b run. **The arms-frozen record must not be committed before all of that.** A§12 item 22 gives
   units 1 and 2 no fallback: without them, A1's rows and the record-based input of (d) are lost. The record checker
   enforces this, since a draft or unbound amendment is refused. The cut-off is 20 Dec 2026 (R1-ARMS-FREEZE-CUTOFF).
2. **Do not change either unit on `main` after A§13 is filled.** The checker requires A§13's `arms_freeze_sha256` to
   equal the checkout's `arms_freeze.py`, and `constants_fitter_sha256` to equal the record's fitter. A later edit to
   either file before the record (for example an A5 schema change) makes `check` refuse, and would need a new binding.
3. **A§13's key names are load-bearing:** `frozen`, `plan_row`, `amends`, `constants_fitter_sha256`,
   `arms_freeze_sha256`, `signed_by`, `frozen_utc`, in the draft's `key: value` form, in the final fenced block that
   ends the file. The draft's block parses with `release._final_block` today; it is refused as `frozen: false`.
4. **D.3.** If the D.3 pre-declaration is signed before the record and pins a constants file, pass it as
   `--d3-constants`. Otherwise `d3_constants` is null, and the D.3 pre-declaration must later pin vectors equal to the
   record's for its seven nodes. Simplest: D.3 pins this unit's file. LADDER η still needs its own fitter (§1, point 1).
5. **T1.** If a T1 set is frozen, step 4b needs the G.5 receipt and table and the same `t1.json` Run I used. A G.5
   table without the full feature set is refused by `training_rows`, as for A3.
