## 1. Unit 1 — the A1/A2 constants fitter (`r1/c3/arms_constants.py`, new)

**What it fits.** Per node:

- **A2** is `gate_input_builder.fit_a2` itself. The unit builds the item list `fit_a2` takes and calls it.
- **A1** is `arms.ConstantPrior` on the row list `fit_a2` builds from the same items. `fit_rows` copies `fit_a2`'s
  comprehension; a test checks that `RulesPrior` on that list reproduces `fit_a2` bitwise.

The rows are those of A§3.1:

- the dev label block of the gate sources (sweep 2 for all eight T0 nodes; G.5 for the frozen T1 nodes);
- both T0 memory modes (T1: its declared modes); a dev row of another mode is refused;
- built by `arms_freeze.training_rows`, i.e. the builder's construction;
- weights 1, sorted by `proposal_id` across sources as `_prepare` sorts them. This order is what makes A2 bitwise equal
  to `fit_a2`.

There is no pooled fallback.

**What it reads and refuses.** It reads only:

- the receipted train/dev partition, through `arms_freeze.load_traindev` (receipt pinned);
- the released table, through `arms_freeze.load_table_rows` → `dataset.load_table` → `guard_table`. The table must be
  the one the receipt released and, for sweep 2, `379b17ca…97d9` (D.3 §5.0).

Rows are filtered to P3 dev instances first. It refuses:

- sweep 1;
- test labels, evaluation fields and evaluation seeds;
- table rows carrying label values;
- raw, test or evaluation paths;
- a required node without a labelled non-inert dev proposal, and stray nodes;
- a checkout whose `gate_input_builder.py` is not the one the preregistration binds (new, N2);
- a dirty checkout.

**What it writes.** One JSON file, written once (`r1_c3_rule_arm_constants/v1`):

- per node: the A1 and A2 vectors, tier, source, σ_node, dev instances and row counts;
- the fitter's path, sha256 and code commit; the fit population, rules and row order;
- the split file's and the builder's pins;
- per source: the receipt, partition, label block and table sha256s, and `configs_sha256` (N8: recorded only, null if
  absent);
- the T1 setting, the T0 and D.3 node lists;
- **`toolchain`** (new, M3): Python, NumPy and SciPy versions and the interpreter path, written from the running
  interpreter. The vectors' bits depend on NumPy and on SciPy's `norm.cdf` (`labels.soft_label`), so unit 3's bitwise
  re-check after step 6 must run with the recorded versions.

`parse` validates every one of these fields (N2).

**Against the amendment.** It follows A§3.1, A§3.2 and A§8 row 1 (inputs; dev filter first; vectors, σ, receipt,
table and split sha256s). The tests A§8 row 1 asks for are present:

- bitwise equality with `fit_a2`;
- `proposal_id` order (shuffled input changes no bit);
- vectors unchanged when other nodes are added;
- no pooled fallback;
- refusal of test and evaluation rows.

**Against the D.3 draft: one unit serves both, for A1 and A2 only.** For the seven D.3 nodes the vectors are what G2
would produce (§5.0): the same reader, the same table pin and receipt binding through `guard_table`, the same dev-first
filter and population, and A2 equal to `fit_a2` per node. A test shows that the seven nodes' vectors are bitwise the
same whether the fit covers them alone or eight T0 nodes plus T1 nodes. Points for the D.3 text (none is a conflict
with the amendment):

1. LADDER η (§5.6) is not in this unit.
2. §5.0's "s = σ̂_node/√5" differs from `fit_a2`'s per-label `k_label`. §5.0's own equality test settles it for
   `k_label`.
3. The D.3 text should name this unit (eight T0 nodes plus T1) as G2 for A1 and A2.
4. (N8) The record checker accepts a D.3 constants file only of the schema family `r1_c3_rule_arm_constants/*`, with
   per-node `A1` and `A2` under `nodes`. The D.3 text must require that format, or pin unit 1's file itself.
5. (N8) D.3 §5.0 pins `configs.json` (`de6d63b5…`). Unit 1 now records each table's `configs.json` sha256, but neither
   reads nor checks it; the D.3 text can compare the recorded value or drop that pin for G2's A1/A2 part.

## 6. What the arms-freeze operator and the author must know

1. **Order (M4).**
   1. The ARMS rows and any `arms_freeze.py` change they need are merged.
   2. These units are re-checked and merged.
   3. Their merged sha256s are entered in A§13, and the amendment is set `frozen: true` with `signed_utc` and
      `frozen_utc` and committed on `main`.
   4. Only then does Run II clone `$C2` and run step 4b.

   The arms-frozen record is never committed before all of that. The cut-off is 20 Dec 2026 (R1-ARMS-FREEZE-CUTOFF).
2. **Once unit 2 is on `main`, no arms-frozen record can be written without the frozen, signed amendment (M6).**
   `check_record` requires `amendments` and `rule_arms`, and `render` and `check` refuse unless the committed amendment
   is frozen and signed and binds both units. A§12 item 22 (if units 1–2 are not bound, A1's rows and (d) are lost)
   and item 23 (if the amendment is not signed, (a)–(d) are not computed) both describe a record that goes ahead
   without the amendment. With unit 2 merged, that path needs an **author row and a reviewed change to unit 2**. If
   the amendment might miss the cut-off, the author must decide early.
3. **After the record pins the amendment, the amendment file never changes.** Every re-run of `check` re-hashes it.
   Units 3–5, if not in A§13 by then, are bound only by CONFIRM-type rows (A§12 item 22's fallback). After A§13 is
   filled, neither unit may change on `main` either; the record would be refused.
4. **A§13's keys are load-bearing:** `amends`, `plan_row`, `frozen`, `constants_fitter_sha256`, `arms_freeze_sha256`,
   `signed_by`, `signed_utc` and `frozen_utc`, lowercase, `key: value`, in the final fenced block that ends the file.
   At the freeze:
   - `frozen: true`, with nothing after it;
   - bare 64-hex sha256s;
   - `signed_utc` and `frozen_utc` as `YYYY-MM-DDTHH:MM[:SS]Z`, with `signed_utc` no later than `frozen_utc`.

   The sign-ready file's placeholders (`frozen: false (…)`, `<pending…>`, `<filled when published on main>`) are all
   refused, which is correct before the freeze.

   (review, procedural note). By the amendment's own rule it must reach `main` before signing. This is not a matter
