## Blocking findings

1. **COMPLETE can be observed without successful finalization, and STOP evidence can fail to record.** `r1/scripts/exam_runner.py:552-559` writes `batch_state.json` with `status=COMPLETE` before `finish_b1_lease()` has completed. The verifier rejects a STOP only if `STOP.json` exists (`r1/exam/b1_batch.py:17-19,71-76`); it does not require independent evidence of completed guardian/lease finalization. In the interval before finish, a concurrent verifier can see a complete batch without a STOP. If finish then raises and the exclusive STOP creation also fails (for example ENOSPC or permission failure), `report_b1_stop_and_save` catches that ordinary error (`r1/exam/runtime.py:30-51`), leaving the prior COMPLETE state and no STOP path. The retained test `test_failed_guardian_finish_records_stop_after_complete_write` mocks successful reporting, not a failed exclusive STOP write or concurrent verification (`r1/tests/test_b1_cgroup_pure.py:228-277`). A reviewer cannot conclude that a finalization failure is always distinguishable from successful completion. Make a positively verified finalization receipt or another durable protocol a prerequisite for verification, with failure and concurrency tests; a missing or partial receipt must STOP. Assess how that protocol preserves the user’s no-deletion and no-retry rules.

2. **A successful FINISH send has a parent-death/lease-release race.** The guardian tests the parent pidfd only at the start of each poll iteration (`r1/exam/b1_cgroup_guardian.py:67-89`). On `FINISH`, it checks `populated`, sends `FINISHED`, and returns (`:114-120`); the parent then waits and closes its own lease (`r1/exam/b1_cgroup.py:384-392`, `r1/exam/runtime.py:934-939`). If the parent dies immediately after a successful guardian send and before finalization is complete, the guardian can exit and close its inherited lease too, with no parent-death freeze/hold or durable notification. A send failure is handled (`guardian.py:41-49`), but successful send followed by death is a distinct interleaving. Similarly, guardian exit after FINISH but before a later wait/control failure means the parent cannot rely on guardian retention when it reports STOP. This does not assert that the interleaving occurred. Establish a reviewed end-of-run ownership/acknowledgement protocol whose failure states retain the required lease and report the outcome; acknowledge that process death and site behavior remain real-kernel checks. The current mocks do not cover this interleaving.

3. **The guarded subtree is not the whole B1-spawned process set.** Before launching each server, `_server` invokes the configured server binary with `--help` using a direct `subprocess.check_output` (`r1/exam/runtime.py:720-725`), outside `B1Containment.spawn`. `gpu_sample` and other helper commands are also direct subprocess calls. On parent death, the guardian freezes only its fresh subtree (`r1/exam/b1_cgroup.py:144-147,168-173`; guardian `:76-89`); it does not prove those direct subprocesses have exited. This is a preflight/helper path, not an observed real GPU or model run, and it does not show an actual surviving child. Inventory the relevant subprocesses, contain or prove their bounded termination/ownership under parent failure, and limit any claim accordingly. The direct `r1.exam.campaign` path also lacks the parent/lease/server/inside-tree ownership proof, as the candidate itself discloses.
