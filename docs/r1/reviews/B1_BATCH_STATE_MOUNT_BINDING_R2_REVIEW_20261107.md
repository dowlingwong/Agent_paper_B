## Scope and evidence

`_mount_for` now returns the most-specific matching `/proc/self/mountinfo` mount ID along with its mountpoint, major:minor and filesystem type; equal-length competing entries are refused rather than guessed. `_require_local_filesystem` still checks the selected device against the directory's `st_dev` and accepts only ext4/xfs, then returns all four fields. In the production B1 path, `ExamRunner.start` checks the work-directory parent before exclusive `mkdir`, checks the new batch child before ACTIVE/lease/work, and refuses unless the two returned identities are equal. A distinct bind mount sharing the device number has a distinct selected mount identity and is refused in the candidate's mocked regression. The candidate records the selected identity in ACTIVE and compares it again during the proposed receipt verification and immediately before ACTIVE retirement. Source inspection supports the intended correction to the non-comparison finding in `B1_BATCH_STATE_MOUNT_PREFLIGHT_REVIEW_20261107.md`.

The identity is a point-in-time value in the reading process's mount namespace; it is not an authenticated site-qualification receipt. Linux mount IDs can be reused after unmount, and overmount/mountinfo snapshots or same-UID/privileged changes can race these checks. Different namespaces can also lead to refusal or require explicit operational verification. The site operator must separately establish that the actual batch/work mount and backing device are the ones qualified, check both required rename flags and storage capacity, and the independent reviewer must assess the evidence. The ext4/xfs type check itself does not prove locality, rename error semantics, durability or mount stability. The report explicitly retains these limits.

The retained `unittest_r16.txt` reports 39 passing tests, including a mocked same-device/different-mount rejection, changed ACTIVE mount refusal and matching identity case; its SHA-256 matches `704750ccf19820ed5f286d022251c60ad0e0af399e1e1b6da715a86089cd80ba`. They are implementer-reported mock results; I did not rerun them, inspect a real mount namespace or verify the target site. The new child directory intentionally remains if the second check fails, and the test expects no ACTIVE creation; this is not proof of all other B1 no-deletion behavior.

The canonical supervisor and `b1_finalization` module remain absent in this branch. Final ACTIVE retirement still has an unresolved success-versus-STOP window, and other JSON writes, harness pending-guard cleanup, process/lease/server ownership and STOP coordination remain open. The accepted scope here does not supersede those blockers or authorize launch.
