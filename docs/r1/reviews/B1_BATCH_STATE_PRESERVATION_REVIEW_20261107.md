# Independent review: B1 batch-state preservation

**Verdict: NOT ACCEPTED for integration.** Candidate `34b1004` adds useful byte-preserving publication on successful operations, but a post-exchange failure can leave a B1 STOP without a durable STOP state while the canonical state remains `RUNNING` or `COMPLETE`. This is a source-supported failure path, not an observed B1 incident. No tests, kernel or filesystem mutation, host access, model, GPU, experiment, process signal, or deletion were performed in this review. B1 has not been started according to the coordinator; no host check was performed here.

## Blocking finding: successful exchange followed by a reported failure

`r1/exam/b1_state_preserve.py` `publish_state` exchanges the new candidate with `batch_state.json` and only then verifies both path identities and calls `fsync` on the archive and parent directories. If either post-exchange check or either directory fsync raises, `publish_state` never returns the new identity. The test `test_failure_after_exchange_retains_both_inodes` correctly models the old inode being retained and the new inode becoming current, but does not call the runner's STOP or recovery paths.

`ExamRunner.save` assigns `self.b1_state_identity` only from a successful return. After that failure the in-memory identity is the old, now-retired inode. `exam_runner.main` catches the exception, changes the in-memory status to `STOPPED`, and calls `report_b1_stop_and_save`; that second save fails its initial expected-identity check because the canonical file now has the new inode. The helper reports a best-effort stderr error but cannot establish durable STOP. The B1 `finally` calls `runner.close(preserve_running=False)`, which removes `runner.lock` and closes the lease. If the failed save was a normal progress save, the canonical `RUNNING` state can subsequently be treated as a resumable batch by `ExamRunner.start`, contrary to the author's instruction that a STOP waits for the author. If the failed save was the final `COMPLETE` save, `b1_batch.verify_batch` sees `COMPLETE` at the canonical path and does not itself check a separate STOP marker; if its other validations pass, a false completed-batch verification is possible. Neither scenario has been executed or observed here.

The report mentions a stale identity and that durable STOP is not assured, but does not spell out this concrete false-resume/false-completion consequence. The user's 7 November prompt §0.4 requires STOP, preservation, STATUS publication and no retry or override. The problem cannot be closed by merely changing the report or ignoring fsync errors. The implementer must make post-publication ambiguity fail closed across the runner, recovery and verifier, without deleting old states; then add targeted tests for failure after exchange during both RUNNING and final COMPLETE publication, STOP-persistence failure, and refusal of resume/verification. An independently reviewed, non-overwriting STOP marker and a verifier/recovery refusal are one possible component, but the required ordering and failure behavior must be demonstrated, including cases where that marker itself cannot be persisted. The operator must additionally qualify the actual filesystem and site failure semantics. Effort is not yet established.

## Verified scope and remaining boundaries

* On the intended successful cooperative path, Linux `RENAME_NOREPLACE` for the first publication and `RENAME_EXCHANGE` for later publications are selected; the new file is exclusively created, written and fsynced, and the old inode is retained at the unique archive name following exchange. The static checks cover the last path component, owned regular state, directory ownership and modes, same device and the expected inode. The supplied mocks model these operations; I did not rerun them or test the real kernel, site filesystem, crash durability or NFS behavior.
* `batch_state.json` remains JSON at the same path read by the batch verifier and resume path. Stage A continues to use the previous writer, so its guardian completion format is not changed by this diff. The site's supported rename flags and directory fsync behavior remain unverified; disk and inode growth must be estimated and monitored.
* Existing batch ownership and ancestor/same-UID pathname races are not proven by directory UID and mode checks. `ExamRunner.start` uses an existing output directory and can operate on a pre-existing state before this new publisher runs. Those are separate material blockers under the author's protection of other work trees. As the candidate report says, this does not fix other repeated JSON writes, audit cache, pending-guard unlink/truncation, runner-lock deletion, or asynchronous STOP coordination.
* The reported 11 passing in-memory tests are implementation-worker evidence, not an independent rerun. Their retained output SHA-256 matches `9e28b326d1df2b9bb4c6a24b4fa1b6e961ab705ae52cf6d784758a5cfa4c0345`. The mock `MemoryFS` does not establish actual rename/exchange or fsync behavior, and no test exercises the runner STOP handler or full verifier after a failed exchange.
