## Render-status and hash follow-up at `f029c9d19cd7ed36cbccbdb583eb08a498706cf5`

**Scoped verdict: NOT ACCEPTED as a complete stale-output and source-provenance safeguard.** The original metadata guard remains accepted for its narrow purpose; full L4.3 remains NOT ACCEPTED. The new mechanism is useful for a single uninterrupted writer and an intact, complete manifest, but the verification claim requires the gaps below to be addressed or explicitly narrowed.

1. **The verifier accepts an incomplete manifest.** It trusts the recorded renderer path and iterates only entries actually present in `inputs` and `outputs` (`r1/analysis/pilot_figures.py:164–174`), without checking the expected renderer path or required input/output sets. In a temporary synthetic directory I supplied `SUCCESS`, a matching hash for an arbitrary `source.py`, and empty input and output maps: `verify_outputs` returned `True` although no pilot inputs or products were present. A dropped individual entry likewise escapes checking. Require the exact expected source identity and required input/output names, and test missing entries, altered hashes and missing files. The committed manifest currently does list the intended renderer, three inputs and nine outputs (`papers/r1/generated/pilot/provenance.json:2–28`); this finding does not assert the current files are wrong.

2. **Recorded hashes do not necessarily identify the bytes actually used.** The renderer reads the noise and offline summaries and proposals earlier (`r1/analysis/pilot_figures.py:73–80`) but hashes the source and inputs only after writing outputs (`r1/analysis/pilot_figures.py:135–144`). If an input or renderer source changes during an invocation, the manifest can record the later bytes and verification can pass even though the running process used earlier content. Read and hash the same input bytes used for computation, and bind the loaded renderer identity or detect changes throughout the invocation; test a mutation between read and manifest creation. The source hash records current file content, not a Git revision or a guarantee of code actually loaded.

**Status behavior and limits.** `main` writes `IN_PROGRESS` before calling the renderer, catches `BaseException` to write `FAILED`, and writes `SUCCESS` only after the renderer and manifest finish (`r1/analysis/pilot_figures.py:147–156`). A process terminated after the initial status write and before successful completion leaves `IN_PROGRESS` (or malformed status if interrupted during a non-atomic status write); verification refuses non-success or fails parsing. A caught failure leaves `FAILED` and old files in place; the synthetic fixture exercises that path (`r1/tests/test_pilot_figures.py:123–135`). This protection is cooperative: consumers must invoke verification, and simultaneous renderers share a status and output directory without locking, so one can mark success while another is still writing. The handoff's assertion that a failed attempt marks old files unusable (`docs/r1/overnight/LOCAL_L4_3_HANDOFF.md:31`) should be understood in that single-writer, verification-required context. No interrupted process or concurrent writer was run in this review.
