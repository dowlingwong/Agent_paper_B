## Render-status and hash follow-up at `f029c9d19cd7ed36cbccbdb583eb08a498706cf5`

**Scoped verdict: NOT ACCEPTED as a complete stale-output and source-provenance safeguard.** The original metadata guard remains accepted for its narrow purpose; full L4.3 remains NOT ACCEPTED. The new mechanism is useful for a single uninterrupted writer and an intact, complete manifest, but the verification claim requires the gaps below to be addressed or explicitly narrowed.

1. **The verifier accepts an incomplete manifest.** It trusts the recorded renderer path and iterates only entries actually present in `inputs` and `outputs` (`r1/analysis/pilot_figures.py:164–174`), without checking the expected renderer path or required input/output sets. In a temporary synthetic directory I supplied `SUCCESS`, a matching hash for an arbitrary `source.py`, and empty input and output maps: `verify_outputs` returned `True` although no pilot inputs or products were present. A dropped individual entry likewise escapes checking. Require the exact expected source identity and required input/output names, and test missing entries, altered hashes and missing files. The committed manifest currently does list the intended renderer, three inputs and nine outputs (`papers/r1/generated/pilot/provenance.json:2–28`); this finding does not assert the current files are wrong.

2. **Recorded hashes do not necessarily identify the bytes actually used.** The renderer reads the noise and offline summaries and proposals earlier (`r1/analysis/pilot_figures.py:73–80`) but hashes the source and inputs only after writing outputs (`r1/analysis/pilot_figures.py:135–144`). If an input or renderer source changes during an invocation, the manifest can record the later bytes and verification can pass even though the running process used earlier content. Read and hash the same input bytes used for computation, and bind the loaded renderer identity or detect changes throughout the invocation; test a mutation between read and manifest creation. The source hash records current file content, not a Git revision or a guarantee of code actually loaded.

**Status behavior and limits.** `main` writes `IN_PROGRESS` before calling the renderer, catches `BaseException` to write `FAILED`, and writes `SUCCESS` only after the renderer and manifest finish (`r1/analysis/pilot_figures.py:147–156`). A process terminated after the initial status write and before successful completion leaves `IN_PROGRESS` (or malformed status if interrupted during a non-atomic status write); verification refuses non-success or fails parsing. A caught failure leaves `FAILED` and old files in place; the synthetic fixture exercises that path (`r1/tests/test_pilot_figures.py:123–135`). This protection is cooperative: consumers must invoke verification, and simultaneous renderers share a status and output directory without locking, so one can mark success while another is still writing. The handoff's assertion that a failed attempt marks old files unusable (`docs/r1/overnight/LOCAL_L4_3_HANDOFF.md:31`) should be understood in that single-writer, verification-required context. No interrupted process or concurrent writer was run in this review.

## Safeguard correction at `8a1ecf58b003b8cbd4a8c43567b1821416303060`

**Scoped verdict: the manifest-set, consumed-input and cooperative single-writer corrections are accepted by inspection; renderer execution identity remains unverified.** This does not accept L4.3 as a whole. The previous synthetic empty/redirected-manifest counterexample is now rejected: the verifier requires the exact declared renderer path and exact three-input and nine-output key sets before checking each hash (`r1/analysis/pilot_figures.py:19–24,173–184`). The new fixture covers the combined empty/redirected case and changed input/output content (`r1/tests/test_pilot_figures.py:143–176`). Missing files also fail on read, by inspection; separate omitted-entry, added-entry, changed-renderer and missing-file fixtures are not present.

The renderer reads each input once into `source_bytes`, parses those same bytes, and hashes that mapping into the manifest (`r1/analysis/pilot_figures.py:79–87,142–147`). A later input change therefore produces a mismatch when the verifier compares the current file to the digest of the consumed bytes (`pilot_figures.py:179–181`). The inputs are read separately, not as an atomic snapshot; the hashes establish the individual byte sequences used, not a simultaneous cross-file snapshot. The focused tests do not simulate mutation during input consumption.

The exclusive nonblocking writer lock covers status transitions, output writing and manifest creation; verification takes a shared nonblocking lock for its status and hash checks (`r1/analysis/pilot_figures.py:152–169`). Cooperating overlapping renderers or verification during a render are thus refused while the lock is held. After `IN_PROGRESS` is written, a caught failure writes `FAILED`; an uncatchable termination leaves `IN_PROGRESS` or a malformed status if interrupted during a write, and subsequent verification rejects it or raises while parsing (`pilot_figures.py:156–173`). If a process dies after acquiring the lock but before replacing a prior `SUCCESS`, prior products remain unchanged and can still verify; status is not a durable record of every attempted invocation. Direct consumers and noncooperating writers do not hold the lock, and verification alone does not reserve files for subsequent use. The failure fixture checks a caught exception (`r1/tests/test_pilot_figures.py:123–135`); interruption and lock contention were not exercised here.

**Remaining source-identity limitation:** the renderer still hashes `Path(__file__)` near the end of rendering (`r1/analysis/pilot_figures.py:142–145`). If the file changes after Python loaded the module but before this hash is read, the manifest can identify the new on-disk source although the process executed previously loaded code; verification can then succeed against the new file. The correction binds data bytes but does not establish the actual loaded renderer bytes. The current committed manifest's source hash matches the current file through the passing verification test, which does not establish absence of such a change during the historical invocation. Bind execution to a known immutable source snapshot or explicitly treat the renderer hash as the file observed at manifest creation, not proof of the code executed.
