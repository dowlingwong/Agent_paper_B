Actual executable identity and launch still require site verification.

The proposed entry guard is conditional on `__name__ == '__main__'`. An alternative Python caller can import this module and call `main()` without triggering the guard; the contract therefore depends on the reviewed direct `python3 -B r1/scripts/b1_supervisor.py ...` invocation and does not independently prevent arbitrary library entry. Neither invocation nor a successful guard proves that `site`, `.pth` code, external libraries, or node code cannot intentionally reset the flag or create other caches. The reviewer did not establish a security boundary against same-UID actors. The proposed environment also affects synthetic B1; production non-B1 worker launches keep the previous environment branch.

The submitted test source AST-extracts the environment function, early guard and conditional argv and reports seven mocked cases. I inspected the test; I did not rerun it or independently observe its reported output. The mock does not launch real Python, exercise site startup, test actual file system imports, prove the complete executable chain, or find non-bytecode temporary files. Actual target Python behavior, the exact startup command, node environment and filesystem must be checked by the authorized site operator under an independently reviewed, no-deletion probe before B1. The implementer must bind the final operator message to the exact `-B` invocation and independently review it; if arbitrary library invocation must be supported, enforce the guard in `main` too, without representing this as protection for the already-started interpreter. Effort is a bounded documentation/code review plus site-dependent inspection; all harness, STOP, tests and final gate blockers remain.
