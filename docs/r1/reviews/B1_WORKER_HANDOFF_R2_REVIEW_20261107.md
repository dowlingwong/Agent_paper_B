# Independent review: B1 cooperative worker handoff, round 2

**Verdict: NOT ACCEPTED** for the production handoff at candidate `aa1d37ffc62706274acec58cfa27f126e8b69c96`. The revision substantially addresses the two concrete round-1 findings, but its parent-side `released` flag is not atomic with delivery of the release record. The resulting ambiguous-release path can run a child the parent treats as unreleased, and may alter the STOP scene. No tests, subprocesses, signals, host access, model, GPU, experiments, or deletion were performed for this review. This verdict does not affect existing B1 STOPs or authorize B1.

## Blocking: a completed pipe write can precede an exception before the parent records release

`r1/exam/b1_worker_handoff.py:71-76` writes the complete newline-terminated release record with `os.write`; `r1/exam/runtime.py:785-788` sets `released = True` only after `release(...)` returns. A Python asynchronous exception, including a delivered signal handler raising `KeyboardInterrupt`, can occur after the kernel has accepted the entire write but before the assignment at line 788 (or while returning from `release`). The source does not mask or otherwise synchronize this transition. The child can read the complete record, validate it, attach the parent-opened `runner.log`, import the campaign and begin execution (`r1/exam/b1_worker_entry.py:9-22`), even though the parent's exception handler sees `released == False` and follows the supposed *unreleased* path (`runtime.py:789-802`). The parent closes the pipe and waits at most 30 seconds, then reports STOP if the child does not exit; it does not stop or prove quiescence of a child that actually received a complete release. That child may append to the log or modify campaign state after the parent reports STOP. This is a source-level possible interleaving, not an observed production incident. The report's statement that an unreaped child has no attached root log and only startup effects possible is not established for this path. The tests at `r1/tests/test_b1_worker_handoff_unittest.py:133-170` mock a release failure with no record delivery and cannot expose a successful write followed by an exception before the flag update.

A correction must treat an ambiguous send as potentially released and coordinate safe, positively owned child/process-tree quiescence and preservation before reporting STOP, or use a reviewed synchronization protocol with a defensible release linearization and failure behavior. The fix must preserve the original error, handle parent death, short write, timeout and descriptor-close errors, and must not signal an unverified process or erase evidence. The broader B1 STOP/descendant/lease problem remains independently unresolved; a test-only shim or a note that the child is “unreleased” is insufficient. A full write followed by a `finally` close error also belongs to the ordinary released-child STOP path and needs to be considered in that broader fix. If a 30-second wait genuinely times out before any release, the proposed code appropriately reports the child as unreaped, but even then it has not proved that Python startup and installed interpreter hooks are read-only.

## Earlier findings and scope

The original supplied-path alias defect is addressed on the intended production B1 construction path: `runtime.py:493-504` compares the supplied absolute spelling with its resolved spelling before host/registry checks; the subsequent production batch creation remains exclusive. Its symlink test is a `Path.resolve` mock rather than a filesystem check, and same-UID changes after the comparison remain a documented cooperative race. DRYRUN/Stage A/B2 retain the prior construction branch; production B1 still rejects a pre-existing direct-child batch, including a non-STOP crash recovery, a disclosed operational restriction.

For the straightforward failure cases where *no complete release was delivered*, the parent closes the writer, waits for its `Popen` child and does not signal it (`runtime.py:789-809`). The child starts with stdout/stderr on `DEVNULL`, reads the job and awaits the record before importing `campaign`, and suppresses an exception before attaching the log (`b1_worker_entry.py:9-28`). Thus this revised path addresses the previously identified ordinary EOF traceback to `runner.log`, provided actual startup code has no other writes and the child exits. Parent-death/EOF, short writes, real `/proc` and process scheduling were not exercised by the reported mocked tests; `PYTHONDONTWRITEBYTECODE=1` does not prove `.pth`, `sitecustomize`, native code or all imports are read-only. `finally` descriptor close can also raise and mask a prior exception; no complete close-failure handling is established.

The parent-passed lease descriptor, observed parent/child PID and start ticks, directory identity and server snapshot are a cooperative source-level check. File inode equality is not independent proof of shared OFD, and URL equality is not proof that the PID owns the TCP endpoint; the candidate correctly records those site and same-UID limitations. Pipe records are not retained receipts. The 23 reported mocked `unittest` checks were not independently rerun and no separate raw log was supplied. This unit does not restore the earlier Stage A→B1 kill/resume coverage or remove pending-guard deletion, STOP quiescence, host ownership, author-note ordering, or final checkout gates.
