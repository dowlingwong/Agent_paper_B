### Majors

**M1 — Layout is the superseded S2-C4 16k layout; R1-SWEEP2-LAYOUT (same day, later) fixed the 32k layout.**
`sweep2/spec.c3b.example.json:165-167` has `walltime_s 10776`, `request_disk_kb 42439718`, `request_memory_mb
32000`; the committed dry-run ad carries `RequestWalltime=10776`, `RequestDisk=42439718`; the doc calls these "the
S2-C4 measured layout" and states at `S2_C3B_UNIT.md:176-181` that "S2-C4 measured at 16,384 context … re-measuring
at 32k remains the sweep-2 prerequisite it already was". That prerequisite was satisfied by the accepted
`f172d299` 32k smoke (both modes rc 0, KV 1,360 MiB, `SMOKE_RESULTS_20261116.md`), and `R1-SWEEP2-LAYOUT` replaced
the 16k layout with **`request_walltime 12,203 s`, `request_disk 42,460,977 kB`, `request_memory 32,000 MB`** (the
branch-tip `sweep2/spec.example.json` already carries `12203/42460977`). This is a documented authority drift, not
a run-safety blocker (the C3b job is a fourth of a chunk; 10,776 s has large margin). **Fix:** take the accepted
32k values (or justify a smaller request from a measured liveness wall time), re-render
`sweep2/dryrun/c3b/`, update `test_renderer_c3b_pins_…` (it asserts the stale numbers) and the doc's residual-risk
paragraph; add `level_layout` to `job_record.json` as the C2 chunk record does.

**M2 — The prompt-length re-measurement is not of the longest prompt class, and the "recorded 1,345-token
maximum" is not a maximum — the pinned record itself shows 1,878.**
The unit measures `trial_1` plus a declared 11-record `memory_on_declared_12` fixture and calls it "the longest
prompt class" (`S2_C3B_UNIT.md:34`) and compares against `SWEEP1_PROMPT_MAX_TOKENS = 1345` as "the recorded
1,345-token maximum" (`s2_c3b_lib.py:119-124`; doc §"Sweep-1 prompt-length comparison source"). But the pinned
pilot that contains the 1,345 value also contains the W=20 root ledgers, and they run to budget 20 with growing
memory:
`results/r1/pilot/E1b_rerun2_A_PARTIAL_memory_on_20261014/provenance/ledgers/roots/tabular_mlp__s142/root_trials.jsonl.gz`
(blob `1da59574…` at `9ae6d877`; sha256 of the .gz = `bd0408a0df8dd47cf629fcbb4439e59072f54858f497097d0ad38a80266860a7`;
`memory_mode=append_only_summary`, 20 trials) records the 7B `usage.prompt_tokens`:

```
budget  1 →  520 ; budget 12 → 1345 ; budget 20 → 1878
```

and across the 54 rerun-2 root ledgers the maximum is **1,886** (`tabular_mlp__s112`). So 1,345 is the **budget-12**
value (the 11-record class the unit reproduced), while the longest sweep-2 prompt class (19 records, budget 20) is
~1,878–1,886 tokens with the 7B tokenizer. Two consequences: (i) the "longest prompt class" claim is wrong (the
measured class is a *middle* class), and (ii) `ratio_vs_sweep1_recorded_max` / the report line "recorded sweep-1
maximum (…) 1345" would state a baseline that the unit's own pinned record contradicts by ~40%. The 32k fit
decision is unaffected (even 19 records would be ~1–2k pick tokens vs 32,768 — >10× headroom), but the deliverable
is a prompt-length record and it would be wrong. Also note the 1,345 source is the **14 Oct** prompt set: at least
`openml_breast_w`'s trial-1 text differs from the 27 Oct liveness/sweep-2 text (rerun-2 `context_sha256`
`d31c77a3…`, 483 tokens vs liveness `61aa9226…`, 482 tokens), so it is not the same text class as the sweep-2
prompts for that node. **Fix:** add a budget-20 / 19-record variant (cheap: same declared-fixture builder) and
report the true observed W=20 7B maximum from the pinned root ledgers (SHA-pinned, like the other records), and
relabel 1,345 as the b012 value, not a maximum.

**M3 — The branch is 3 commits behind the accepted wrapper (`sweep2-main-20261116` tip `d23e4e22`), so it misses
round-5.1 hardening and the 32k layout update.** `066bac28`'s parent is `8a8ea832` (round 5); the tip chain is
`d9a17b86` (round 5.1: m11 layout-field floors, m12 exact `--chat-template-kwargs`, m13 kill-before-liveness-STOP
persistence, m16 gate verdict on STOP, +1 C2 test), `f172d299` (32k smoke + spec layout), `d23e4e22` (docs). The
C3b spec/doc were copied from the round-5 spec: `sweep2/s2_c2_lib.py` imported by `s2_c3b_lib` is the round-5
validator, so the C3b gate **does not** enforce the accepted wrapper's `--chat-template-kwargs`-exactly check
(`d9a17b86` changes it to `kwargs != {"enable_thinking": False}`) and does not enforce the measured disk/memory
floors. That matters here because a spec with extra server-level `chat_template_kwargs` would pass C3b validation
while the per-request `/apply-template` kwargs stay `{"enable_thinking": False}`, silently making the measured
prompt differ from what the server renders. Also the C2 suite on this base is 28 tests (tip: 29), which is why the
doc's "34 S2-C2" count is impossible (m1). **Fix:** rebase/merge onto the tip (or cherry-pick `d9a17b86`) and add
the exact-kwargs and layout checks to `s2_c3b_lib.validate_spec` explicitly.

**M4 — Post-run STOP evidence is persisted while the owned llama-server is still running, so the transferred
`SHA256SUMS` can fail verification at seal.** In `run_liveness_job` every post-run STOP calls
`_stop_with_evidence` → `_persist` → `c2._write_sums(Path("."))` while the server is still alive; the kill only
happens in the `finally` at `sweep2/s2_c3b_lib.py:931-932`, after the sums were written. `SHA256SUMS` includes
`llama-server.log` (`s2_c2_lib.py` `SUMMED_OUTPUTS`). Any line the server writes after hashing (last-request slot
log, SIGTERM/handler message) changes the log; `seal` then refuses with `STOP: transferred SHA256SUMS verification
failed` — i.e. exactly the shortfall/failure path that the unit promises "evidence persists and can be sealed"
(`S2_C3B_UNIT.md:27-29, 158-162`) is the one that can become unsealable. The success path is fine (persist happens
after the `finally`). This is the same defect class the accepted wrapper fixed as m13 in `d9a17b86`. **Fix:** kill
the owned server (guarded for `None`) **before** `_stop_with_evidence`, then hash; or hash the log only after the
kill. Note for the rebase: the tip's m13 patch as written calls `_kill(None)` on the liveness-STOP path and raises
`AttributeError` (verified locally: `_kill(None)` → `AttributeError`), so do not copy it verbatim.

### Minors

- **m1 — wrong test arithmetic in the doc.** `S2_C3B_UNIT.md:195-197` says "105 passed (34 S2-C2 + 6 S2-C4 + 71
  S2-C3b)"; 34+6+71 = 111, and the actual run is 28+6+71 = 105 (the C2 unit doc itself says "34 (28 S2-C2 + 6
  S2-C4)"). On the accepted tip the C2 count is 29, so a rebase makes it 106.
- **m2 — no STOP when the rendered prompt does not contain the user text.** `measure_prompts` computes
  `position = rendered.find(text)` and silently uses an empty prefix when `position < 0` (`s2_c3b_lib.py:593-609`);
  `user_text_present_in_rendered=False` is recorded but not a STOP, so a template that mangles/whitespace-normalises
  the text would still produce a "measurement". Add a STOP on `not user_text_present_in_rendered` (or on an empty
  prefix decomposition).
- **m3 — tokenizer-vs-`usage.prompt_tokens` semantics is disclosed but not resolved, and can be resolved for free
  in-run.** `/tokenize(rendered, add_special=True)` may double-count a BOS that is already in the `/apply-template`
  output (the doc's residual risk acknowledges this). The job's own liveness run gives the ground truth: the pick
  server returns `usage.prompt_tokens` for the *same* trial-1 text in its own ledgers
  (`out/ledgers/*/root_trials.jsonl` → `extra.manager.llm_call.prompt_tokens`). Comparing the rebuilt
  `/apply-template`+`/tokenize` count against that in-run number (and recording both) would settle the BOS question
  and also give the authoritative pick count at zero cost. Same for a smoke `/v1/chat/completions` on one message.
- **m4 — no test of the `run_liveness_job` STOP wiring.** `test_shortfall_stop_persists_the_record_and_tars` calls
  `_stop_with_evidence` directly; no test drives `run_liveness_job` with mocked clone/fetch/server/subprocess and
  asserts (a) the record+SHA writing order and (b) that the server is dead before the sums are written. Such a test
  would have caught M4.
- **m5 — the job record has no `level_layout`.** The C2 chunk record carries
  `level_layout {request_walltime_s, request_disk_kb, request_memory_mb}`; the C3b record does not, so the layout
  actually requested by the sealed attempt is only visible in the transferred JDL/ad, not in the record (relevant
  to M1 auditing).
- **m6 — `evaluate_liveness` is slightly loose.** It does not check `report["schema"] == "r1.liveness/2"` (it only
  records it) and ignores extra nodes if the pinned report ever contained them; the 8-node requirement is enforced
  only through `nodes` cardinality. Harmless with the pinned code, but the check could be explicit.
- **m7 — the exam-seed block check covers 9001–9303, not "9001+".** `EXAM_SEED_BLOCK = (9001, 9303)`
  (`s2_c3b_lib.py:76, 211-217`). Because the spec's prompt seeds are pinned to exactly 6101–6108 and the liveness
  pairs are pinned to 100/102…115, no seed ≥ 9304 can enter, so there is no exposure; the comment/claim should say
  so or use an open-ended check.
- **m8 — the sweep-2-report disclosure is not yet carried into the vehicle.** R1-S2C3B-SEEDS requires the
  liveness/sweep seed overlap to be disclosed **in the sweep-2 report**. The unit doc discloses it thoroughly (§
  "Declared seed choice…" and residual risks), which is sufficient for this unit, but
  `S2_ENGINEERING_PILOTS_DISCLOSURE.md` — the document explicitly described as "disclosure for the sweep-2 report"
  and which already has an S2-C4 entry — has no S2-C3b line. Add one (ENGINEERING-only, 10-of-90 liveness seed
  reuse accepted by R1-S2C3B-SEEDS, no label path, no 7001–7010).
