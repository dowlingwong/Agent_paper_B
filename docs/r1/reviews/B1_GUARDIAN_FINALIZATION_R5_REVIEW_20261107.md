## The addressed operator ambiguity

`r1/exam/b1_operator_exit.py:24–47` requires absolute resolved batch and supervisor directories with the same parent, reads an owned `SUPERVISOR.json` bound to the supplied batch and HEAD, checks positive PID/start ticks, checks the known supervisor STOP, batch STOP and uncertainty names, validates the actual waited-success receipt under the publication reader lock, then rechecks STOP names and supervisor binding. Existing STOP/uncertainty wins at the first check; a change at the second raises and the CLI reports NOT_CHECKABLE. A valid receipt plus nonzero operator-supplied exit is labeled `COMMITTED_NONZERO_EXIT_OPERATIONAL_ISSUE`; it does not itself establish absence of a STOP or accept the batch. Missing or malformed binding and an unavailable receipt refuse classification. The supplied exit is an operator observation, not independently established by this code, and the script does not prove the supervisor has exited or that its STOP/log output was fully captured. The operator draft explicitly requires checking logs and actual STOPs and says to restore Track S/P before the complete-batch verifier only after normal completion is established. This reasonably documents the R4 post-commit finally exception as an operational anomaly, under the stated cooperative publisher and fault model, provided that the operator actually follows it. The draft is conditional and says the operator **may** run the classifier; classification does not establish safe handover, verified restoration, or final B1 authorization.

## Blocking: the actual complete-batch reader can ignore a persisted supervisor STOP

The production analysis entry calls `verify_batch` (`r1/exam/analyze.py:139`); `verify_batch` checks `batch/STOP.json` and the receipt (`r1/exam/b1_batch.py:71–81`), but does not call the new classifier, receive the supervisor directory, or otherwise check `supervisor_dir/SUPERVISOR_STOP.json`. The receipt schema (`r1/exam/b1_exit_receipt.py:205–209,263–265`) binds runner, HEAD, ACTIVE, state and finalization, but has no supervisor directory or supervisor binding. Thus the new STOP priority is a property of the optional standalone operator check, not of the production reader. The command's exit code is also zero for the nonzero-exit operational-issue classification, so it must not be treated as a complete-batch acceptance signal.

A concrete source-supported interleaving is: terminal ACTIVE retirement succeeds; reconciliation cannot read back the commit; creation of the batch uncertainty marker fails; the supervisor records `SUPERVISOR_STOP.json` successfully and retains its publication lock (`r1/scripts/b1_supervisor.py:69–96,138–141,220–224`); later the stopped supervisor exits and its lock is released. After transient I/O recovers, a direct existing `verify_batch` call can validate the committed receipt despite the **successfully persisted** supervisor STOP. No such incident is claimed. This is narrower than an arbitrary simultaneous-storage-failure guarantee: an available supervisor STOP exists, but the actual reader is not bound to it. The draft's log-inspection instruction is useful process discipline, yet does not make the reader refuse a recorded STOP when that optional command is skipped.

**Minimal concrete correction:** bind the actual supervisor directory and immutable `SUPERVISOR.json` bytes/hash to the waited-success receipt (or another immutable batch-owned record created by the supervisor); make the actual shared-lock receipt verification used by `verify_batch` validate that binding and refuse any named `SUPERVISOR_STOP.json` with `lstat`-based error handling before and after reading the receipt. The supervisor directory must be a canonical same-parent owned location, and the record must bind the same authorized HEAD and batch. Preserve the publication lock across those checks so the supervisor cannot write a STOP concurrently under the cooperative protocol. This is a candidate implementation, not an assertion that same-UID malicious replacement, failed STOP persistence, concurrent out-of-contract mutation, or crash durability are solved.
