# Independent review: B1 batch-state preservation, round 3

**Verdict: NOT ACCEPTED as a complete B1 completion/verification path or for integration as ready-to-run.** Candidate `cbfbc4a` adds an ACTIVE barrier that addresses the particular R2 case in which receipt fsync fails before retirement: in the modeled ordering ACTIVE remains, so the verifier refuses the visible receipt. The final ACTIVE retirement still has no demonstrated end-to-end success-versus-STOP guarantee, and the actual supervisor and guardian finalization verifier remain absent. This review did not run tests, perform kernel or filesystem operations, access a host, run a model or GPU, signal a process, or delete files. B1 launch status is coordinator-reported, not independently checked on TASL-7.

## Remaining blocking failure: successful retirement followed by publisher failure

`publish_waited_success` validates inputs, writes and fsyncs the receipt, then calls `_retire_active_last`. The latter fsyncs the two directories **before** the no-replace rename of ACTIVE to `_to_delete/B1_ACTIVE.completed.json`; it deliberately does not fsync the directories after that rename. `verify_waited_success` accepts only absent ACTIVE, a present retired sentinel and matching receipt/state/finalization bytes. If the final rename takes effect but an exception is raised before the supervisor has completed its own successful exit, a subsequent verifier can observe exactly those acceptance conditions. For example, the `finally` in `_retire_active_last` catches `OSError` from `os.close`, not `BaseException`: a Python callback already queued before the signal mask or another asynchronous exception can interrupt after the rename. The caller can also fail after `publish_after_wait` returns, because there is no implemented canonical caller/exit contract. A process death after the rename is a separate unresolved lifecycle case. These are source-supported possibilities, not observed incidents. An error reported as STOP must not turn into an apparently successful batch when STOP recording also fails.

Blocking catchable OS signals in the publishing thread narrows one race but is not evidence that previously queued Python callbacks, another thread's activity, process death, all I/O failure semantics or later caller code cannot produce that outcome. The report explicitly identifies this as a **material unresolved fault-model STOP**; an ext4/xfs mount label and mocked tests do not resolve it. The Linux [rename(2) manual](https://man7.org/linux/man-pages/man2/rename.2.html) specifies `RENAME_NOREPLACE` and documents a failure-after-rename case on NFS, which the candidate excludes; that example does not establish or refute all ext4/xfs error behavior. The Linux [fsync(2) manual](https://man7.org/linux/man-pages/man2/fsync.2.html) says a directory fsync is needed to ensure a directory entry has reached storage. This candidate intentionally has no directory fsync after the final rename, so its exact crash-recovery and success-publication fault model remains to be justified, not inferred from an ext4/xfs label.

To unblock: the B1 implementer must implement and independently review a concrete supervisor/finalization and publication protocol whose observable verifier outcome distinguishes a completed publication from reported STOP under its documented failure model, including a successful final rename followed by a queued callback or publisher/caller failure, failed STOP publication, and process death. The review must explicitly assess what happens when final storage operations themselves are unreliable; an external observer is one possible solution, not a mandated architecture. Then the authorized site operator must establish supported filesystem/rename and operational behavior without deleting probe files. The required effort and site capability are not established. No author choice is inferred.

## Site check is currently late

`_require_local_filesystem` rejects filesystem types other than ext4/xfs and checks the batch device against `/proc/self/mountinfo`. It is called during waited-success publication **after** the runner has been waited, and during verification; this candidate does not call it from production `ExamRunner.start` before B1 work. If the actual work tree uses an unsupported filesystem, a run could finish before encountering this new restriction. The existing report calls for an operator site check, but no site filesystem is verified here and `$HOME` free-space evidence does not establish the B1 work mount. Integrate the capability/type check into the reviewed preflight before any experiment if this restriction is retained; document an actionable alternative if the site's filesystem is excluded. The label alone does not prove physical locality, support for both rename flags or error/durability semantics.

## Source and test scope

The new ACTIVE check prevents a fully written receipt from being accepted in the **modeled** R2 file-fsync and directory-fsync failures because retirement is not called after the write raises. `RENAME_NOREPLACE` also refuses an existing retired name. The tests exercise this behavior and mount/signal checks using mocks; they do not perform a real wait, rename, signal-mask interaction, crash, filesystem recovery or verifier run after a successful rename followed by a caller failure. The candidate's retained `unittest_r11.txt` reports 34 passed and hashes to `4a15ba566a1b414f6f30c2a0403e02bc63439a9c5b693b316f6a9999377b0c29`; it was not rerun here.

`publish_after_wait` still has no production caller in this checkout, `publish_waited_success` accepts a cooperative caller-supplied wait result, and `r1.exam.b1_finalization` is absent. Consequently the real parent/guardian/lease, finalization evidence and end-to-end success path remain unimplemented on this branch. Same-UID writers, concurrent mount/path replacement, worker/server identity, other JSON writes, fixed-harness cleanup and asynchronous STOP coordination remain outside this unit. Existing-batch refusal prevents automatic resume in the intended B1 entry but does not itself prove all prior state is preserved or all STOPs are durable. The independent R1 and R2 reports remain applicable except for the narrow pre-retirement receipt-fsync case corrected here.
