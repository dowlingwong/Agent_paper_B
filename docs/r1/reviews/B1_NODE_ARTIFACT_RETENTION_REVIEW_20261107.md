## Required integration finding: STOP and queued audits

`r1/exam/campaign.py:203–207` submits all audit configurations to a `ProcessPoolExecutor`, then consumes futures inside the executor context. If one future raises the preservation STOP, context exit calls executor shutdown with its default waiting behavior; submitted but not yet started configurations may still start before the worker exits. That conflicts with the author's explicit instruction to **stop starting new work** on B1 STOP. This is not resolved by the artifact helper. The B1 integrator should use a bounded submission strategy and cancel not-yet-started futures on the first failure, then make the failure promptly visible to the runner so the existing B1-owned worker and llama-server shutdown paths can act. The exact integration must avoid waiting for queued work to start and must record any log/record lines written during shutdown, as the author permits; a fresh reviewer must exercise a queued-work failure and confirm no later submission or start. This recommendation does not require cgroups, freezing, malicious-same-UID defenses or proof of completed GPU work. Already running operations and shutdown-side log writes must be described honestly rather than claimed absent.

A further scientific disclosure is necessary: `run_config` begins `wall_seconds` timing immediately before the new preservation call (`r1/c3/audit.py:82–88`), and the existing outer worker timing can also include archive overhead. Metric inputs and canonical output paths are unchanged by this unit, but timing and storage usage can change. Report this implementation difference and qualify the complete B1 analysis separately; no outcome equivalence or author protocol change is inferred.
