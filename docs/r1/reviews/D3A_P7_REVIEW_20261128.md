## Findings

### BLOCKER

**B1 — "worker failures = 0" is false; the gate script misclassifies charged failures.**
The record says "There were no worker failures" and every row of the §2 table shows
`worker fail = 0`. The captures show **33 charged worker runs failed**: 32 `invalid_config`
(`exit code 2`) and 1 `runtime_error` (`exit code 1`). Every one has
`extra.worker_failure_message` and `run_command finished … success=False` in the captured driver
log (16 such lines for 6301, 17 for 6302). The per-campaign `worker_runs` include them
(271 charged runs total: 195 harness + 76 replicate).

| seed | A0 | A0R | A1 | A2 | FIXR3 | EGATE | LADDER |
|---|---:|---:|---:|---:|---:|---:|---:|
| 6301 | 5 | 5 | 4 | 2 (1 `runtime_error`) | 0 | 0 | 0 |
| 6302 | 4 | 4 | 4 | 4 | 0 | 0 | 1 |

The cause is `worker_gate.py`: it treats every record with `validity_status == "invalid"` (or
`decision == "failed_invalid"`) as "a proposal rejected before any worker run (control-plane cost
only)", so `failed_runs` never increments and the script never checks the
`worker_failure_message` criterion in its own docstring. Only **4** of the 37 `failed_invalid`
records are actually uncharged precheck rejections (`worker_mode = local_worker_precheck`,
"structured edit is a no-op"); the other 33 ran the worker. The pooled charged failure rate is
**33/271 = 12.18 %** (6301 16/133 = 12.03 %; 6302 17/138 = 12.32 %). That is below the §10
12.99 % STOP under the declared pooled definition (failed replicate runs count as worker runs and
failures; the 76 successful replicate runs are also worker runs in the denominator). Counting only
the 195 harness-charged runs would give 33/195 = 16.9 %, above the STOP, so the receipt must state
which denominator it applies. Either way the failure count is not zero, and it must be reported.
As written, the coordinator would cite `gates.worker=PASS` on a false zero-failure claim.

**B2 — An unclassified worker `runtime_error` is omitted, and it may be a §10 STOP.**
`run-s6301/chunks/A2/campaigns/openml_climate__s6301`, `budget_index 71`, `trial-071`:
`decision=failed_invalid`, `failure_category=runtime_error`, message `exit code 1`, applied edit
`class_weight: balanced → {1` (structured edit `{1: 1, 2: 2}`). §10 makes any worker
`runtime_error` outside the two pre-admitted classes (truncated-mapping YAML `ParserError`;
`max_depth: null` `TypeError`) a **STOP**. The log line suggests the same truncated-mapping class
as sweep 2, in which case it is pre-admitted and simply belongs in the failure rate — but the
receipt neither says so nor includes the trial's `art/trial-071/run.log`, so the class cannot be
determined from the deliverable. It must be disclosed and classified, or the STOP must be reported
with a disposition.

### MAJOR

**M1 — The latency maximum is mislabelled and the projection basis is understated.**
§4 says "mean 5.75 s, maximum 6.11 s per call". The mean over the 199 calls that carry a
`latency_ms` is 5.753 s, but the maximum is **11.096 s** (6301 A0R, `budget_index 23`; second
8.087 s at index 19), not 6.11 s. 6.11 s is the largest *campaign mean* (A0R 6301). The projection
uses 6.11 s for every arm; using the observed maximum for A0R alone would raise its 18-campaign
basis from 2,640 s to 4,793 s and the seven-node sum from 38.7 to about **42.9 GPU-h** (still
< 140). The claim should be relabelled (max of campaign means) and the sensitivity stated. Also
note the denominator: 296 `llm_calls` are summed in the captures but only 199 carry a latency
(77 skipped proposals and 20 FIXR3/EGATE proposals have none), so the projection assumes the same
per-call latency for unmeasured calls.

**M2 — The nested manifests do not verify, and the failure logs are not delivered.**
The 28 inner `SHA256SUMS` files reference 1,712 entries, of which **1,324 are absent** from the
deliverable (the `art/` and `node/` trees: patches, trial run logs, node configs); all present
entries hash correctly, and the outer 224-entry manifest is sound. Consequently every inner
`SHA256SUMS` fails `shasum -c`, and the specific `raw_log_ref` logs needed to diagnose B2 (and the
32 `exit code 2` failures) are outside the receipt. Either capture the failing trials'
`art/trial-*/run.log` (and `patch.diff`) and regenerate the manifests over the delivered set, or
state the manifest scope and remove/replace the inner manifests that claim undelivered files.

**M3 — The §2 footnote misdescribes the invalid column.**
"invalid proposals were rejected before a worker run (control-plane cost only)" is false for 32 of
the 37 invalid records; they are charged worker failures. The `invalid prop.` column (totals 37)
therefore mixes 33 charged failures with 4 uncharged precheck rejections, while `runs` already
counts the 33. A corrected table should show `runs`, `success`, `worker failures`
(`invalid_config` + `runtime_error`), `precheck rejections`, and `skips` separately.

**M4 — The §11 "measured chunk time" is an extrapolation, not a measurement.**
The smoke ran one campaign per arm per seed sequentially; the 18-campaign chunk time is derived as
`18 × calls × latency` under the single-slot `-np 1` serialization assumption. That is a
reasonable engineering projection, but §11 asks for the measured chunk time per arm; the record
should say explicitly that no 18-campaign chunk was measured and that the scheduler request is an
extrapolation from campaign times.
