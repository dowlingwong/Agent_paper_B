## What the wiring does

The production runner creates a nonblocking anonymous pipe and supplies its writer to the v2 worker contract (`runtime.py:910–928`; `b1_cgroup.py:294–327`). The child verifies that the descriptor is a distinct nonblocking FIFO writer (`b1_worker_contract.py:137–155`); its inode/peer identity remains a cooperative parent contract rather than independently established. The real collector uses a fork-context process pool and wraps actual `run_config` jobs (`campaign.py:234–247`). On an ordinary thrown audit failure, the wrapper writes `S` before propagating the error (`b1_audit_stop.py:34–53`); the parent-side 50 ms polling thread marks stopping and invokes the existing owned-cgroup freeze (`:66–99,117–136`). The outer worker path also attempts notification before the executor context shuts down. The real runner checks the monitor, requires a normal completion byte and zero child exit, and checks the worker cgroup empty (`runtime.py:938–973`). Under working cooperative pipe and guardian behavior, this can surface an audit exception before the executor waits for other jobs. These are source-level observations, not measured Linux pipe, fork, process, endpoint or cgroup behavior. It does not promise instantaneous freezing: peers can act before a successful freeze.

## Blocking findings

1. **Notification failure can still leave running peers after a detected STOP.** `run_notifying_audit` calls `require_notify_fd` outside its `try` (`b1_audit_stop.py:41–42`) and, if its one-byte write raises or is short, throws `AuditNotificationStop` locally (`:45–52`). The future error reaches the collector, which again attempts the same writer inside the executor context (`campaign.py:239–247`); if this writer is unavailable or its write also fails, context exit can wait for already-running peers before the collector exits. A different forked peer still holding the inherited writer can prevent EOF, so the runner's monitor may have neither an `S` nor EOF and may not detect the failure promptly. The candidate report explicitly acknowledges this case; it is an incomplete required failure path, not a claim an actual event occurred. A notification failure is itself reported as STOP by the code, so the author's “stop at once and preserve everything” applies; waiting for a later deadline while peers write does not establish that behavior. **Unblock:** implementer must add a concrete independently observable failure path or prove a narrowly documented channel invariant sufficient for every supported writer-failure case, and inject invalid/failed write while a second owned audit task remains alive. A full pipe that already contains a STOP byte can be handled separately from a closed/invalid writer; do not assume all write failures have the same meaning. Independent review and Linux site qualification follow. Effort: code and focused synthetic tests, then site-dependent qualification; exact time unknown.

2. **Normal completion can fail spuriously because the monitor stops without draining the completion byte.** The monitor performs a nonblocking read, then immediately returns if `process.poll()` shows exit (`b1_audit_stop.py:119–125`). An empty read can occur just before the collector writes `D` and exits; the following poll can see the exit, causing the monitor to return without reading the now-queued byte. The worker exited 0, but `finish()` then raises `STOP: audit completion notification is missing` (`:142–148`; `runtime.py:969–972`). This is a concrete ordinary scheduling interleaving, not an observed incident. **Unblock:** after observing exit, drain and validate all pending notification bytes before deciding completion, without accepting a preceding STOP; exercise an empty read followed by `D` and child exit, plus STOP/completion ordering, in focused in-memory cases. Implementer and independent reviewer; bounded code/test effort likely short, site validation separately required.

## Limits and remaining gates

A successful audit notification does not establish that freeze actually succeeds, nor does a failed freeze establish quiescence. On read errors the monitor requests freeze; an actual guardian/cgroup outcome needs target-site qualification. The candidate's v2 contract needs the final integrated checkout and fresh end-to-end review with its actual pinned harness and launch configuration; this review does not accept those. The incomplete writer failure path is distinct from the desirable stronger guarantee of perfect operation under arbitrary simultaneous faults. Normal completion still depends on the finalization protocol and handover, and all author, strict no-deletion, test and site gates remain open. No author decision is made or inferred here.
