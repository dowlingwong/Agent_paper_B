# Independent review: M3 child assignment identity guard

**Verdict: NOT ACCEPTED** for candidate `490e981a6761316a019c77e6ff56a87760729ffc`. The test report omits a known pytest cleanup attempt from the reported 81-test invocation. The guard also needs an explicit account of parent-side `os.register_at_fork` callbacks before it can support the stated numeric-PID lifetime conclusion. No tests, kernel probes, host access, model, GPU, process signals or fixture cleanup were performed in this review.

1. **Test evidence and preservation.** The candidate report says the 81 mock tests used a fresh `--basetemp` and `--capture=sys`, but does not disclose pytest's numbered temporary directory `current_symlink.unlink()` path. The command includes the parametrized `test_mocked_supervisor_sequences_listener_before_workload_ack`, whose cases use `tmp_path` (`r1/tests/test_m3_supervisor_component.py:57-59`). The retained `/private/tmp/m3-sigchld-tests-20261107-05` has directories `test_mocked_supervisor_sequenc0` through `...7` and a shared `test_mocked_supervisor_sequenccurrent` symlink. The independently reviewed pytest 9.0.3 source audit `B1_PYTEST_PRESERVATION_STATIC_REVIEW_20261107.md` describes its unlink attempt. A final snapshot is not syscall evidence: it does not establish whether the earlier current symlink was successfully created or removed. The user says never delete anything; preserve the full root and add the precise disclosure, with uncertainty, before any acceptance. Fresh base and `--capture=sys` alone do not avoid this tmp-path behavior. Do not rerun without a separately reviewed safe method.

2. **Fork callbacks and claimed lifetime.** `offline_supervisor.py:127` calls Python `os.fork()` after the guard, then `add_own_child` calls the guard again and identifies a child using a pidfd and `waitid`. Python executes previously registered parent-side `os.register_at_fork` callbacks as part of `os.fork()`; the guard does not inventory or exclude those callbacks. A callback could temporarily change SIGCHLD disposition, reap the forked child, create another child and restore the expected disposition before `add_own_child` checks it. If the numeric PID were reused by that new child, the later `waitid(P_PIDFD)` could confirm a child relationship without proving it is the originally forked child. This is a possible sequence, not an observed event or claim that existing application code registers such callbacks. The report's current assumption of single-threaded, blocked signals and default SIGCHLD alone is insufficient to exclude it. Either establish and enforce a dedicated trusted launcher without such hooks through this interval, or narrow the guarantee explicitly and treat the unproved condition as an M3 STOP with owner and concrete qualification. Add focused mock coverage where feasible without violating the preservation instruction. This point is separate from already disclosed external tracer and hostile same-UID limitations.

3. **ABI and signal scope.** The field layout, syscall number and eight-byte signal set are consistent with the candidate's cited Linux x86-64 kernel UAPI, but this review did not execute or independently qualify that ABI on Linux. The guard refuses unsupported architecture, non-default kernel SIGCHLD, `SA_NOCLDWAIT`, missing masks, multiple enumerated threads, and Python dispositions other than SIG_DFL or SIG_IGN; this is conservative and can STOP under normal CPython's default SIGINT handler. `signal.getsignal()` can also return `None` for dispositions not installed through Python, so a viable dedicated launcher must establish every inspected Python disposition, not just SIGINT, and be reviewed. Reported mock tests do not exercise a real Linux signal action, mask, fork, pidfd, cgroup or PID reuse.

4. **Remaining scope.** The proposed change holds the parent's signal mask through assignment and tries to restore it on success and exceptional exit; the child restores before bootstrap. Under the explicitly bounded assumptions, retaining a waitable child avoids ordinary kernel PID recycling before the write, but that conclusion requires the missing fork-hook premise above. `_kill_and_reap` and the rest of the supervisor, real site capabilities, notification withdrawal/HUP, all-case binding, and M3 replay qualification remain separately unaccepted. Restoration errors intentionally raise STOP; nested cleanup failures may still mask prior errors and need full-supervisor review. This review does not authorize M3 replay or M4.

**Unblock / owner / effort:** implementer updates the report's test-preservation disclosure and establishes a concrete trusted fork-callback boundary or leaves that condition explicitly STOP; an independent reviewer verifies the resulting exact files and evidence. Effort is unknown until launcher and hook constraints are established; site/kernel qualification remains a separate later operator task.
