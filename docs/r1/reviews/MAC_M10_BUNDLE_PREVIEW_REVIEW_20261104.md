## Verdict: accepted only as a local, non-authorizing preview

The function compares exact manifest bytes with a caller-supplied catalogue and supplied catalogue digest, checks one matching manifest entry, preserves argv boundaries in its command hash, compares metadata and refuses duplicate JSON keys and non-finite values. It returns `PREVIEW_ONLY` with `submission_authorized`, `immutability_verified` and `review_authority_verified` all false. It is not connected to the submitter. Independent Python 3.9.6 test (`PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 -m unittest discover -s r1/tests/hk2 -v`) completed **20 tests passed**, including the 5 new preview tests; Slurm calls in tests are mocked.

**Important interpretation limit:** neither the catalogue nor the caller-provided digest is trusted authority. Classification is a consistency comparison, not semantic validation of the actual work. Offline counterexample: a caller can create matching bytes for `phase=HK6`, `kind=engineering`, task `setup` and argv `python3 closed_loop.py`; `preview_match` returns `PREVIEW_ONLY`, with all three authority booleans false. This is consistent with the module's stated scope; it must never be promoted to an authorization check. The preview also does not fully validate job-manifest fields, check runtime dependencies or their immutability, or assert that catalogue task names correctly classify executable behavior. The matching evidence-task-versus-engineering check depends entirely on the supplied task label, and does not itself identify evidence. The prior independently reviewed guard design's trust root, immutable execution closure, author gates and site-specific user-wide accounting/admission remain unresolved.

**Optional test:** add the matching-but-misclassified untrusted catalogue counterexample above so future refactoring cannot imply that a PREVIEW_ONLY match identifies the command's true purpose. This is a documentation-of-limitation test, not evidence that the preview prevents misclassification.

The verdict does not accept M10 as complete, qualify the status tool for HoreKa, enable submission, or satisfy HK1. Any integration into an admission or authorization path requires new design and independent review; tests must retain the unconditional refusal until the broader controls are implemented and accepted.
