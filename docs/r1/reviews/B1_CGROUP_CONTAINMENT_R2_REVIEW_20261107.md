## Earlier findings: progress and remaining blockers

1. **Completion publication remains open in the exact candidate.** `b1_batch.py:71-79` now requires an exact `FINALIZED.json`, which improves the previous unguarded `COMPLETE` check. However the runner writes that receipt after its guardian finishes (`exam_runner.py:559-564`), using an exclusive file that becomes visible before its own `fsync` (`b1_finalization.py:22-40`). If the write yields complete parseable bytes but `fsync` raises, and `STOP.json` cannot be recorded, the standalone verifier has no further receipt or ACTIVE-sentinel check and may accept that state. There is also a normal concurrent window after `FINALIZED.json` becomes visible and before the supervisor publishes the proposed separately supervised receipt. `b1_supervisor.py:63-74,133-144` describes a separate final publication and exception reconciliation, but imports `r1.exam.b1_exit_receipt`, absent from the exact candidate. Its tests substitute a fabricated module (`test_b1_cgroup_pure.py:262-291`). In particular, `b1_batch.py` in this candidate does **not** call that proposed receipt verifier. The candidate's report acknowledges both the missing dependency and the visibility/fsync ambiguity (`B1_CGROUP_CONTAINMENT_CANDIDATE_20261107.md:37,47-55`). Integrating another branch may change this finding, but is not demonstrated by this checkout. A missing, partial, failed, or concurrently invalidated finalization must be rejected by the *actual* batch-verifier entry point; review the exact integrated code, failure semantics, and durable receipt/STOP interaction without inferring success from mocks.

2. **Guardian FINISH and supervisor death still have a handoff window.** The new supervisor holds the same inherited lease and waits for the runner, which can preserve it on an ordinary runner failure while the supervisor remains alive (`b1_supervisor.py:106,118-146`). The guardian now watches both runner and supervisor pidfds and the supervisor STOP channel (`b1_cgroup_guardian.py:74-96`). These are improvements over R1. However, once it receives `FINISH`, the guardian checks the subtree, sends `FINISHED`, and exits without another liveness check (`guardian.py:121-127`). If the supervisor dies just after a successful send, while the runner is finishing, the guardian can already have released its inherited lease; when the runner exits, no holder is assured. This is a source-supported race, not an observed incident. The retained mock `test_finish_refuses_guardian_nonzero_after_ack` establishes only how a mocked nonzero exit is treated; it does not demonstrate post-send supervisor-death behavior. A revised protocol needs a precisely reviewed commit point and a failure/lease-retention rule covering runner and supervisor death and FINISH delivery. Any interpretation that failure after that point is normal completion rather than a runner/guardian STOP needs explicit consistency with the author's §0.4; the current report itself leaves the fault model unresolved.

3. **The server `--help` and several GPU helpers are now routed through containment, but coverage is not complete.** B1 `_build` and `_server` use `capture_b1_helper` for version/help and current GPU checks (`runtime.py:711-718,738-754,799-804,853-860`); this addresses the concrete `--help` omission in R1 on that path. The helper allows fast process exit and the implementation/tests use mocked process and descriptor behavior (`b1_cgroup.py:271-340,372-424`), so actual exec, wait, descendant emptiness and pipe limits remain site-qualified, not proven here. Other direct Git subprocesses remain in the runner's configuration, harness and authorization checks (`runtime.py:168-169,221-256,377-384,531-534`) and the parent process is outside the owned subtree; the report should not be read as proving coverage of *every* spawned process. The direct campaign entry remains separately unbound to the parent/lease/server and inside-tree ownership, as disclosed.
