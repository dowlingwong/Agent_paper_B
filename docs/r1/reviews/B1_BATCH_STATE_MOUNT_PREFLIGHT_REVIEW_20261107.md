# Independent review: B1 state mount preflight

**Verdict: NOT ACCEPTED for the claimed parent/child mount preflight.** Candidate `cfdeb3b` usefully checks the existing work-directory mount before creating the batch directory, but its second check does not establish that the new child is on the same mount as that checked parent. The completion/publication protocol remains separately **NOT ACCEPTED** for the R3 reasons in `B1_BATCH_STATE_PRESERVATION_R3_REVIEW_20261107.md`. No host, kernel, tests, filesystem mutations, model, GPU, experiments, process signals or deletion were performed during this review.

## Finding

`ExamRunner.start` now calls `_require_local_filesystem(self.out.parent)` before `self.out.mkdir`, then `_require_local_filesystem(self.out)` before writing ACTIVE or acquiring the lease. Each call independently verifies that its own path resolves to a directory, that its own `st_dev` matches the most-specific entry in the current `/proc/self/mountinfo`, and that this entry's type is ext4 or xfs. `_require_local_filesystem` returns only the filesystem type; the caller ignores its return. It neither returns nor compares the parent and child's mount IDs, mountpoints or device identities.

The inline comment states that checking the child “also detects a changed/overmounted path.” That is not generally established: if a distinct ext4/xfs mount is placed at the new child before the second check, the child can agree with its own mountinfo entry and pass, despite not being on the filesystem the operator qualified at the parent. A bind mount with matching device numbers creates another reason that device equality alone need not identify one mount. This is a source-supported possible race, not an observed site event; privileged concurrent mount changes and same-UID races are already disclosed as outside the candidate's proven scope. The defect matters if the preflight is represented as binding the eventual batch to an operator-qualified parent mount. A site operator's separate qualification is still required, and no live TASL-7 filesystem has been established here.

To unblock this bounded finding, the implementer should either bind and compare a suitable parent/child mount identity—including distinct mounts on the same device—while honestly specifying residual races and validating against the site qualification, or narrow the code comment and operating contract and provide a separately reviewed check that the **actual batch mount**, rather than merely its parent, is the one qualified. Include a safe mock regression for distinct supported parent/child mounts. Owner: B1 implementer and independent reviewer, then the authorized site operator for actual capability/identity checks. Engineering effort is not established; the site check depends on host availability.

## What this change establishes

On the ordinary intended production B1 path, the first type/device check occurs after author/config checks and before batch `mkdir`; the second check occurs after exclusive `mkdir` and before ACTIVE creation, GPU lease acquisition or worker execution. Therefore an unsupported **parent** is refused before batch output is created. If the child check fails, its newly created directory remains, with no ACTIVE or lease from the subsequent path. The added test mocks `_require_local_filesystem` to fail for the parent and asserts that `mkdir` and sentinel publication are not called. The retained `unittest_r12.txt` reports 35 passes and has SHA-256 `c7a6885422fe0d1aa9963b615becd8d9730cd8b3444b51f208e0b20cc7454398`; I did not rerun it. The test does not model two individually supported but different mounts, actual rename-flag support, directory fsync, process behavior or the site device.

This check, even corrected, would only address a site preflight prerequisite. It does not prove ext4/xfs error semantics, physical device locality, successful `RENAME_NOREPLACE`/`RENAME_EXCHANGE`, exclusion of later mount changes, final ACTIVE publication safety or the absent canonical supervisor and finalization module. The final-rename STOP ambiguity, other JSON/harness deletions and all B1 launch conditions remain open. Do not launch or infer author authorization from this review.
