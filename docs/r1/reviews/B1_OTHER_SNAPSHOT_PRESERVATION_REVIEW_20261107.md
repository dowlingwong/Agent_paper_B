## Blocking findings

1. **The B1 server-record serializer introduces an additional, unrequested STOP.** Previously `LlamaServerInstance._save()` used `json.dumps(self.record, indent=2)` with Python's default `allow_nan=True`. Contained B1 now calls `publish_server_record()` (`r1/scripts/llama_server_instance.py:279–288`), whose common publisher uses `allow_nan=False` (`r1/exam/b1_state_preserve.py:89–107`). `_get_json()` uses Python `json.load()` without a non-finite-value rejection hook (`llama_server_instance.py:211–219`), and a 200 health response is inserted into the record before `_save()` (`:444–462`). A health body containing Python-parsable `NaN` or `Infinity` can therefore be saved before this change but raises `ValueError` on the new B1 path. This is a source-supported input case, **not an observed real server response**, and it concerns server metadata rather than a measured scientific result. No author instruction reviewed here requires this additional gate. It can STOP a batch that otherwise would continue and affects which batches complete. The report discloses the difference but its first paragraph's claim that JSON representations are retained is not universal. Preserve the existing server-record serialization semantics in this preservation-only change, or establish an independently reviewed requirement and document the STOP's unblock, actor and effort. Audit cache already used `allow_nan=False` (`r1/exam/campaign.py:32–37`), so its existing non-finite behavior is unchanged.

2. **A server-record exchange can continue after STOP intent is detected.** `_save()` invokes `b1_containment.write_active(write)` (`llama_server_instance.py:279–288`). `write_active` checks `_stop_requested` and `_frozen` once while holding `_write_lock`, then calls the publisher (`r1/exam/b1_cgroup.py:270–279`). A concurrent monitor can set `_stop_requested` under `_grant_lock` after that check (`:263–268`) while `_publish_named` is writing or before it calls `renameat2` (`r1/exam/b1_state_preserve.py:125–163`). Freeze takes `_write_lock` only later (`b1_cgroup.py:225–227,250–253`), so the callback can write and exchange paths after detection and before the freeze is established. This is a possible source-level interleaving, not an observed real STOP. The audit-cache publisher is in the separate campaign worker and lacks a demonstrated cross-process STOP barrier (`campaign.py:196–203,208–225`), as the candidate report acknowledges. Under the instruction to stop and preserve the scene, jointly review a concrete coordination/failure protocol for both publications; do not treat the presence of `write_active` as proof of no post-STOP writes.

## Verified scope and limits

- On the normal modeled path, `_publish_named` writes a unique `O_EXCL` candidate into the owning directory's `_to_delete`, uses `RENAME_NOREPLACE` for the initial canonical file and `RENAME_EXCHANGE` for subsequent writes, then checks identities and fsyncs both directories (`b1_state_preserve.py:101–164`). This can preserve the previous inode if filesystem, ownership, serialization and same-UID cooperation assumptions hold. It does not establish those assumptions at TASL-7. A failure after an exchange can leave the canonical inode changed while `cache_identity` or `b1_record_identity` is stale; close/fsync errors can also mask earlier failures. Preserve both names and keep the phase stopped for independent review; no automatic retry is authorized.

The source change keeps that name and, for ordinary finite inputs, uses the same JSON formatting. The server retains its canonical `llama_server_<port>[_r<generation>].json` path (`llama_server_instance.py:245–251,279–288`) and the ordinary B1 runner installs the containment object before the first `_save` (`runtime.py:755–759` and `llama_server_instance.py:358–402`). Stage A and paths without a containment object continue through the prior server writer; this is not proof that an alternate direct worker is authorized.
