## STOP versus terminal completion remains inconsistent

The proposed semantic is that successful `RENAME_NOREPLACE` of ACTIVE is the terminal success point (`r1/exam/b1_exit_receipt.py:146–152,177–181`), and failures before that point are STOP. This is a reasonable candidate for defining normal completion, but the implementation does not reliably enforce the distinction. For example, after rename has actually succeeded, an already queued Python exception can escape the `finally` close path, which only catches `OSError` (`b1_exit_receipt.py:182–190`). `_publish_or_reconcile` then verifies the receipt (`b1_supervisor.py:64–75`). If that verification encounters a transient read or other failure, the exception reaches `main`'s STOP handler (`:165–166`). That handler reports STOP and attempts to create `SUPERVISOR_STOP.json` **in the separate supervisor directory** (`:38–47,118–120`); it does not create the batch `STOP.json`. The reader checks only the batch STOP path (`b1_exit_receipt.py:101–104,119–120,236–239` and `b1_batch.py:18–19`), so after transient reads recover, a reader may accept the already-committed receipt even when the supervisor's STOP file was successfully written. This is a concrete source-supported double-failure/exception ordering, not an observed incident; it is distinct from an ordinary pre-commit release failure, which remains refused. The supervisor directory's STOP file is not automatically an author-readable batch gate.

The author requires “On any STOP from the runner, guardian, author gate or anchor gate: stop at once and preserve everything; publish the STATUS; report” (`MAC_OVERNIGHT_PROMPT_20261107.md` §0.4), and normal completion requires lease release, state restoration and the complete-batch verifier. That text does **not** explicitly require the lease remain held after an uncatchable supervisor death or promise perfect operation when storage simultaneously fails. It does require honest STOP reporting and preservation; the source currently can label the same commit STOP while the independent verifier accepts it. A fault model allowing a completed commit to remain terminal despite a subsequent error can be reasonable only if the code and report consistently apply it, and an unresolved commit state is not presented as a normal complete batch.

**Concrete correction:** implementer should make the terminal/ambiguous outcome explicit in the actual supervisor and batch verification contract. Before the commit, any caught error must leave ACTIVE and fail closed. After an independently confirmed commit, catchable post-commit errors must be classified as terminal success or an explicitly separate post-completion operational issue, never create a contradictory STOP. If the commit outcome cannot be confirmed, retain the scene and expose an explicit unverified/STOP disposition that the complete-batch verifier actually consumes, for example via an immutable supervisor-to-batch binding plus a checked STOP/uncertainty record. An inability to persist or read that disposition is an honestly documented storage-failure limit; do not assert it is solved by an ext4 label. Add focused in-memory failure injections covering post-rename queued exception, transient reconciliation failure, STOP write success/failure, and subsequent reader outcome. The implementer and fresh independent reviewer own this work; bounded effort depends on the chosen contract (a few focused code/test iterations), followed by operator site checks.

## Lease and site limits

After RELEASED the guardian returns (`b1_cgroup_guardian.py:115–116`), and before ACTIVE retirement the supervisor is the remaining evidenced lease holder. If it dies in this interval, the lease can disappear; ACTIVE remains unless rename happened. The empty-subtree observation narrows this specific risk, but does not prove GPU quiescence, prevent outside work, or retain a lease. Guardian death after FINISHED prevents success if the release exchange fails, though guardian and supervisor concurrent death still has no surviving watcher. These are real lifecycle limits; the quoted §0.4 does not by itself establish a requirement for impossible lease retention after every uncatchable last-holder death. The implementer and reviewer should state the supported crash/operational behavior and ensure an operator has a concrete inspection/recovery procedure; site operator must separately verify actual socket, pidfd, OFD, cgroup, filesystem and handover behavior. Time is site-dependent.

The final rename is not followed by directory fsync, and `_require_local_filesystem` expressly cannot establish physical locality, I/O error atomicity, or crash durability (`b1_exit_receipt.py:47–52,146–152,177–181`). A failure after an effective rename combined with inability to verify and inability to persist uncertainty remains outside the demonstrated guarantee. Full protection against arbitrarily simultaneous storage failures is a stronger guarantee than the author explicitly specified; the limitation must not be presented as resolved or as evidence of a completed batch. The independent complete-checkout review, real-worker determinism, fixed-harness deletion, author gate, handover and all other B1 launch conditions remain separate and incomplete.
