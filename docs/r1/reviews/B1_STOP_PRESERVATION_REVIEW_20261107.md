# Independent review: B1 STOP preservation candidate

**Verdict: NOT ACCEPTED for B1 STOP enforcement.** Reviewed candidate `bb86931d013e318de6acf4bcb8f81899168510a9` against its parent `262ef62f`; this review is static and did not run tests, contact a host, start a process or model, use a GPU, or delete files. The candidate improves specific exception-unwind behavior, but does not establish that a live B1 campaign stops producing work when a STOP is detected, or that STOP status survives a storage failure. It must not be used as evidence of launch readiness.

## Blocking findings

1. **A live campaign can continue after its supervisor records STOP.** In `r1/exam/runtime.py:644-665`, a lost disk/GPU margin, watchdog failure, deadline or other supervision exception reaches the production-B1 exception handler; the changed condition leaves `self.child` alive. The parent records the interruption and rethrows, and `r1/scripts/exam_runner.py:540-548` records STOPPED and preserves the server. A live root worker can therefore keep executing its campaign and model calls and writing its output after the runner has stopped. There is no demonstrated stop or quiescence channel to the child and its descendants. The user's 7 November prompt §0.4 requires “stop at once and preserve everything” for runner/guardian/author/anchor STOPs; retaining an active process alone does not show that this requirement is met. This is a code-path risk, not a claim that a real B1 STOP occurred. A reviewed bounded approach must establish how active work becomes quiescent without damaging the scene, including descendant processes, outstanding requests and lease lifetime. A mock that merely asserts no `stop_tree` call (`test_exam_b1_stop_preserve_20261107.py:10-32`) does not establish quiescence.

2. **A server may spawn after the disk watcher detects STOP.** The watcher appends to `disk_error` at `r1/exam/runtime.py:581-586`. `r1/scripts/llama_server_instance.py:345-362` checks the callback, performs additional operations, then calls `Popen`; the append can occur between the check and spawn. The readiness loop eventually checks again (`:410-412`), but does not undo a spawn. Likewise, a STOP arriving during the health request may be observed only after that request returns, and a success path can perform record/lease work before control returns to the caller (`:423-441`). The two synthetic cancellation tests only return true before spawn or at the first readiness check; they do not exercise this interleaving. A fix needs a reviewed synchronization/ownership protocol with meaningful tests of the concurrent transition; a bounded in-flight network timeout must be stated accurately.

3. **STOP record persistence is not established when disk writes fail.** `run_job` appends an interruption then calls `self.save()` in its exception handler (`runtime.py:660-665`); `main` updates STOPPED and calls `runner.save()` if a lock exists (`exam_runner.py:540-547`). If a disk-full or I/O condition also makes those writes fail, the save can mask the triggering error and there is no demonstrated durable STOP state or published STATUS. The user explicitly requires STATUS publication; the candidate has no test for a failing save or fallback reporting. Preserve the original error in a separate available channel and specify an independently reviewed publication/owner procedure, including the failure case. Do not treat a proposed fallback as proof that a damaged filesystem is writable.

## Scope and evidence

The changed exception paths avoid explicit `stop_tree` on the production B1 child and avoid normal `stop_service`/lock cleanup when the main runner catches a production B1 exception. The server start receives `preserve_on_failure=True` and a disk-error callback. These observations are useful but limited: the callback does not coordinate with external guardian STOPs; no real process lifecycle, signal, GPU descriptor inheritance, shared-host ownership, or lease persistence after runner exit was tested. The author forbids retry or alteration of an actual STOP scene. No such scene was created in this review.

The author-specified no-deletion rule remains independently unresolved: normal completion still calls `self.lock.unlink` (`runtime.py:732-733`), and the candidate report identifies the exactly pinned harness's guard deletion/truncation and conditional editable-file removal. This review does not approve a harness change or infer an exception. The author gate and approved-note ordering are separate unresolved prerequisites.

The candidate reports six mock-only tests in unique temporary paths; this review inspected their source but did not rerun them. Their use of fake `Popen`, fake child, mocked health response, and mocked `save` is appropriate for bounded control-flow tests; it cannot establish external process quiescence, concurrent guardian coordination, fault-tolerant STATUS publication or the absence of all indirect deletes. Review fixes and the exact final integrated HEAD independently before any host preflight or B1 launch.
