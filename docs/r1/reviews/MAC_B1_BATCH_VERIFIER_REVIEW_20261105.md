## Findings

1. **Candidate manifests can switch the verified registry.** `r1/exam/b1_batch.py:37–40` checks the batch snapshot against configured registry, but `:63–71` does not bind each manifest's `registry_path` and `registry_sha256` to that snapshot. `r1/exam/analyze.py:146–153` reopens the manifest-supplied registry and uses its family, policy and ordering. In independent synthetic probe `/private/tmp/b1_batch_registry_probe_20261105.py`, the second manifest pointed at a different self-consistent registry with a changed family; `b1_summary_verified` returned that forged family. Family affects the absent-family finalist rule. Bind each manifest to the verified snapshot and digest before analysis, with negative fixtures.
2. **Recorded D28 is not derived from verified ledger bytes.** `b1_batch.py:104,108–110` requires a node key and compares the candidate flag against root claims, but never computes D28 from `root_trials.jsonl`. The passing synthetic fixture in `r1/tests/test_exam_b1_batch_verify.py:35–44` has an empty trial ledger yet marks D28 pass for every root; the liveness evaluator in `r1/liveness/check.py:158–182` would not find a node in an empty ledger. Recompute the node verdict from the verified records, with the correct manager and memory mode, and reject discrepancies including absent nodes.
3. **Reported audited values can disagree with their hashed source.** `b1_batch.py:93–101,106–107` verifies evidence-file hashes and only compares the candidate's list to the root's list; it does not connect the root audit entries to `audit_cache.json`, the hashed config texts, or replayed proposals. In `/private/tmp/b1_batch_audit_probe_20261105.py`, root/candidate metadata reported `[0.9]*4` while the hashed cache for the same candidate hash contained `[0.0]*4`; the verified summary accepted μ̂ 0.9 and selected that candidate. `r1/exam/campaign.py:150–182` shows the actual provenance: replay, config hashes, paired cache, and observer forecast events. Reconstruct proposal identity and audits from the ledger, pinned starting files, audited config texts and cache, and bind the forecast fields to the relevant event. Candidate diagnostic and descriptive D28 summaries also need checking against the roots before they are presented as evidence.
4. **Anchor discrimination is not established.** `b1_batch.py:45–55` includes whatever Stage A pass rows are supplied but does not demand all three anchors; it does not inspect or recompute `state['anchor_gate']` or verify the selected duplicate-reference source/interval. The passing fixture supplies only two candidate rows, no anchors, and no anchor gate. `r1/scripts/exam_runner.py:213–224,354–355` requires the scripted/random discrimination and 7B pilot duplicate interval before candidate work. Require all three anchors and re-evaluate the recorded discrimination and reference against the verified anchor outputs; incomplete, malformed or failing inputs must STOP. The true pilot source and author selection remain separate open prerequisites.
5. **Input containment is incomplete.** `b1_batch.py:33–34,56,86–101` confines a root manifest but opens `batch_state.json`, `b1_manifests.json`, root jobs, certificates and evidence files without checking their resolved targets stay within the batch/root. The existing `runtime.verify_campaign` likewise dereferences evidence paths. An external symlink can make supposedly self-contained evidence depend on an outside file, including a preserved path, before any rejection. Reject escaping lexical/resolved paths before opening each batch or root constituent; exercise symlinks to outside locations.
6. **Original harness bytes are not proven for faithful replay.** The production runner in `r1/exam/runtime.py` checks harness `HEAD` against the configured pin, but does not check that checkout is clean; `r1/exam/campaign.py:125–132` copies live node files and uses their contents as the replay start state without recording their initial hashes. A dirty checkout can therefore share the expected commit while executing changed harness/node bytes. The verifier cannot retroactively infer the bytes used from the commit alone. Check the pinned harness before collection, bind the exact initial editable source bytes into each production job/root, and verify those bindings before replay. This is a content-provenance check, not a new signing/trust-root requirement.
7. **Eligible and budget metadata need consistency checks.** The derived expected set includes only Stage A passes, but `b1_batch.py:63–71` does not require the candidate manifest's `stage_a_pass` and `stage_a_pass_source` to match that set. Nor does it check the hashed job's actual settings or root budget against authorized W/call-cap (`campaign.py:143–146`); the passing fixture lacks root compute-budget data. A false stage flag can silently remove an otherwise eligible candidate from `choose_finalists`, and anomalous over-budget roots are not independently identified. Validate fields against the bound configuration and independently check the reported counts against available event/ledger accounting.
