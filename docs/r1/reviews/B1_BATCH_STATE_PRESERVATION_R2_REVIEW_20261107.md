# Independent review: B1 batch-state preservation, round 2

**Verdict: NOT ACCEPTED for B1 integration or as a working fail-closed completion path.** Candidate `21b128f` blocks automatic reuse of an existing production batch and adds a waited-exit receipt, addressing parts of the R1 false-resume and false-completion scenario under its cooperative assumptions. A receipt publication failure can nevertheless leave a valid-looking receipt that the verifier accepts after the publisher reported an error. The intended finalization verifier and canonical supervisor are not present in this branch, so no normal success path is currently implemented. No actual runner, wait, rename, filesystem mutation, test, host, model, GPU, experiment, process signal, or deletion was performed in this review.

## Blocking: receipt fsync failure can still look like success

`b1_state_preserve.write_exclusive_json` creates `B1_EXIT_RECEIPT.json` with `O_EXCL`, writes the complete JSON, then calls `fsync(fd)` and later `fsync(directory)`. If either fsync raises after the bytes were written, `publish_waited_success` and `publish_after_wait` raise and do not return a success result. Nevertheless the complete receipt name and bytes can already be visible. The candidate report correctly acknowledges this visibility/durability ambiguity; its implication is stronger than a mere storage-site qualification: in the absence of a separately durable `STOP.json`, `verify_waited_success` reads those bytes, checks their schema, state/active/finalization hashes and absence of `STOP.json`, and may accept them. `b1_batch.verify_batch` then continues with a canonical `COMPLETE` state. Thus an error during receipt publication can be treated as a successfully finalized batch after the error was reported. No proof of actual post-error STOP publication is present in this branch, and a `STOP.json` write can itself fail under the same filesystem fault. The current tests mock `write_exclusive_json` and do not cover a fully visible receipt followed by file or directory fsync failure and subsequent verifier invocation.

This is a source-level possible interleaving, not an observed B1 event. It conflicts with the author's §0.4 instruction to stop and preserve on any STOP, and prevents the R1 false-success issue from being considered closed. An implementer must supply an independently reviewable error/publication protocol that makes a failed receipt writer distinguishable from a genuinely successful one to every later verifier, including visible complete bytes after failed fsync, crash and failure of STOP publication. A durable outside observer or a different audited ordering may be needed; no particular architecture is mandated by this review. Add meaningful regression coverage against the actual coordinator, runner and verifier, not only a stubbed return. Site filesystem durability and error behavior must also be qualified. Owner: B1 implementer and fresh reviewer, then authorized site operator; effort and site capability are not established.

## Working-path and authority limits

The current branch contains `publish_after_wait`, which calls `child.wait()`, but no production caller invokes it. Its tests use a `SimpleNamespace` with a lambda `wait`, so the results do not establish a real `subprocess.Popen` wait, process identity, wrapper exit handling, or durable receipt. The separately public `publish_waited_success(batch, head, pid, wait_result)` also accepts a caller-supplied integer zero and does not itself wait; the report explicitly relies on a cooperative canonical supervisor. Even after this function is wired, same-UID code can fabricate inputs or call it directly; a reviewed supervisor identity and lifecycle are necessary for the intended evidence claim. This is a process/trust limitation, not evidence of an observed forged receipt.

`_verified_finalization` imports `r1.exam.b1_finalization`, which does not exist in this checkout; both receipt publication and verification fail closed without it. Its future implementation, guardian/lease behavior, no-delete cleanup, direct worker identity and integrated exact HEAD are separately unreviewed. A missing module and an unwired supervisor currently make every legitimate B1 verifier call refuse; this is not a completed implementation. The user requested concrete B1-path unblocks: implement and independently review the actual supervisor and finalization protocol, resolve the receipt-failure condition above, then perform the authorized site qualification; the person responsible is the B1 implementer/reviewer and the TASL-7 operator for site checks. Effort remains unknown.

## Scope of the corrections

The production runner now creates a new batch direct child with `mkdir(exist_ok=False)` and does not automatically resume any existing batch, including a non-STOP crash. That stops the specific R1 automatic-resume route on the intended runner entry. It is a behavior restriction and does not establish a general parent/worker identity or resolve concurrent same-UID races. Its active sentinel is written before work, but absence of the sentinel cannot prove success.

For a cooperating, genuinely waited runner returning nonzero, the receipt code refuses to publish success even when canonical `batch_state.json` says COMPLETE. For a zero result it checks active identity, state, STOP absence and finalization, then hashes their bytes into an exclusive receipt; the verifier rechecks them. This is bounded source analysis, not proof of the promised real wait, process ownership, atomicity or durability. Other B1 JSON replacements, fixed-harness guard deletion/truncation, runner lock cleanup, asynchronous STOP and GPU work remain outside this unit.
