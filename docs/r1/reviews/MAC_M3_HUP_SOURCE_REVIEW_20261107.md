## Evidence and assessment

1. The report correctly labels normal final-exit HUP as an inference, and does not establish target-kernel behavior. `r1/c3/offline_supervisor.py:140–145` currently treats listener HUP as STOP; a normal-HUP STOP is a potential availability issue, not proof that any actual site execution has failed.
2. The v6.6 source at lines 1026–1029 and 1032–1112 establishes an interruptible pre-receipt wait, cleanup of the queued notification on interruption, and that `WAIT_KILLABLE_RECV`'s killable wait applies only after the notification reaches SENT. The [upstream seccomp documentation](https://github.com/torvalds/linux/blob/master/Documentation/userspace-api/seccomp_filter.rst) independently describes withdrawal before receipt. This supports the report's inference that bare HUP plus an empty queue cannot prove all attempts were observed. The documentation link is to a moving branch; the version-specific conclusion rests on v6.6 source. The path is a source-level possibility, not a demonstrated reproducer under the full candidate or target host. In particular, this review did not establish signal delivery, scheduling or actual workload behavior at the site. The candidate x86-64 filter defaults unlisted syscalls to ALLOW (`r1/c3/offline_seccomp.py:36–81`), so the report does not establish that it excludes all signal sources either.
3. The reviewed design requires durable observation and STOP for each prohibited attempt, including swallowed errors (`docs/r1/proposals/C3_REPLAY_OFFLINE_BOUNDARY_DESIGN_20261104.md:7,21,39`). A successful child status and empty cgroup do not themselves supply that evidence. The candidate can return only `COMPLETE_UNQUALIFIED` (`r1/c3/offline_supervisor.py:146–153`); this is explicitly not a production pass. Treating a bare HUP as success would therefore be premature. This is an evidence gap and a requirement-driven STOP, not a claim that site failure has been measured.
