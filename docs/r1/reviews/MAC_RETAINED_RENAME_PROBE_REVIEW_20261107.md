The script's ctypes signature and flag values match those declarations. The header does not prove the actual filesystem implements the flags or settles all error/crash behavior.
- The script opens `/private/tmp` with `O_DIRECTORY|O_NOFOLLOW`, compares its opened/named device and inode, exclusively creates a new root, and validates owner, mode, same device, and opened/named identity for that root and its newly created `_to_delete` directory (lines 13–43). A read-only local observation during this review found `/private/tmp` root-owned and sticky (`drwxrwxrwt`), `/private` root-owned, and 549241856 KiB available on `/System/Volumes/Data`; this is a point-in-time observation, not an ongoing guarantee. The code does not independently check parent UID/sticky bit or pin all ancestors for the lifetime of the operation. The operator must freshly inspect them and assume cooperative same-UID actors and stable paths; the sandbox and OS permissions do not exclude an actor with the same UID or sufficient privilege.
- Both files are created with `O_CREAT|O_EXCL|O_NOFOLLOW` and fsynced, then their bytes, owner, single link and inode are checked. Under Darwin's stated rename semantics, the `RENAME_EXCL` existing-target check refuses the collision; the subsequent EXCL move and SWAP exchange work across owned directory descriptors and leave both contents at `b` and `_to_delete/c`. The script checks identities and bytes after each stage. It performs no intentional unlink, truncation of an existing file, destructive cleanup, signal or model/GPU operation. An unexpected kernel/API violation, same-UID path race or independent actor is outside this source-level guarantee; do not claim no effect from arbitrary failures.
