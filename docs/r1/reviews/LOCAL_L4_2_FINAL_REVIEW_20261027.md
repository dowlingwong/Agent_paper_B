## Findings

1. **Blocking — partition isolation is not enforced in the environment.** All positive-weight train, val and test rows are appended to the same episode population (`r1/c3/env.py:120–138`); sequential/random reset can select any of them (`r1/c3/env.py:162–171`), and `evaluate_policy` iterates the whole population (`r1/c3/env.py:257–268`). Executing a test episode returns utility derived from `z_eval` (`r1/c3/env.py:233–245`), while Track P forbids evaluation-seed quantities in training and model selection (`docs/r1/TRACK_P_POST_TRAINING.md:115–117`). A synthetic mixed-table fixture exposed episode splits `train, test, val` and returned test reward −0.031; constructing from test rows alone failed because fitting A1 requires train rows (`r1/c3/env.py:139–141`). Thus a normal training loop over the environment can consume test rewards, and there is no separate test-only population with a training-fitted reference. The split is visible in `info`, so an external caller could filter, but no enforced caller or integration establishes that separation. This is an exposed pathway, not evidence that a real training run leaked.

2. **Blocking — rule-on execute does not suppress no-ops.** The adopted rule layer skips both no-ops and duplicates (`r1/c3/arms.py:60–69`), but the amended step checks only duplicates (`r1/c3/env.py:225–230`). In a synthetic no-op with zero increment and `rule_layer=True`, action 0 returned `execute=True` and reward −0.001 instead of the rule skip and zero reward. A no-op without a `z_train`/`z_eval` vector also fails upon execution (`r1/c3/env.py:236–239`), although legacy assembly gives no-ops an exact zero increment (`r1/c3/offline_eval.py:155–157`). The fixture only covers duplicates (`r1/tests/test_c3_h8_amendment.py:102–108`).

3. **Reset failure can retain the previous belief against a new row.** The new row is assigned and the `info` dictionary is constructed before belief state is cleared and before the guarded block (`r1/c3/env.py:171–190`). In a two-row synthetic fixture, the second row lacked `delta_hat`; reset raised `KeyError`, but `_current` was the second row and `_belief` remained from the first. `step(1)` then accepted the failed-reset row. This is distinct from the covered provider-exception path (`r1/tests/test_c3_h8_amendment.py:84–99`). Clear/commit state atomically for all fallible reset operations, including observation construction, and test failures before and after the provider.
