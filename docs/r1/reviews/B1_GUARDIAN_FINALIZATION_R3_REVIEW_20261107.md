The revision closes the specific revision-2 example **when the in-batch marker is successfully created before a reader checks**. `r1/scripts/b1_supervisor.py:75–96` catches errors from `publish_after_wait`, attempts reconciliation, and writes `B1_COMMIT_UNCERTAIN.json` exclusively if reconciliation fails. `r1/exam/b1_exit_receipt.py:218–225,228–252` rejects that path before and after its receipt verification; an existing partial file or symlink also refuses, and an lstat permission error propagates. Thus after successful uncertainty creation the batch reader will refuse this path, even though the separate supervisor STOP record remains unbound. A verified post-publication callback within `_publish_or_reconcile` is treated as terminal success. This is a bounded source finding, not an acceptance of the overall completion path or real filesystem behavior.

**Remaining blocking source interleaving: a supervisor can still report STOP after verified publication without any reader-visible disposition.** The handler in `_publish_or_reconcile` covers only exceptions thrown by `publish_after_wait` (`b1_supervisor.py:76–96`). Once that function returns, `_release_then_publish` returns to `main` (`:99–111,181–185`), but `main` still wraps the return boundary in a broad `except BaseException` (`:186–187`). A previously queued Python exception or other catchable exception at that boundary reaches `_retain_on_stop`, which writes `SUPERVISOR_STOP.json` only in the separate supervisor directory (`:38–50`). The receipt reader checks the batch `STOP.json`, ACTIVE and the uncertainty path, but does not read the supervisor STOP (`b1_exit_receipt.py:228–252`). Thus the same published receipt can be accepted even though the supervisor has reported STOP. This is the same kind of source-supported queued-callback ordering that motivated the R2 fix, but it occurs *after* the new handler's scope. It is not an observed run failure and is not an assertion that ordinary successful execution triggers it.

**Reader overlap is also unguarded.** ACTIVE is retired atomically before publication returns (`b1_exit_receipt.py:180–182,207–209`). If a post-rename error is followed by failed reconciliation, an independent `verify_waited_success` can finish both uncertainty checks before the supervisor creates the marker (`b1_supervisor.py:78–86`), accepting the receipt; the supervisor can then create the marker and report STOP. The two lstat checks do not serialize publication and reading. `verify_batch` invokes this check once near its beginning (`r1/exam/b1_batch.py:74–81`) and can continue after a later marker appears. The candidate report acknowledges this window; source review confirms it. An ordinary overlapping reader and a queued callback with a transient reconciliation failure are sufficient for this ordering; no simultaneous failure to write the marker is required. The author requires STOP preservation and reporting and a complete-batch verifier; that does not explicitly require perfect guarantees under all concurrent storage failures, but it does require a coherent acceptance/STOP contract for the supported reader workflow. Neither B2 nor any downstream phase is authorized here, so this is a potential path, not a claim of actual downstream use.

**Concrete unblocking work:** the implementer should cover the entire supervisor return/exception boundary with a terminal/ambiguous disposition that the actual reader consumes, not just the `publish_after_wait` call. Define the reader's allowed timing and enforce it in the reader: e.g., a reviewed per-batch supervisor-liveness/serialization protocol that refuses or waits while publication can still be classified STOP, with a terminal outcome bound to the batch. An alternative is acceptable if it proves the same coherent behavior under the explicitly supported fault model. Add pure failure-ordering checks for an exception after `_publish_or_reconcile` returns and for a reader overlapping post-rename reconciliation, including the full `verify_batch` entry rather than only the helper. The implementer and fresh independent reviewer own these corrections; effort is a few focused implementation/review iterations plus site-dependent qualification, not an author decision. The site operator must later verify the chosen locking/filesystem behavior without deleting probe files.

**Documented limits:** if an effective commit is followed by failed verification and uncertainty creation itself fails, the current tests deliberately show a reader may later accept (`r1/tests/test_b1_publication_uncertainty_unittest.py:56–67`). The implementer discloses this as NOT CHECKABLE. An ext4 label, mocked rename or these checks do not establish crash durability or resolve arbitrary simultaneous storage failures; treating all such failures as covered would be a stronger, unsupported guarantee. The last lease can be lost if the remaining supervisor dies after guardian release and before publication; §0.4 does not expressly require a lease to survive the death of every holder. These limits still need an operational inspection/STOP procedure, not a claim of readiness. Other launch prerequisites and the pinned-harness no-deletion conflict remain independent STOPs.
