The actual full batch entry calls `verify_waited_success` (`r1/exam/b1_batch.py:74–81`). The supervisor exclusively creates and flocks that path before it starts guardian release or success publication, and holds the descriptor through the return or its retained STOP (`r1/scripts/b1_supervisor.py:110–120,212–224`). Before creation/lock acquisition, ACTIVE has not been retired by this publisher; after lock acquisition, cooperating readers of the same inode refuse until it is released. The unlocked validator used for supervisor reconciliation avoids self-conflict. This addresses the specific R3 reader-overlap window under ordinary local flock behavior, stable path identity and cooperative writers; the source and mock test do not establish those properties on TASL-7, resist an uncooperative same-UID pathname replacement, or cover copied batches. The held lock spans receipt validation rather than all subsequent `verify_batch` computation; the conclusion depends on the supervisor having exited or remaining retained and no later cooperative publisher mutating the committed outcome.

The supervisor outer exception handler now calls `_finish_or_stop`: after publication can have begun, it either independently validates the already committed receipt and returns terminal success, or creates a batch-visible uncertainty marker before retaining STOP (`b1_supervisor.py:69–107,138–141,220–224`). The public reader refuses the marker before and after receipt validation (`b1_exit_receipt.py:221–228,255–279`). This closes the specific exception after `_publish_or_reconcile` returns and before the protected `try` exits, when marker persistence or the held supervisor lock is available. The earlier revision's ordinary RELEASE/ack failure still precedes success publication.

**Remaining actionable boundary:** `main` executes its `finally` block *after* the `return 0` and outside the `except BaseException` (`b1_supervisor.py:219–231`). Although individual `os.close` and `log.close` calls are guarded, a queued Python callback can raise between those guarded operations, for example during iteration before entering the inner `try`. That can override the success return and make the supervisor exit nonzero after the terminal receipt is committed, without running `_finish_or_stop`. This is a post-commit exit/operational ambiguity, not proof of a written STOP or an observed failure; a cooperative reader can subsequently see a valid receipt. The current report's statement that a confirmed commit is terminal is a plausible contract, but it does not document or test how the operator distinguishes this nonzero exit from a precommit STOP, or ensure an explicit uncertainty disposition when the exit is reported as STOP. **Unblock:** implementer must either prevent an exception escaping the entire post-commit return/finally boundary, or explicitly define and implement the operator's terminal-success-versus-STOP handling using a reviewed, observable committed receipt; add a focused injection at that boundary and independent review. This is a narrow continuation of the existing exception contract, not a demand for arbitrary failures to be recoverable. Effort: one focused implementation/review cycle; actual host qualification remains site-dependent.

**Limits and remaining steps:** the lock depends on cooperative use and site flock behavior. A supervisor killed after an ambiguous commit while no uncertainty/STOP marker can be persisted can release its lock and leave a receipt that a later reader accepts; this combined-failure limit is explicitly NOT CHECKABLE, not resolved by the mock tests. The final rename lacks a post-rename directory fsync, and lease loss if the last holder dies after guardian release remains possible. The author has not required a lease to survive every uncatchable death or perfect results under simultaneous storage failure. The complete operator sequence also requires Track S/P restoration before the complete-batch verifier; this patch enforces only the publication/supervisor timing, not that handover sequence. No final checkout, no-deletion harness, live guardian/worker/server binding, actual site or B1 launch is accepted here.
