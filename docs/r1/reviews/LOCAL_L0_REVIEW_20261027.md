## Initial findings (review of `f0e224d`)

1. **Start commit is inconsistent with the retained timestamps.** The report says tests started at `ad90149` (`docs/r1/reports/LOCAL_BASELINE_20261027.md:7`). The paper JUnit's suite timestamp is `2026-10-26T23:49:10.886379+01:00`, while `git show -s --format=%cI ad90149` gives `2026-10-26T23:49:52+01:00`. The suite therefore started approximately 41 seconds before the commit was created, on the same reported clock. The intervening commit only adds the CPU exception to PLAN; `git diff 8ba81b68..ad90149 -- r1 Makefile` is empty, so this does not establish that the tested code differed. The working-tree content and whether the author clarification was already in place at launch cannot be inferred from the commit timestamp. Correct the provenance using contemporaneous evidence, or explicitly mark the start state as unknown; do not assert the commit as the launch HEAD without supporting evidence.

2. **Exact invocations and enforcement settings are not independently recoverable from the committed record.** The report asserts the sandbox variables, offline cache, 590-second timeout, collection-error continuation and deselection (`LOCAL_BASELINE_20261027.md:10-11`). The paper log shows only the expanded `python -m pytest -q -p no:cacheprovider r1/tests` command; the harness logs show no command line. Neither log records `PYTEST_ADDOPTS`, the complete environment, exit status, the cache location, or the executable's version. The JUnit and package list corroborate outcome counts and availability of `pytest-timeout`, not that the options were set. The report identifies the deselected test (`local_baseline_20261026/paper-ids.md`, “Deselected before execution”), but not the exact selector. Record the actual complete invocations and relevant non-secret environment settings with their evidence or label unverified details as operator-reported; explicitly distinguish configured timeout from proof of runtime compliance. This is needed for a comparable rerun, not a request to rerun these suites.

3. **Regeneration is not byte-identical even after decompression; preserve as an unresolved test finding.** The paper log records failure of `r1/tests/test_trackp_exam_synthetic.py::test_committed_set_matches_its_hash_and_regenerates_byte_identically` at the regeneration assertion, after the committed-file hash check passed (`paper-tests.log.gz`, failure detail; test source `r1/tests/test_trackp_exam_synthetic.py:31-35`). Using the existing Python 3.13.4 environment and generating in memory only, I reproduced the failure: committed compressed SHA-256 `4f4db29b6a4c0ca0181825e5c2c0fb031521e034a006990b93686cd5fffc8290`; regenerated `47b85f05c1f4f8184b560640fbb98472ee834e0f3048bf585fd65797adf6eca6`. Decompressed SHA-256 values were respectively `ed8a26058daaa8fe2e8871f3804be88d6876cb53e44db76bc235e75ff7722cad` and `f19ab6f1620b7151a7c7794ebb27becf656f76d40655be4eb2f43132e80abc9b`: 1 of 4,000 JSONL records differs, `e0-train-01601`, in `y_hard` (one-hot index 3 versus 2). This is a content difference, not merely a gzip-header or compressor difference; the cause is not established. A separate pilot-table byte-identity test also failed (`paper-tests.log.gz`; `r1/tests/test_trackp_soft_label_v2.py:72-79`). The baseline correctly lists both as failures; future reports should not describe regeneration as byte-identical or assume an environmental cause without further evidence. These failures do not by themselves invalidate an accurately recorded failing baseline.
