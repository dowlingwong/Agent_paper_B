## 1. Checks performed

### (a) Pilot dimension and spec derivation

`make_specs` derives two S2-C2 specs from the reviewed `spec.example.json` through the **accepted validator**
(`lib.validate_spec`): one node (`digits_mlp`), `instances = 2`, one spec per memory mode
(`append_only_summary`, `none`), per-mode `chunk_id = <node>-<mode>-pilot`, the run id from the CLI, ENGINEERING
label (no authorization), the frozen v1 gpu digest and the B2 harness pin inherited from the base spec. It creates
a fresh output dir (refuses an existing one) and writes the two specs + `pilot_specs.json`. The operator submits
them through the accepted S2-C2 renderer (`render_jdl.py --stage-dir …`) and the reviewed JDL, so the same
pins/class/transfer rules apply. **Matches the runbook's "1 node × 2 instances × both modes"** — 2 jobs, 4 root
campaigns. ✓ (minor: `make_specs` does not re-validate the derived specs itself — the renderer validates at stage
time, so an invalid derivation would STOP there; fail-fast in `make_specs` would be nicer.)

### (b) Extrapolation

`layout()`: `pilot_wall = max(wall over the two chunks)`; `full_wall = pilot_wall × (18/2) = ×9`;
`chunks = 8 nodes × 2 modes = 16`; `total_gpu_hours = full_wall × 16 / 3600`; proposed
`+RequestWalltime = min(86400, max(3600, round(full_wall × 1.3)))`; `request_disk = 50,000,000` kB;
`request_memory = 128,000` MB; `proposed_chunking = one (node, mode) chunk per job`. This is a **conservative
upper bound**: it scales the pilot's fixed per-job costs (GGUF fetch, server start/load) by 9 as well, and it uses
the slower mode's wall for all 16 chunks. That is safe for a walltime proposal (the ~30 % margin sits on top of an
already-inflated base); a decomposition (`fixed = fetch + load + start` from the record, `per_instance = (pilot −
fixed)/2`, `full = fixed + 18 × per_instance`) would be more accurate and is worth adding to the report. Three
points to note in the unit/report:
- the pilot's single node (`digits_mlp`) is extrapolated to **all 8 nodes**; the nodes' campaign costs differ, so
  the estimate assumes the pilot node is representative (or conservative). State that assumption, or pick the
  pilot node deliberately (e.g., the node expected to be the most expensive) before submitting.
- the walltime clamp: if `full_wall × 1.3 > 86400`, the proposal silently becomes 86400 s (too short for an
  18-instance chunk) — add a check that then splits the chunk (fewer instances per job) instead of clamping.
- the sweep fetches the 19.6 GB GGUF **once per job** (16 chunks ≈ 314 GB from HF); note the repeated fetch time
  and the HF egress/429 risk in the report (the pilot measures one fetch).
The measured `request_disk`/`request_memory` are **not** in the pilot: the proposal just repeats the S2-C2
defaults (50 M / 128 G), which are safe but not measured. The S2-C4's purpose includes fixing the layout, so parse
the HTCondor user log's event 006 (`ImageSize`/`MemoryUsage`, the chain's I3/S5 evidence pattern) or fetch the job
ad after completion and pin the measured peaks; the job record has no disk/memory usage field.

### (c) Timing collection and the no-label rule

`collect_chunk` reads, from the transferred chunk directory (the stage dir): `job_record.json` (no labels; label
must be `ENGINEERING_ONLY` — non-ENGINEERING records are refused), the HTCondor user log (`s2_c2_job.log`; 000/001/
005 events → queue wait = execute − submit, wall = terminate − execute), `llama-server.log` (CUDA0 model/KV buffer
sizes), and the record's model download seconds, collector seconds, offloaded/total layers, host/GPU. It writes
`timing.json` + `S2_C4_TIMING.md`. The core reading is sound and label-free. Caveats:
- the **mode fallback reads `out/manifest.json`** (the campaign manifest) when the record has no `collector_mode`.
  That manifest is metadata rather than raw labels, but it lives under `out/` where the labels are, and the mode is
  available without it: the record's `collector.argv` contains `--memory-mode …`, and the `chunk_id` itself
  (`<node>-<mode>-pilot`) encodes the mode. For a strict "no labels read" claim, use one of those and do not open
  anything under `out/`/`work/`.
- a **missing `job_record.json` raises an uncaught `FileNotFoundError`** (traceback) instead of a clean STOP; wrap
  it as a `lib.Stop`.
- the log timestamp parse hardcodes 2026 (fine for this run; NIT), and the llama buffer regexes should be checked
  against the actual v1 log wording (the I3 v3 evidence; if they miss, the buffers are silently omitted — for a
  pilot whose purpose is the GPU-memory record, a missing buffer should at least be a warning).
- the pilot's `out/`/`work/` (which contain the raw labels) are transferred to the submit host; the collect must
  not read them (the manifest fallback aside), and the unit doc should say whether the pilot chunks are run
  through the S2-C2 seal step (they are ENGINEERING_ONLY, so sealing is for the record, not evidence).

### (d) Small-chunk-first rule and STOPs

The first ENGINEERING run is the 2-instance pilot (not an 18-instance/7200 s guess), so a misestimated
walltime/memory/disk cannot hold or kill a long job — this follows the accepted S2-C2 r4 guidance and is the right
order. The S2-C2 STOPs apply to the two jobs (image/host/GPU/CPU/model/server/offload/resume, pre-created transfer
outputs, deadline = walltime − 600). The C4 collect STOPs: existing spec dir, non-ENGINEERING record, missing user
log, inconsistent timestamps, empty timing set — plus the missing-record STOP above and the walltime-cap/chunk-split
check. That is sufficient for a pilot, provided the no-label strictness and the measured disk/memory are folded in.

## 2. Findings

### BLOCKING / MAJOR

None. The unit is a small, sound helper for a 2-instance ENGINEERING pilot that runs through the accepted,
already-reviewed S2-C2 path.

### MINOR

1. **M1 — the mode fallback reads `out/manifest.json`.** Use the `job_record.json`'s `collector.argv`
   (`--memory-mode`) or the `chunk_id` instead, so the "no labels read" claim is strict (nothing under
   `out/`/`work/` is opened).
2. **M2 — disk/memory are proposed from the S2-C2 defaults, not measured.** Parse the HTCondor user log's event
   006 (`ImageSize`/`MemoryUsage`) or the job ad after the pilot and pin the measured `request_disk`/
   `request_memory` in the layout (the S2-C4 purpose includes fixing the layout; the defaults are safe but should
   be confirmed).
3. **M3 — node/extrapolation assumption and walltime cap.** State that the single-node (`digits_mlp`) pilot is
   extrapolated to all 8 nodes (or choose the pilot node deliberately); and if `full_wall × 1.3 > 86400` the
   proposal must split the chunk rather than clamp the walltime to 86400.
4. **M4 — missing-record STOP.** Wrap the `job_record.json` read in a `lib.Stop` ("missing chunk record") instead
   of a traceback; also note the repeated per-chunk GGUF fetch (16 × 19.6 GB) and its HF egress/time in the report.
5. **M5 — pilot node/mode coverage.** Both memory modes are covered; the single node is the base spec's
   `digits_mlp` — document why it is representative (or switch to the worst-case node) so the full-sweep estimate
   is defensible.

### NIT

- `make_specs` could validate the derived specs itself (the renderer validates at stage time).
- The `parse_condor_log` year is hardcoded to 2026 (fine now).
- The llama model/KV buffer regexes should be checked against the v1 log wording; a missing buffer is silently
  omitted — warn for a pilot.
- The unit doc's "27 tests total" matches the suite (23 + 4); mention the S2-C2 round-3 test additions explicitly.
