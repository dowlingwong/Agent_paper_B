- **Publication:** R1-T1-NODE-EXPANSION lets the coordinating chat publish this note and its spec once they are
  independently reviewed and their launch checks pass, without a further author decision. The check
  (`g1b_tasl.py check-note-x`) reads the `publication_row` line and no signer line; `launch` also checks that the row
  on published `main` says so. To publish: complete P2 and P4 (below), copy the note to
  `docs/r1/authorizations/g1b_x_t1_tasl_<YYYYMMDD>.md` with a date no other G.1b note uses, set `approved: true`, run
  `python sweep2/t1_tasl/g1b_tasl.py check-note-x sweep2/t1_tasl/g1b_tasl_x_spec.json --note <note> --draft` on the
  unsigned copy and then the strict check on the published note, and publish it byte-identically on `main`.
- **Per-node gates:** a node launches only when its `gate_<node>` line reads PASS and cites what the spec requires
  for it (`check_gate_x`, at every launch): `host check <report under docs/r1/reports/> sha256 <64 hex>` — the TASL-2
  harness-isolation host check at that node's own harness pin, with the lines `host_check_host: TASL-2`,

  sentence "venv_jax is admitted as the census environment of mlgym_metamaze for its G.1b on TASL-2"); for ETTh1 and
  Forest Cover also `review docs/r1/reviews/G1B_EXPANSION_REVIEW_20261126.md` (this unit's review record on `main`,
  with exactly one line `spec_sha256: <this spec's sha256>`, exactly one line `verdict: ACCEPTED` and exactly one line
  `cpu_census_disposition: <node> ACCEPTED`: the review accepts the CPU census as the census of a CPU G.1b, in place
  of the GPU census their kit reviews asked for in c2/c4, on the conditions of the `cpu_census_conditions` line); for
  Titanic and Forest Cover also `determinism check <the record its determinism_check line names> sha256 <64 hex>`
  (R1-TASL2-CPU: the replacement set's fixed-seed determinism check, on `main`, with the lines that line lists). A
  PENDING gate keeps that node from launching; it does not keep the note from being published. A gate completed
  later is published in a later note with the same spec and run (a new file name, the other lines unchanged), and
  that later note is itself independently reviewed before it is published.
- **The engine and the CPU-only list:** `mlgym_titanic` is in the harness's `CPU_ONLY_NODES` at its pin. The other
  three are not, at their pins (their kits change no harness source), so the job starts the harness engine with that
  node added to `autoresearch.trackg.noise_floor.CPU_ONLY_NODES` in the engine's own process, for its own chunk only
  (`census_override`; `X_ENGINE_OVERRIDE` in `g1b_tasl.py`). Their U2 census drivers did the same to the smoke's
  copy of the list (`tests.trackg.port_smoke_gpu.CPU_ONLY_NODES`). No harness file changes; the checkout stays at its
  pin and clean.
- **Launch:** from a published checkout of the launch commit (or a docs-only descendant) holding this spec
  (`verify_launch_tasl`), on TASL-2, one node per call:
  `sweep2/t1_tasl/t1_tasl_node.sh g1b sweep2/t1_tasl/g1b_tasl_x_spec.json <node> <note> --enable` with
  `G1B_TASL_ENABLE_REAL=1`. Before the first job: one harness checkout per node at its pin (paths on the node lines;
  `git worktree add <dir> <pin>` from a separate clone of the harness repository, not Track P's, branches pushed by
  the kits), clean apart from the `data` link the job's setup writes; the host check at each pin; and, for Titanic and
  Forest Cover, the determinism check of the replacement set (the gates; prep report section 9).
- **Schedule (fits 2 Dec 2026):** the four CPU sets (0-3, 4-7, 12-15, 16-31) are disjoint and none contains 8-11, so
  on TASL-2 each node starts as soon as its own gate is PASS and all four can run at the same time; Titanic (12-15)
  is the longest. Latest starts at the sensitivity ratio 1.5 are on the `latest_starts` line.
- **CPU sets and G.5:** R1-G5-EXPANSION-JOIN gives the expansion G.1b jobs precedence on the TASL cards only, not on
  CPU sets, and the G.5 jobs take no CPU lease (the G.5 spec on `main` uses TASL-2 cpus 0-7 for the GPU worker and
  8-15 for CPU audits; its audits are being moved off 8-15 in a parallel G.5 amendment). So every expansion job samples
  its CPU set (`cpu_preflight`) before the attempt and before each part, and refuses if another job is using it.
  Keeping G.5's TASL-2 CPUs disjoint from the four expansion sets while those nodes run is for the G.5 schedule (the
  prep report, section 5, gives the recommendation).
- **On a STOP:** the outputs are kept and nothing is deleted. An infrastructure STOP may be followed by a new attempt
  of the node; a node or timing STOP ends the node (the author's). No node runs on cpus 8-11, so the earlier
  two-attempt rule for that set is dropped. A node whose G.1b has not completed with determinism PASS by the cutoff
  goes to the appendix (T2).
