## 1. What the code must establish

For each actual submission, the tool must bind the planned work, the reviewed command, the applicable author decisions and any evidence authorization to the exact bytes that run; establish the outstanding and allocated GPU-hour totals for all of this user's relevant jobs; apply the runbook's conservative used + full outstanding reservations + new job rule, 90-job and dev-QoS limits, F/C and STOP state; then durably reconcile the outcome. The runbook queries the user (`squeue -u`, `sacct -u`), including unrelated jobs and the queue probe; a proposed control covering an entire account may be more conservative and can include multiple users. Actual user, account and QoS limit scopes must be verified with the site. These are separate claims. A manifest's self-declared `kind`, `production`, phase, path, process name or digest alone does not establish the work's category or authorization. A local file lock cannot govern an author, shell, scheduler continuation, or unrelated tool that ignores it. Two ordinary Slurm queries do not prove a completed job has appeared in accounting.

## 2. Reviewed work identity

A reviewable candidate is a committed, immutable submission bundle, with a stable identifier and:

- manifest bytes and SHA-256; reviewed phase and role; an argv array with no shell evaluation; entrypoint, arguments, environment allowlist and output roots; fixed paper/harness commits and pinned configuration, executable and input digests; and a list of the runtime dependencies whose changes could alter behavior;
- a detached review record that names the precise bundle digest, phase, reviewer verdict and immutable review commit. The author and independent reviewer do not derive authority from a filename or text in the manifest. The controller validates the review record against a trusted, pinned review source. Hash checks before submission and at job start alone are insufficient: the runtime and every behavior-relevant dependency must remain immutable throughout their period of use, with independently verified enforcement, or submission/execution refuses. The boundary includes interpreter, wrappers, dynamic imports and libraries, inputs, symlinks and their resolved targets. A pinned read-only artifact is one proposed mechanism, subject to implementation and site-specific review; a supposedly read-only checkout without enforced immutability is insufficient. A digest binds the review to bytes; it does not establish their semantic category. The precise trust root and commit-verification mechanism require independent review.
- J0 is a bootstrap exception only in the sense that its final environment does not exist before it runs. Its reviewed bootstrap executable, interpreter, build instructions, pinned downloads, verification procedure and all inputs must themselves have an enforced immutable boundary during use; verify downloads against predeclared digests before consumption, and seal and verify outputs before subsequent phases use them. The bootstrap boundary and enforcement must be specified and site-reviewed; if it cannot be established, refuse J0. Do not assume a pre-existing finished runtime.
- an independently verifiable mapping from each reviewed bundle to its allowed phase, permitted partition and production/engineering status, rather than user-supplied labels alone. Refuse unknown bundles, unreviewed commands, edits, mismatched hashes and deviations from that mapping. A review of the bundle must evaluate the actual command and reachable inputs; hashing merely binds that human/agent review to bytes and cannot prove their scientific purpose.
- a separately committed author authorization, byte/hash-bound to the relevant scope, before accepting **any evidence task**: the T1 sweep, its audits and the closed loop, regardless of phase name or J3 template. An independently reviewed mapping must classify all such tasks from the actual reviewed work identity. Engineering J3 and evidence J3 require distinct classifications; a manifest that declares an evidence closed-loop job to be engineering must be refused. Parse the actual authorization format and decision row stipulated by the eventual protocol, not an invented free-form boolean. Evidence remains refused until that format, mapping and reader are specified and reviewed. The submission row R1-HOREKA-AGENT-SUBMIT and J3 confirmation alone do not authorize evidence.
- PLAN §10 `R1-HOREKA-J3-CONFIRM` at `3ecb718` records the author's "确认涵盖 J3"; the recorder's proposed consequence includes J3's local proposer loop under the submission ruling pending NHR@KIT's answer. A restrictive NHR reply triggers STOP. This does not authorize a run or waive the independent-review, budget, resource and phase/evidence authorization gates; the bundle still needs a reviewable J3 classification.

The runbook does not currently define the review registry, command identity schema, or transitive dependency closure. The above is a design to review, not an existing authorization or a claim that a new registry has been adopted.

## 3. User-wide serialization and ledger completeness

### Strong control (preferred if the site can provide it)

A proposed site-enforced admission authority must cover **every** submission route for the user, including author terminal calls, other agents/tools and batch continuations, and reject bypasses. A wider account-level control is only a conservative proposal and may encompass multiple users. Admission must serialize the check and the actual submission atomically relative to all relevant submissions. It must return a durable, authoritative job identity or a reconcilable idempotency key. For every admission it must supply a complete user-wide snapshot of pending/running allocations and all elapsed GPU usage since campaign start with a documented consistency/watermark guarantee; the job limit, dev QoS and budget are evaluated against the same admission state, with actual site-specific scopes separately verified. Confirm feasibility, policy enforcement, failure semantics, existing jobs/arrays/requeues and accounting behavior with NHR@KIT/Slurm administrators. A proposed client-side lock alone does not meet this condition. The site may be unable to provide the gateway or watermark; this is not an asserted existing capability.

### Operational control (only if independently substantiated)

An alternative is a formally reviewed, author-adopted single-submitter procedure that covers *all* relevant routes of this user and establishes how nonparticipating submissions are technically prevented, not merely requested to cooperate. Before opening each admission, it must reconcile the complete set of this user's relevant jobs since campaign start (including jobs submitted before the tool existed), retain an authoritative user-wide enumeration and demonstrate a site-supported accounting completeness watermark or another auditable bound covering all completion/accounting races. A recorded assertion that no other session is submitting, an advisory lock, and a matching local submissions log cannot prove those properties. If the site cannot offer a completeness guarantee, known job sets alone can prove only the status of previously observed jobs, not absence of unseen jobs. Under this alternative, any inability to establish completeness, exclusive admission or an unchanged governing procedure leaves real submission disabled.

The current status tool and `sacct -u`/`squeue -u` interface can help collect observations; neither can manufacture a guarantee the site has not provided. Independent submissions during `test-only` or before accounting catches up invalidate the snapshot. Never call an unverified zero a measured zero. A conservative full allocation reservation for an unknown job is usable only when its count and maximum resources are themselves authoritatively bounded; inventing such a bound is unsafe. Slurm arrays, requeues, job-ID reuse, elapsed fields and typed GRES/TRES are verified against actual site behavior before a parser is accepted.

### Facts needed, not assumed

1. Whether site enforcement can require one admission path for every relevant submission by this user and cover continuation and author submissions; whether Slurm can atomically enforce the 90-job and dev constraints for the verified user/account/QoS scopes.
2. Exact `squeue` and `sacct` output/semantics on this account, retained history, timestamps, arrays/requeues, accounting lag and whether a trustworthy completeness watermark exists.
3. How this user's pre-existing jobs, the queue probe, unrelated personal jobs and submissions from other tools are inventoried and covered by the budget since the campaign start, and whether wider account-level counts add other users.
4. F/C/D, campaign start, T_max and budget decisions that are still proposed/open in the existing config; a site-local clock/time-zone check. These remain proposals unless the author records a decision.
5. NHR@KIT's response remains pending. `R1-HOREKA-J3-CONFIRM` records the author's J3 confirmation; it is not an NHR answer. A restriction on agent submission or batch-job LLM loops triggers the existing STOP.

## 4. Durable outcome reconciliation

Before admission, durably persist the bundle digest, an externally meaningful unique submission id, the conservative reservation and PREPARED state; fsync the file and its directory. The authority must associate the unique id with the actual Slurm job so that a timeout, connection loss or crash can be resolved by querying the authoritative system. After `sbatch`, durably store the returned job id and submit output. On an ambiguous result keep an UNRESOLVED marker and its full reserved cost and job slot, refuse *all* further admission, and reconcile through the authority. Do not retry merely because an immediate queue query returns no job; delayed registration and accounting must be bounded by the site-supported reconciliation protocol. Move retired markers into `_to_delete/`, never delete evidence. Atomic file replacement must fsync both the file and the relevant directory; a crash at any boundary must leave either a complete state or a refusal.

The current local marker blocks this tool's next submission, but is not a user-wide reservation, idempotency mechanism or proof that a job was not created. No safe automatic reset is defined. Manual handling needs the author/operator and the independently reviewed site-specific procedure; this draft neither authorizes one nor invents a resolution.
