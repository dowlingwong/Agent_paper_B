## 1. Scope and invariants

- **G1**: one campaign runner for every D.3a/b arm, on the T0 seven-node set (§2): `digits_mlp`,
  `openml_breast_w`, `openml_climate`, `openml_credit_approval`, `openml_ionosphere`, `openml_sonar`, `tabular_mlp`;
  `openml_wdbc` excluded. One GPU model for both stages, a model with a measured D.3 chunk time. The H200 is **not** a
  prerequisite (PLAN R1-D3-ORDER): it is currently absent, so launch binds the measured pool model of the reviewed
  note; a model change is an author item, not a G1 assumption.
- **G6**: the Y audit and its budget curve Y(w), w = 5, 10, 15, 20, over campaign **incumbent snapshots**, with the
  pre-declared audit seeds 6701–6880, K = 10, on deepthought CPUs under §7.2.
- **Primary outcome is the final incumbent at the campaign's actual final charged-run count**, not Y(20) when a
  campaign ends early. Y(5), Y(10), Y(15), Y(20) are descriptive budget-curve points (PLAN R1-D3-OUTCOMES2); they are
  not substituted for the primary Y and are not tested.
- No test/evaluation label, no T1 label, no use of a D.3 output to train/tune/select an arm. No resume, ever.
- Inputs pinned by sha256: D.3 pre-declaration draft and its constants file; `r1/c3/d3_analysis.py`,
  `r1/c3/audit.py`, the harness at `a3fedbbd…` (or the reviewed FIXR3/EGATE pin), image digest, model file sha,
  server flags, noise source `3d12ce05…`, host config. A pin mismatch is a pre-launch STOP.

## 2. G1 campaign execution (per §2/§4/§12)

### 2.1 Unit and layout
- **One HTCondor job per `(stage, node, arm, repetition)` chunk**, as sweep 2: a chunk holds the 18 instances
  `node__s6201…s6218`; one GPU, CPUs for workers, 16 workers; no per-instance job. The GPU model must be one with a
  measured D.3 chunk time (R1-D3-MIN; PLAN R1-D3-ORDER); the H200 is currently absent, so launch uses the measured
  pool model of the reviewed note, not a model substitution chosen here.
- Ledger root per `(stage, arm, repetition)`:
  `<run_root>/<stage>/<arm>/r<rep>/<instance_id>/` (this carries the harness `*_pending.json` guard). The harness
  `campaign_id` is the **instance id** (D26 seed rule); arm/repetition are not encoded in it. Record name:
  `<stage>__<arm>__<instance_id>__r<rep>`.
- Output directory is new and checked absent before launch; a STOP writes a manifest and keeps the scene; a killed
  chunk is rerun whole in a **new** directory with the old one moved aside and disclosed (sweep-2 rule).
- Per chunk files: `chunk.json` (pins, image, model sha, server flags, host, walltime, status), `campaigns/<id>/`
  with `campaign.json`, `ledger.jsonl`, `runs.jsonl`, `snapshots/w{5,10,15,20}.json`, `summary.json`,
  `SHA256SUMS` over the tree; a chunk-level `SHA256SUMS`.

### 2.2 Campaign loop
- Budgets: `c3_budgets(W=20, LLM_CAP=80)` for **every** arm (A0 too); replicate and verify runs count against W and
  every proposal/revision/controller call against the LLM cap. Enforce both before each action; report `ended_on` with the §3.3
  enum (`worker_runs` / `llm_call_cap` / `no_fundable_candidate` / `stop` / `error`) and precedence.
- Instance seeds: train seed = split seed = instance seed 6201–6218. Replicate runs j use 6500 + 10·i + j
  (6501–6679); every configuration in a campaign sees the same seed list, so incumbent runs are reusable. The
  controller API distinguishes `(candidate, seed j)` from `(incumbent, seed j)` and charges both.
- Controllers per arm: A0 default; A1/A2 existing `RuleController`/`TableArmPrior` with σ_cmp and r = 2;
  FIXR3/EGATE with their replicate rules (EGATE `PaceStyleGate` max_pairs 8); LADDER; learned A3/A5/A6 adapters.
  Each controller is constructed from the pinned constants file; a missing constant is a pre-launch STOP.
- **Charged-run counter (G8/accounting).** `w` is the number of **charged worker runs** spent by the campaign:
  every executed trial run, every replicate run (candidate and incumbent), and every verify run: verify has r = 2
  pairs, so `2r = 4` charged runs per verify
  counts exactly once; an LLM call counts against the LLM cap but not against `w`; a skip/no-op charges no run.
  The same counter is the campaign's W=20 budget; a failed run that consumed a worker run is charged once (it is not
  re-run). Reuse of an incumbent run already paid in the campaign does not charge twice.
- **Snapshot contract (G6's input):** a **per-charged-run hook** writes `snapshots/w<w>.json` immediately after the
  run that brings the charged count to exactly w, for w ∈ {5,10,15,20}; the snapshot is live (not reconstructed),
  taken before the controller decision triggered by that run, and contains:
  `{schema, stage, arm, node, repetition, instance_id, w, w_actual=w, incumbent_config (the last kept config before
    this run's decision), start_config, last_kept_trial_index, worker_runs=w, llm_calls, ended, config_sha256,
    controller_state_sha256, pending_action (if w falls inside a multi-run action), timestamp_utc}`.
  `controller_state_sha256` covers the serialised controller state **after** the run and before its decision, so a
  snapshot can be replayed against the same controller state. A snapshot is written even when no trial was kept up
  to w (incumbent = start). The hook charges exactly one run at a time: there are no block charges. A verify
  contributes `2r = 4` separate charged runs, each with its own hook and w increment; no action can make w cross a
  boundary in one charge, so the exact w points are always recorded. `pending_action` names the action in flight. Writes are atomic (`tmp` + rename); no later mutation.
  If a campaign ends before 20, write `snapshots/final.json` at its actual `w_final` with `final: true`; do not invent
  w points.
- The runner never reads the audit; it only emits snapshots. It refuses to start if a snapshot would overwrite.

### 2.3 Preflight and STOPs
- Pins (§1), image/model/server flags, harness commit clean at the expected pin, node edit sets equal to the declared
  E1 sets, seeds inside §4 blocks, namespace check, output/scratch absent, 16 workers, core co-tenancy rule for the
  audit host, no test labels. Any difference is a pre-launch STOP with no output directory.
- During campaigns: the §10 STOP list applies (pin/server mismatch, thinking >1 %, parse failures >0.2, worker
  failure rate >12.99 %, campaign over W/cap, seed outside blocks, chunk walltime, killed/non-clean chunk, any test
  read). A STOP stops submitting, lets in-flight runs finish, writes the manifest with reason, exits 3; no contrast
  is computed from a partial design.
- Engineering smoke per arm: `openml_climate`, instance seeds 6301–6302, every arm (12 campaigns), replicate seeds
  6311–6319/6321–6329; outputs set walltimes **and the compute projection** (PD:120), never enter an outcome table, never audited.
- Verify-seed disjointness (harness `vary` rule) is recorded by the G1 implementer and checked by a separate
  reviewed check outside `d3_analysis.py`, as §4.1 requires; result enters the pre-declaration before review.

## 3. G6 Y and Y(w) audit

### 3.1 Outcome
For an incumbent configuration `c` at snapshot w, the audit runs `c` and the start configuration `c0` on the
instance's K = 10 audit seeds (6701–6880; audit seed k of instance i = 6700 + 10i + k), train seed = split seed =
audit seed, as `r1/c3/audit.py` runs B.2 audits; Δ oriented as the C3 audit.
`y_raw(w) = (1/10) Σ_k [m(c, a_k) − m(c0, a_k)]`; if `c == c0`, `y_raw(w) = 0` by rule and no audit runs.
`Y(w) = y_raw(w) / σ_node` (σ_node PROPOSED as §7.1).

**MAJOR 1 fix — primary Y.** The primary outcome is **Y_final = Y(w_final)**, the final incumbent at the campaign's
actual final charged-run count, exactly as PD §7.1 defines Y (final incumbent over start). `Y_final = Y(20)` when the
campaign reaches w=20; an arm that ends early for a **normal reason** — all-skip A1 (Y=0), LLM-cap end, or
`no_fundable_candidate` — still contributes its final row, with `w_final < 20` and `ended_on` recorded. No instance is
dropped for lacking w=20; no Y(20) is imputed. A campaign that ends on a **STOP or error** does **not** contribute
Y_final and is not in the outcome table: per PD §10 a STOP stops the stage and no outcome table is built from a
partial design; per the pinned analysis only complete campaigns are read. The stage-wide STOP handling is in §2.3. **Y(5), Y(10), Y(15), Y(20)** are descriptive snapshots for the
R1-D3-OUTCOMES2 budget curve only: they are reported per arm/node/w, are never substituted for the primary Y, are
not tested, and do not enter the primary contrasts. A missing w point is `missing_w` and is not imputed.
- **Cache:** keys `(node, config_sha256, audit_seed)` and `(node, c0, audit_seed)`, shared across arms, repetitions
  and w points; a cached run is reused only if its record sha matches; cache hits are disclosed in the manifest.
- Audit conditions: deepthought CPUs only; 16 workers; ≥10 of 40 cores free (co-tenancy sampled); e1 replay
  environment basis; Python 3.13.15/sklearn 1.8.0/NumPy 2.4.4/pandas 3.0.3/SciPy 1.17.1 and `uv.lock dd42d018…`;
  harness/node/config/worker/audited-library paths equal the campaign pin, checked at start; host difference
  disclosed (audit Python 3.13.15 vs v1 image 3.13.18).
- **New G6 record:** `audit/<stage>/<arm>/r<rep>/w<w>/<instance_id>.json` with the 10 seed runs, per-seed Δ, y_raw,
  σ_node, Y, cache flags, run sha256s; `audit/Y_final.jsonl` (primary) and `audit/Y_w.jsonl` (descriptive) one row per
  (stage, arm, node, repetition, instance, w) for the analysis;
  `audit/SHA256SUMS`; no audit value enters any campaign run or controller.
- Run one audit job per chunk's snapshots? PROPOSED: G6 audit jobs are separate HTCondor CPU chunks (deepthought
  direct, no GPU) after campaign seal, one per stage/arm/repetition, 16 workers; they read only sealed snapshots and
  the node/config code. A failed or non-finite seed run is a STOP, never retried; completion record included.
- If an arm/campaign has no snapshot at w (ended early), the row is `missing_w`; Y for that w is not imputed. The
  primary analysis uses every campaign's Y_final (126 instances per arm; no w=20 completeness filter); Y(w) curves
  show missing points explicitly. A campaign ending before w=5 contributes Y_final but no Y(5), Y(10), Y(15), Y(20).

### 3.2 Analysis interface
**Data path (MAJOR 3 fix).** The primary Y_final is routed **G1 → G6 → G7 outcome-table builder → the pinned
`d3_analysis.py`**, which reads the `r1_d3_outcome/v1` table exactly as it does now; `d3_analysis.py` is not changed
to read `summary.json`/`Y_final.jsonl` directly. G6 writes its audit rows and the G7 builder emits one complete
`r1_d3_outcome/v1` row per **(stage, arm, node, instance)** with the final `y_raw`, σ_node and Y, plus the campaign's
`ended_on`, worker runs and LLM calls; only the existing G7 builder (a reviewed unit) touches that schema. The
unchanged pinned `d3_analysis.py` then computes the §7.3 t/Holm/bootstrap contrasts (exact tests are not claimed;
§7.3 is the authority) and refuses a partial design, a seed outside the blocks, a snapshot/config mismatch, a
test-label read, or a table without the pre-declaration sha.
`Y(w)` is **not** in the signed PD §7 and is not yet authorized as code: before any Y(w) code, either the PD's
§7/§8 gain the Y(w) text/schema/missingness rule and the script is re-pinned, or the author declares Y(w) as a
separate descriptive unit (own script/sha) under PLAN R1-D3-OUTCOMES2. Until then Y(w) exists in this design only as
the G6 snapshot contract; no analysis code reads it.

**MAJOR 3 (single statement).** PD §7 declares only Y(final); Y(w) is required by PLAN R1-D3-OUTCOMES2 and must be
written into the PD before any D.3 run (or declared as a separate reviewed descriptive unit with its own script/sha).
This design does not treat Y(w) as part of §7.3 and no code writes Y(w) until settled; the primary family is unchanged.

## 3.3 Fixed settings and remaining review items (revision 3)

- **G1 fixed settings (from PD §2):** memory mode `append_only_summary`; proposal schema `manager_proposal/v1`,
  temperature 0.2 with D26; server `-c 32768 -ngl 999 -np 1 --jinja`, chat-template kwargs
  `{"enable_thinking":false}`, q8_0 K/V, `cache_prompt` false; skip display `one_line/v1`; run price g = 0.1 σ_node;
  noise source sha `3d12ce05…`; harness pin `a3fedbbd…` unless a reviewed FIXR3/EGATE change names a new pin; image
  and model sha from PD §2; the G1 hook executes inside that pinned harness/runner and increments `w` by exactly 1
  per charged worker run (no block charge; a verify's `2r` is two separate charged runs). If a controller or harness
  can only charge a block, code stops for an author decision.
- **Smoke:** runs the 2-instance/arm engineering smoke; records walltimes **and the compute projection** (PD:120),
  not only walltimes; never an outcome; the smoke's measured chunk time sets the 1.5× walltime. The P10 verify-seed
  check is re-run at the launch commit; a difference is a STOP.
- **Preflight/STOP additions:** all §10 items — constants-file sha, arms-frozen per-node A1/A2 constants, pinned
  `d3_analysis.py`/tests sha and test pass, stage-note preconditions, image/model/server flags, `cache_prompt` and
  thinking flag, A5/A6 fallback rate (>1 %), no evaluation/T1 label read, measured-GPU chunk time/1.5× walltime and
  P7 projection ≤140 GPU-h; a killed or non-clean chunk is recovered whole in a new directory and disclosed (this is
  recovery, not a STOP class); a STOP class stops submitting new chunks, in-flight chunks finish, and no outcome table
  is built from the partial stage.
- **G7 row path:** the G7 builder emits one `r1_d3_outcome/v1` row per `(stage, arm, node, instance, repetition)`;
  repetition is explicit (1 by default; an optional rep 2 stays an author item). G6 writes the audit, G7 the row.
- **Audit no-label rule:** G6 calls only the audit core with an explicit, reviewed no-label configuration; it must
  not open a label/evaluation block (testable by a file-open guard); an accidental read is a STOP.
- **G6 compute:** four w snapshots per campaign can be ≈3.6–7× the §11 single-audit estimate; G6 reports its CPU
  projection (4 × audit work, cache-aware) before launch and reports it against PD §11's estimate; no fixed allowance
  threshold exists, so an overrun is disclosed, not silently accepted.
- **Cache:** key `(node, config_sha256, audit_seed)` for both the incumbent and the start config (c0 by
  config_sha256, not by symbol) and provenance = the run record sha; a hit is reused only if the source record and
  config sha still match; cache hits are listed per row. A missing provenance is a STOP.
- **Rows/arms:** PLAN rows R1-D3-DECOMP (A0R) and R1-D3B-UNCONDITIONAL are put into PD revision 4 by R1-D3-ORDER
  step (2); they are author items, not yet PD text. G1 does not implement a row that changes the arm set until the PD
  is revised and re-pinned.
- **`ended_on`:** enum `worker_runs`, `llm_call_cap`, `no_fundable_candidate` (normal, eligible for Y_final);
  `stop`, `error` (not eligible); precedence if simultaneous: `stop` > `error` > `llm_call_cap` >
  `no_fundable_candidate` > `worker_runs`.
- **Y_final and Y(20):** when `w_final = 20` they are the same audit; G6 writes one canonical audit row and both
  references point at it (`Y_w` at w=20 is a reference to the same run records, no duplicate audit). For w_final=0
  (A1 with no kept trial, or an immediate normal end), Y_final=0 by rule, no audit runs, and `snapshots/final.json`
  at w=0 is the canonical record; an audit path is written only for w>0.
- **Final-at-actual-w audit:** the primary `Y_final` audit reads `snapshots/final.json` (present for every normal
  campaign) and audits its incumbent at w_final, not necessarily 20; `Y_w.jsonl` is descriptive only.
