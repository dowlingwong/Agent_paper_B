\section{Experimental Design}
\label{sec:setup}

Details are in Appendix~\ref{app:design}, and every departure from an earlier plan is listed in Appendix~\ref{app:deviations}.

\subsection{Nodes, logged sweeps and audits}
\label{sec:setup-data}

\paragraph{Tier T0: controlled CPU nodes.}
T0 has eight CPU training nodes: two multilayer-perceptron tasks (digits, and a synthetic tabular task) and six OpenML classification tasks \citep{vanschoren2013openml}: breast-w, ionosphere, wdbc, credit-approval, sonar and climate-model-simulation-crashes. On T0 a proposal changes a single configuration parameter. Every decision can then be audited cheaply. The primary analysis uses seven nodes; the eighth, \texttt{openml\_wdbc}, missed one liveness criterion and is a pre-declared sensitivity row.

\paragraph{Tier T1: GPU nodes.}
T1 takes task assets from three public suites and runs them as nodes of our own loop: autoresearch \citep{autoresearchloop}, MLGym \citep{mlgym2025} and MLAgentBench \citep{mlagentbench}. On T1 a proposal is a code-level diff. Eight T1 nodes are prepared, and four further candidates are screened. A node enters by passing a fixed-seed determinism check, not by a noise threshold and not by a date (Appendix~\ref{app:nodes}). T1 enters the offline gate and a descriptive closed loop. \TOneNodesUsed

\paragraph{Logged sweeps.}
A \emph{sweep} runs the default loop with a language-model manager and logs every proposal. Two T0 sweeps use the same eight nodes and the same 18 instance seeds per node, with a budget of $W=20$ worker runs per campaign. Sweep~2 is the main source. Its proposer was selected by an exam under a rule frozen before the selection data existed (Appendix~\ref{app:exam}). Sweep~1 used a smaller manager and is the second source. T1 label runs use the main proposer, with 12 instances per node.

\paragraph{Audits.}
From each logged campaign we replay the proposals against their incumbents. Every proposal that is neither a duplicate nor a no-op is audited: candidate and incumbent are retrained on $K=10$ common fresh seeds that were not used to generate, filter or select the proposal. Five seeds form the \emph{label block}, which gives the training label, and five the \emph{evaluation block}, against which decisions are scored; the two roles never mix. Instances, not trials, are split into training, development and test. Access is staged: arms are trained, selected and calibrated on the label blocks of training and development instances; an \emph{arms-frozen record} then fixes every arm, split and gate file by hash; only after it are test labels and evaluation values released.

\subsection{The closed loop}
\label{sec:setup-closed}

The closed loop answers the headline question. Arms control fresh campaigns with the main proposer on the seven primary T0 nodes, with the append-only summary memory, one repetition, and \LoopInstances{} new instances per node that occur in no sweep and no split file. All arms run on the same instances and seeds, so contrasts are paired. Every arm has the same budget of $W=\LoopW$ worker runs, against which replicate runs count, and the same cap of \LoopCalls{} manager calls. A skipped proposal is charged no worker run, and the manager is asked again. Arms are therefore matched on the budget, not on realised use: an arm that skips can issue more manager calls, up to the common cap, and Table~\ref{tab:closed} reports the runs and calls that each arm used. The outcome is $Y$ of Section~\ref{sec:problem}: the final incumbent's audited improvement over the start configuration, measured on $K=\LoopAuditK$ fresh seeds outside the campaign budget, in units of $\sigma_{\mathrm{node}}$. One pre-declaration, committed with its hash before any closed-loop run, fixes the nodes, instances, seeds, budgets, contrasts and analysis script. \TBD{Citation and hash of the signed pre-declaration; check every design value of this subsection against it.}

\paragraph{Rule arms and the decomposition.}
Seven rule arms run: A0, A0R, A1, A2 and the three reference rules of Table~\ref{tab:arms}. The first four form a two-by-two design. Two contrasts read it:
\begin{itemize}
\item A0R $-$ A0: what the rule layer adds under the default keep rule;
\item A2 $-$ A0R: what the one-step rule adds once the rule layer is in place.
\end{itemize}
The noise-aware part of the question rests on A2 $-$ A0R and A1 $-$ A0; A2 $-$ A0 alone does not separate it from de-duplication. The remaining contrasts of this family are each rule arm against A0, and the margin rule against A2. The constants of A1 and A2 are fitted on the development label block of sweep~2 and pinned before the first run. No arm of this family reads a test label or an evaluation value, so these campaigns do not wait for the gate.

\paragraph{Learned arms.}
A3 and A5 run exactly as frozen in the arms-frozen record, on the same instances and seeds. They run whether or not the offline gate passes. The contrasts are A3 and A5 against A2 and against A0, and A5 against A3. Contrasts are tested two-sided, with a Holm step-down at family-wise level 0.05 within each family. \TBD{Multiplicity of the enlarged families, from the signed pre-declaration.}

\paragraph{Secondary outcomes and reference rows.}
Declared before any run, and descriptive: the budget curve $Y(w)$ at $w=5,10,15,20$, compute per campaign, runs-to-match against A0, mechanism counts, the agreement between each arm's offline utility and its closed-loop outcome, and the learned arms by tier. Two classical configuration methods, random search with de-duplication and SMAC3 \citep{lindauer2022smac}, replace the manager on the same instances as reference rows. On three T1 nodes, A0, A2, A3 and A5 run a descriptive closed loop on new instances. The reference rows and the T1 loop are optional: they enter if they are complete and reviewed when the required parts are (Appendix~\ref{app:closed}).

\subsection{The preregistered offline gate}
\label{sec:setup-gate}

The gate tests the one-step claim: on logged proposals, a learned per-proposal forecast improves one-step decisions against A2. Its analysis was preregistered and frozen before any test label or evaluation value was released, and it is unchanged (Appendix~\ref{app:gate}).

The quantity is the offline one-step utility $U$ of Section~\ref{sec:problem} at the run price $g=0.1\,\sigma_{\mathrm{node}}$. Decisions use forecasts built from label blocks only, and values come from the evaluation block. An \emph{oracle} applies the same rule to a forecast built from the proposal's own label block. Per node, the \emph{gap closed} by an arm is $(U_{\mathrm{arm}}-U_{\mathrm{A2}})/(U_{\mathrm{oracle}}-U_{\mathrm{A2}})$ on test instances. The two statistics are the interquartile mean (IQM) of gap closed over eligible nodes, and the probability of improvement (PoI): the share of test instances on which the arm's utility exceeds A2's, averaged over nodes. A3 and A5 are tested with a Holm step-down at family-wise one-sided level 0.05. An arm passes if the bootstrap lower bound of its IQM is above 0 and the lower bound of its PoI is above 0.5. The gate passes if either arm passes. There is one read.

The gate has low power. In the simulation that fixed the pass rule, the mean two-arm power was \GatePowerMain{} at an effect size of \GatePowerEffect{}, and \GatePowerSmallTOne{} when a T1 node has six instances (qualifiers in Appendix~\ref{app:gate}). A gate that does not pass is therefore weak evidence that learning adds nothing to one-step decisions.
